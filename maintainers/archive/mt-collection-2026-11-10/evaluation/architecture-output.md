**case_id: recovery-boundaries-7**

这份提案目前不能宣称“替代事务”，也不能把多个 List 依次 `RENAME` 后写入 `complete` 视为整个品牌的原子发布。最终值 journal 可以成为有限条件下的中断恢复协议，但恢复、隔离、发布可见性、服务器耐久性和下游提交是不同保证。

本次只根据提案做静态评审；没有读取项目实现、核对线上配置或执行故障实验。以下机制判断有明确边界，线上适用性仍待验证。

| 提案机制 | 可以成立的保证 | 当前不能成立的结论 |
|---|---|---|
| 先保存最终值计划，再重写目标 | 在计划可靠保存、目标写者受控、恢复顺序正确的前提下，可重放同一次转换 | 不保证多个命令同时生效，不保证读者看不到中间态 |
| 进程内 `RLock` | 约束使用同一把锁的本进程线程 | 不能阻止另一进程写入，也不能证明崩溃后接管安全 |
| `DEL/RPUSH` 重建 List | 恢复完成后可能得到计划里的最终值 | 当前直接 `LRANGE` 的读者可能看到不存在、空列表、部分写入或不同批次的数据 |
| `HSET complete` | 表示生产者写入了一个阶段标记 | 未绑定同一任务版本与必需结果清单时，不能证明业务完整，更不能证明下游已经提交 |
| 多次 `RENAME` | 若实际引擎、拓扑与权限支持，每次替换可具有该命令边界内的原子性 | 多个结果之间仍有窗口，读者可能看到旧、新批次混合 |
| `SET journal` 成功 | 得到一次命令执行确认 | 不能单独证明断电不丢、不会被逐出或不会被外部清理 |

还需核对“GET 累计结果”的具体含义：若指对同一个 Redis List 键调用 Redis `GET`，命令与数据类型不匹配；若只是泛指读取累计数据，应在协议里写明实际键、类型与命令。

下季度两个 Worker 共用 namespace 是明确的复审触发点。两个进程可能读取相同旧值，分别生成最终值，再相互覆盖 journal 或结果；旧 Worker 也可能在接管后继续写入，覆盖新结果。即使两个计划各自能够重放，也无法据此证明无丢失更新。仅声明“单写者”或加一把会过期的锁，仍不足以证明旧持有者失去写权限。

可比较的选择如下：

1. **优先评估现有关系库单事务。** 若结果、任务状态与发布事实能落在同一事务边界，由它维护唯一权威事实，并结合适当的并发约束处理双 Worker。Redis 若仍供读取，可作为派生数据，明确更新窗口与对账协议。是否适合取决于数据量、完成窗口、争用和现有读取契约；目前没有这些实测，不能直接宣称容量足够。
2. **保留受控单写者和最终值恢复协议。** 适用于能实际阻止第二个写者、允许其恢复语义、读者也遵守可见性协议的场景。必须先确认不可变计划，再写目标，确认全部完成后清理计划；损坏或类型冲突时保留现场。当前直接 `LRANGE` 不满足隔离读要求，不能保持该读法又宣称没有中间态。
3. **按实际交付单位设计发布边界。** 允许各结果独立发布时，可评估逐项暂存、校验和替换。业务确实要求整个品牌一起可见时，可评估不可变版本数据与单一 manifest／指针提交，要求读者一次选定版本并贯穿读取；还需解决并发发布、版本保留和清理。不能仅增加一个 `complete` 字段便声称完成该协议。具体物理设计交 DBA。

普通读写账号不意味着 `RENAME`、条件写或事务命令全部可用；这些能力、键位置限制、持久化和淘汰策略都需按实际部署核对，不能在提案里默认存在。涉及跨存储交接时，还要说明哪个事实唯一权威，避免关系库、Redis 状态各自被当成最终真相。

固定三小时暂停也不能通用化。先说明暂停保护哪条依赖：共享账号、存储、账本或容量故障，应影响依赖它的任务；健康且独立的任务继续运行。业务允许时，应让恢复、补传和清理继续，以便解除准入限制。恢复条件应来自故障消除、依赖检查、明确的限流截止或容量回落。若确有已批准的时间截止，应持久化原截止时间，重启按剩余时间恢复，不能每次重新延长三小时。

此外，多个结果同批发布不等于源接口提供了一致快照；生产者完成也不等于消费者已持久提交。这两条边界需要各自的契约与证据。

建议把以下验证义务交给对应负责人，并在依赖方案落地前完成：

| 验证义务 | 责任与到期点 |
|---|---|
| 用实际账号核对命令、拓扑、持久化、淘汰和清理策略 | DBA／SRE，选型确认前；保留版本、配置及脱敏原始结果 |
| 在每个关键写入前后中断，并模拟“成功但回复丢失” | 实现者提供可控实验，QA 独立验证，恢复方案验收前；检查身份不变、可恢复且不误报完成 |
| 双 Worker 同时执行、接管后旧 Worker 恢复写入 | 实现者与 DBA 负责控制，QA 验证，第二 Worker 启用前；证明拒绝冲突或正确串行，不能覆盖已提交新结果 |
| 实际 `LRANGE` 读者在重写、发布、恢复期间读取 | 读取方实现者与 QA，读契约验收前；核对允许的可见状态及多结果版本一致性 |
| 合法空结果、必需结果缺失、计划损坏或被清除 | 实现者与 QA，批处理集成验收前；空结果可表达，缺失不得冒充完成 |
| 发布后消费者已处理但确认丢失 | 生产者与消费者负责人、QA，交接验收前；不因正式键缺失而盲目重发，明确消费去重与提交边界 |
| 累计结果增长、全量读取／计划保存／重写／恢复成本 | 实现者与 SRE，在代表性数据量下测量，容量承诺前；提交时间、流量和内存证据 |
| 依赖恢复、容量回落和独立任务继续运行 | SRE 与 QA，暂停策略验收前；验证停止范围与恢复条件 |

最终值计划可能反复保存和重写累计结果，成本随累计量增长；目前没有测量，不能给出恢复时限、吞吐或资源上界。合法重复业务行也应保留，不能以“重放去重”为由按内容删行。

需要修订的是这些不成立的架构保证及其依赖契约。架构评审不能据技术限制自行改动业务完整条件或暂停范围；新业务取舍由产品决策者确认，权限与共享 namespace 的控制及残余风险由相应负责人接受。

**case_id: simple-control**

复用已有 ADR 的 PostgreSQL 单事务方案即可。本次只增加来源标识，没有证据表明需要增加 Redis、journal、队列或新的协调机制，也无需另造选型方案。

最小架构增量是明确来源字段的语义和兼容边界：

- 来源值由哪个模块提供并负责校验；它表示采集来源、数据归属还是其他含义。
- 新批次与历史数据是否必须有值，未知来源如何表达；不要未经批准把历史数据归到某个真实来源。
- 现有消费者是否容忍新增字段；仅在它进入实际消费契约时检查严格解码等兼容问题。
- 来源字段是否参与任务身份、去重或唯一性。若只是说明字段，应保持现有身份规则；若要改变这些规则，另行评估对应不变量。

数据语义与访问需求交 DBA，由 DBA 决定物理结构及迁移方式。结果与任务状态继续按已有 ADR 的事务边界提交；本次字段写入不应引入事务外的第二份权威状态。

需要复验的范围是：迁移链与实际数据库一致；旧数据和旧调用兼容；新来源能够正确写入、读回；事务失败时不会留下部分结果或提前完成态。实现者负责变更及适用检查，QA 在现有批任务集成验收中验证。若需要大量回填，DBA 另核对锁与批处理完成窗口；没有回填需求则不增加该项工作。

当前只完成架构建议，没有实施或运行验证。正式交付引用既有 ADR 的编号和版本即可；其 accepted 状态不能作为本次字段已经实现或部署的证据。新增并发写者、跨存储提交或数据量显著增长时，再复审原 ADR 的适用条件。

**case_id: publication-control**

“直到出现非空数据才允许整份月报发布”没有当前已批准需求的依据，并改变了逐指标发布的契约。已确认请求身份，源接口明确成功且 `data=[]`，应按该契约识别为合法空结果；不能仅因没有行，就改判为失败、未采集或启动无期限重试。

交付边界应保持在指标层面：已满足自身完成条件的指标可以独立发布。只有明确依赖某项输入的衍生指标才受该依赖影响，不能凭空增加整份月报的共同停发条件。

需要保留一个语义区别：**合法空集合不自动等于数值零。** 指标展示为零、“无数据”还是“不适用”，应服从既有指标定义与展示契约；若尚未定义，交产品／数据语义负责人补充，不能由实现者任意转换。但这不影响本次响应已经成功返回空结果的判断。

交付时应沿用现有契约，确保消费者能区别“成功且为空”“尚未完成”和“失败”。不能只靠 List 键不存在表达这些不同状态；如现有表达不足，由数据与接口负责人补齐最小契约，并关联对应月份、指标、请求身份和批次版本。正常空结果也应有明确的发布及确认结果，避免旧数据残留或被误认为还在等待。

验证由指标实现者负责接入，QA 在发布旅程验收前独立执行：

- 输入身份正确、明确成功的 `data=[]`，该指标进入约定的成功空状态，读取方能正确展示或消费，不等待未来非空数据。
- 该指标为空时，其他具备发布条件的指标照常发布。
- 实际失败、身份不符或缺少必需输入时，分别按原契约处理，不与合法空结果混淆；影响范围限于真实依赖。
- 同一批次重复提交、重启恢复或确认丢失时，身份与发布内容保持一致，不回退到旧数据或重复产生下游业务效果。

若团队坚持整体停发，应由产品负责人明确接受这一需求变更及其可用性代价，并同步修订相关契约与验收。当前仍按已经批准的逐指标发布要求交付。本次没有实施、调用源接口或执行上述验证；运行结果仍未验证。
