case_id: `ownership-delivery-7`

这份设计需要先补齐任务所有权、业务断点和交付确认，否则换类型继续会同时留下丢任务、重复执行和重复投递的窗口。本次仅评审，未实施或运行验证。

建议保留现有队列和采集框架，做以下最小修订：

| 位置 | 最小修订 |
|---|---|
| `ZPOPMIN` 后才保存 pending | 将领取和持久登记执行权放入存储实际支持的原子或条件更新边界。先核实当前 Redis 版本、ACL、拓扑和持久化配置。仅原子弹出不能覆盖弹出后进程退出的丢任务窗口。 |
| `pending EX 600` | 把可过期的租约与持久任务恢复材料分开。持久记录保存稳定 `task_id`、业务输入、状态、执行者、租约截止时间和执行代次；租约过期后由指定回收者接管。旧执行者迟到提交必须因代次或所有权不符被拒绝。 |
| 回队却保留有效 pending | 回队是所有权移交：在同一受控转换中使旧执行权失效，再使任务可领取。若保留当前执行权等待恢复，就不再创建另一个可执行副本。不能让两个路径都认为自己有权提交。 |
| 从像素位置恢复品牌采集 | 记录“品牌／地区／月份／筛选条件／必要契约版本”等业务断点，以及各单元的结果与证据。恢复时重新确认会话、输入和页面状态；通过请求与响应共同归属，隔离旧任务和旧筛选条件的迟到包。坐标只能用于操作，不能证明哪个月份已完成。 |
| 缺月份当 `[]` | 未收到响应记为 `missing`，请求失败记为 `failed`；只有真实响应、业务成功且归属明确时才能记为 `confirmed-empty`。检查获批契约要求的月份与模块，不能靠“阶段成功”代替完整性检查。 |
| 其他月份逐个发布 | 是否允许逐月交付由现有业务契约决定。允许时，各月使用稳定批次身份独立交付，整体仍标明缺失月份和部分完成状态；要求整项一起可见时，先暂存并校验，再通过版本或 manifest 指针发布。不能从这个场景推导出所有来源都必须整体发布。 |
| 数据与 `unsynced` 分两次写 | 优先把结果与待同步状态纳入同一可用事务／原子边界；不能做到时，采用明确的可恢复计划或等效协议，先持久保存意图，再执行可重放写入，并规定读者如何避开中间态。迁移、删除部分数据时也必须维护游标。仅加进程锁不能约束其他进程。 |
| `RPUSH` 后 `HSET` 回执 | 先区分回执代表入队、持久接管还是业务提交。同一错误重传沿用原 `error_id` 和内容；相同 ID 对应不同内容进入冲突处理。生产者保留未确认记录，确认状态持久化后才清理。消费者应在可用的同一事务或等效恢复协议中保存去重记录与业务变化，提交后才确认。 |

日志交付还有一个已经存在的歧义：追加成功但回复丢失后，下游可能已消费正文并清掉回执。此时“正文和回执都不存在”不能证明从未投递，换 `error_id` 会把同一事件变成新事件。消费者需要保留覆盖生产者离线、重试和人工重放窗口的持久幂等记录；即使把 `RPUSH` 和 `HSET` 原子化，也不能替代这一点。对于历史上已经把正文、回执和去重证据全部清掉的事件，应保留“提交未知”状态并对账，不能补称为恰好一次交付。

调度按共享依赖处理：

- 共享账号失效时，两个依赖该账号的类型都停止使用该账号发起操作，不能切类型绕过。独立健康账号和来源继续运行。
- 品牌限速需记录响应、限流提示、截止时间及其作用范围。若是共享账号或共享配额限制，停止对应共享范围；确认为品牌模块局部限制时，暂停该模块。没有证据时先保护可能受影响的共享范围，再通过受限探测或来源方说明收窄。
- 关键配额账本读写失败时，停止依赖该账本的新增操作；未知次数不能当零，也不能通过换类型继续消耗。增加正常准入预算，在接近额度时主动让出，保留进度且不计作失败重试。
- 独立、非关键的性能统计失败按契约降级并留下诊断，不停止全部采集。
- 暂停类型、保留会话、关闭浏览器和停止进程分别决策。限速本身不证明需要重建浏览器；重开页面也不会恢复额度。等待期间可继续安全的补传、对账和清理。

建议在隔离环境中按以下顺序验证，使用明确的任务、批次和错误 ID，保存实际输入、命令结果及状态快照：

| 注入场景 | 核对结果 |
|---|---|
| 领取后、pending 保存前终止进程 | 任务仍可由唯一恢复路径发现，不静默丢失。 |
| 租约过期后第二进程接管，第一进程迟到提交 | 新执行者继续；旧代次提交被拒绝，同一任务没有两个有效执行者。 |
| 失败回队与进程退出交错 | 最终只有一个可领取／可提交的所有权，稳定 `task_id` 不变。 |
| 恢复时切换月份或地区，注入旧请求的迟到响应 | 正确归属的响应被接收；旧输入响应被隔离，不能污染当前断点。用真实脱敏抓包同时覆盖接收与拒绝。 |
| 一个必需月份缺响应，另一个月份真实返回 `[]` | 前者保持缺失；后者保存空结果证据。整体状态和可发布范围符合交付契约。 |
| 在数据、游标及删除清理的每个关键写入前后中断 | 能恢复或对账，结果不会永久遗漏同步；中间态不会被当成完成。 |
| 日志追加成功但回复丢失，下游随后消费并清理正文 | 原 `error_id` 重试不重复产生业务效果；若幂等证据也已丢失，进入提交未知处理，而非换 ID 重发。 |
| 同内容、不同 `error_id` 的两个独立错误 | 两个事件均被保留，不能按内容误合并。 |
| 账号失效或关键账本失败，同时运行独立健康来源 | 仅依赖故障资源的操作暂停，健康来源继续；性能统计失败不扩大停机范围。 |
| 额度、账号或存储容量恢复 | 重新检查准入，补传能够排空，任务从业务断点继续；不会无依据地只能等到次日。 |

case_id: `empty-control`

第一项保存为有证据的 `confirmed-empty`；第二项保持 `missing` 或等待响应状态。两者不能共用“没有数据”这一种表达。本次仅评审，未修改存储或运行验证。

对确认空结果的任务，保存明确的空批次，例如包含稳定 `batch_id`、任务与月份、地区、必要契约版本、业务成功状态和 `data: []` 的结果记录，并关联脱敏请求与响应证据。请求中才有的地区、月份等身份应随结果注入，不能假设响应会再次提供。不要只靠“没有 List 键”表达空结果。

断点可以把该业务单元标为已采集且确认空。写入结果后，按既有可恢复协议登记待同步游标；消费者应实际接收空批次、持久记录处理结果并确认，然后才能退休该游标。采集完成与消费者落库完成分开记录。如果它是任务最后一个必需单元，完整性检查通过后可结束采集阶段；不能据此直接声称消费者已完成。

完全没收到响应的任务不能写成 `[]`，也不能标记对应业务单元完成。保留原任务身份、输入、尝试信息和恢复材料，按既有超时、重试预算及所有权协议等待、重试或移交。恢复时重新核对输入，并隔离旧尝试的迟到响应。

可执行验证思路：

1. 用两个固定任务分别重放“真实成功空响应”和“没有响应”。检查持久结果：前者有明确 `data: []` 与成功、归属证据；后者无伪造成功结果，断点保持未完成。
2. 让真实消费者读取空批次，查询消费者的持久结果或完成记录，检查其正常确认并清退待同步游标，后续调度不再反复采集该空单元。
3. 在保存空结果与登记游标之间、消费者提交与确认之间分别终止进程并恢复。检查空结果不会丢交付，同一批次重传不会重复产生业务效果。
4. 为无响应任务补入归属正确的迟到响应，再补入错误月份或地区的响应。检查只有符合当前任务及有效执行权的结果被接纳，缺失不会被无依据改成空。
5. 查询任务完整性：确认空单元可以满足相应必需单元条件，缺响应单元仍阻止其所属任务被误报完成；独立已完成任务按各自契约正常交付。
