## durable-state-7

本次是方案评审，未实施，也未连接 Redis 或 SQL。Redis 版本、拓扑、ACL、持久化和故障恢复配置尚未验证。

可接受的是：可从主库重建的响应缓存使用 TTL；在允许的陈旧窗口内用随机抖动分散过期；使用 staging 准备完整结果，再通过受支持的原子替换发布。它们的适用边界需要分别声明。

不可接受的是：把所有键统一视为缓存；让唯一 pending、未确认 journal 和发布证据随意过期或被逐出；用进程内 RLock 约束两个进程；把 staging 消失直接判为发布成功；在允许离线七天的协议中只保留一天回执；在 SQL 提交前删除日志正文；按内容 hash 合并独立事件。

建议按以下生命周期区分：

| 数据 | 过期、清理与恢复要求 |
|---|---|
| 响应缓存 | 可以设 TTL 和抖动，但最大 TTL 必须符合允许的陈旧窗口。如果上限是五分钟，可用 240～300 秒，不能用 300～360 秒。未命中回源，Redis 丢失后重建。 |
| 唯一 pending | 属于任务恢复状态。不能因五分钟到期而销毁唯一执行依据。完成或取消状态、结果及必要交接已持久确认后，才按协议清理。执行租约可以独立过期，但不能让租约过期同时删除任务事实。 |
| 未确认 journal | 保存不可变的计划 ID、结构版本、目标范围和恢复所需内容；先确认计划保存，再写目标，全部确认后清理。损坏、类型冲突或结果不明时保留现场，进入修复或对账。 |
| staging | 准备阶段只有在可安全重建、尚未确认发布意图时，才可以按明确规则回收。发布意图确认后，必须保护其内容和发布身份，直至发布或消费结果可核实。合法空结果也需要明确的完成表达。 |
| 发布、消费回执与去重记录 | 保留期覆盖最长离线七天，以及允许的重试、人工重放、传输延迟和时钟余量。明确计时起点和超窗处理。一天不足；也不能未经分析便认定恰好七天足够。 |

`allkeys-lru` 可以用于只承载可重建缓存的实例。它会逐出未设置 TTL 的键，因此不能用于承载这些唯一恢复状态的共享实例。应把缓存与关键状态分开，或使用能保护关键状态的实际部署方案。关键状态若保存在 Redis，可评估独立实例及 `noeviction`；达到内存上限后仍须处理写入拒绝，不能把保存失败当成成功。

不设 TTL、使用 `noeviction`、收到 `SET` 成功回复，都不能独立证明断电不丢。需要明确可接受的数据丢失窗口，核对实际 AOF/RDB、同步策略、复制及故障切换行为，并验证备份恢复。若任务要求超出这些配置所能提供的耐久性，应让现有事务存储或另一可靠来源保存恢复依据，而不是仅靠 Redis 键存在。

两个进程各自持有 RLock，仍然可以同时覆盖同一 journal。应选择可实际执行的写入协议，例如使用事务存储约束所有权和版本，或使用条件写及有效的 fencing 机制。租约过期后，旧进程的后续写入必须被存储端拒绝；只写“单写者”或只加一把有 TTL 的锁不足以证明这一点。正常读者与恢复过程也必须遵循相同的版本或可见性协议，避免读取半完成状态。

staging 消失可能源于 RENAME、过期、逐出、外部删除或故障丢失，因此当前条件下只能得到“结果未知”。应使用稳定发布 ID、持久发布意图以及目标或消费者的持久回执对账。目标已被消费者取走时，目标缺失同样不表示从未发布。允许至少一次重传时，可按原发布 ID 恢复投递，并由消费者持久幂等处理重复，不能生成新 ID 冒充一次新发布。还需核对 RENAME 在实际拓扑中的键位置、权限和命令约束；单键原子替换不等于整个任务或 SQL 提交原子完成。

日志交接应调整为：

1. 每个独立事件分配稳定事件 ID，重传沿用该 ID 和原内容。内容 hash 只用于完整性检查；两个内容相同的独立事件仍然保留。
2. 消费者在同一个 SQL 事务中写入事件唯一记录并完成对应业务变化。同 ID 不同内容进入冲突处理。
3. SQL 提交成功后，才返回明确表示“业务已提交”的确认，并清理对应输入正文。提交结果未知时保留输入，按同 ID 重试或查询。
4. 生产者持久记录确认后，再清理本地正文；清理失败只继续清理，不能重新生成事件。事务外副作用另需幂等和恢复协议。

以上为设计要求，尚未验证。故障验证至少应覆盖：

- journal 保存、目标写入、发布、SQL 提交及本地确认前后中断，以及操作成功但回复丢失。
- 两个进程并发恢复同一任务、旧租约持有者恢复运行、读者绕过恢复协议。
- staging、journal 被逐出、过期、损坏，以及权限拒绝、内存写满。
- 发布后下游已消费但确认丢失；离线七天后重传及超窗重放。
- 两个同内容不同 ID 的事件、同 ID 不同内容、合法空结果。
- Redis 重启及实际故障恢复后的状态与业务对账。关闭持久化的临时实例或 mock 不能证明断电耐久性。

容量方面应统计未确认状态的数量、大小和积压期限。软阈值暂停新增工作，同时继续补传和确认清理；达到硬上限时保留已有未确认材料，并明确处理路径。

## cache-control

这是可重建、允许陈旧五分钟的响应缓存，可以采用纯 TTL 的最小方案，无需增加任务队列。本次只给方案，未修改配置或数据。

- 每次回源成功后，使用单条带过期参数的 `SET` 写入缓存，TTL 随机取 240～300 秒。五分钟若按源数据读取时点计算，应扣除回源到写入之间的耗时；不要通过缓存命中不断续期。
- 未命中或被逐出时回源主库，再写入带 TTL 的缓存。Redis 不可用时按主库承受能力限流回源，避免无限放大请求。
- 先修正写入路径，再清理已有无 TTL 的缓存。旧值年龄未知，直接补五分钟 TTL 不能保证陈旧上限；可按本业务键前缀分批 `SCAN` 并定向失效，让后续读取重建。过渡期读到无 TTL 的旧条目时也应视为未命中。
- 十万键 × 每键约 2 KB，纯值体约 200 MB；实际内存还包括键、元数据和碎片。设置包含这些开销的容量上限。这个实例只有可重建缓存，`allkeys-lru` 可以接受。
- 缓存不承担唯一恢复职责，因此无需为它增加可靠队列或业务恢复日志。

实施后应抽查过期时间，确认不存在遗漏的无 TTL 写入路径，并验证过期、逐出和 Redis 不可用时能够按限流策略回源。上述检查尚未执行。

## receipt-control

采用稳定事件 ID、SQL 事务内去重和提交后确认即可；本次未实施。

1. **事件产生时保存身份。** e1 首次进入本地持久记录时生成 `event_id`，重传沿用该 ID 和原内容。e2 是独立事件，必须使用另一个 ID，即使内容完全相同。可保存内容摘要用于检查同一 ID 的内容一致性。
2. **接收端原子提交。** 在同一个 SQL 事务中，插入受唯一约束保护的事件 ID，并完成对应业务变化。如果该 ID 已经提交且内容一致，不重复执行业务变化，直接返回其提交确认。同 ID 内容不同则报告冲突并保留现场，不能静默覆盖。并发到达的重复事件由数据库唯一约束和事务处理，不能仅靠应用先查询。
3. **提交后确认。** 确认中包含事件 ID，并明确表示 SQL 业务提交已完成。SQL 提交结果不明或失败时，不返回成功，也不删除仍需恢复的输入。
4. **发送端持久确认后清理。** 生产者收到确认后，先持久记录该事件已确认，再删除对应本地正文。删除失败只继续清理；恢复时不再重新发送已持久确认的事件。

因此，e1 首次投递即使已提交但回复丢失，生产者也只是携带原 ID 重传；消费者识别已提交的 e1，返回确认，不重复产生业务效果。e2 的 ID 不同，应作为另一独立事件正常提交。内容 hash 不能作为两者的去重身份。

SQL 事件 ID 记录应覆盖允许的离线、重试和人工重放窗口；窗口未给定，暂时不能确定清理期限。超窗后应查询、对账或按明确契约处理，不能直接当作新事件执行。若还有 SQL 事务外副作用，需要另行规定其幂等与恢复边界。

建议验证提交前中断、提交成功但回复丢失、重复并发投递、同 ID 内容冲突，以及生产者确认持久化后清理失败。该协议使用至少一次投递及消费者幂等，不据此宣称端到端恰好一次。
