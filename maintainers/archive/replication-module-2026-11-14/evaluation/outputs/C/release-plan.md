## 将来执行的顺序（本轮均未执行）

1. **固定发布身份与工作树边界。** 操作者记录目标环境、配置版本、包 build-B 的不可变摘要、其受测源码/构建指纹、相关测试原始命令/退出码及精确覆盖。标出本次文件与其他任务 WIP；沿既有产物发布方式使用受测包，而非从共享脏树随意重建。若必须重建，先明确输入差异与受影响检查；不复用旧回执冒充新包受测。
2. **继续观察已授权的 service-A 停止。** 核既有 service manager 状态、owner 与进程身份、排空请求/活跃连接、shutdown 日志和端口持有者。按服务约定的排空预算/截止判断是否异常；本输入没有该约定，不能虚构等待秒数。停止方式升级只沿已有授权与运行手册；没有升级授权则交 owner 决策，不强杀别的进程。
3. **确认 A 真正停止并释放端口。** 以 service manager 完成状态、旧 PID 退出/身份与端口监听证据对应；端口仍被占用时不启动第二个实例去碰撞，不开始批量媒体探测。若持有者改变先识别新 owner，不能沿用 A 的停止授权。
4. **沿既有方式让目标实例加载 build-B。** 使用固定包和配置，记录启动命令、退出码、服务 manager 单元、实际消费路径、PID/启动时间、端口绑定及启动日志。命令返回成功仅证明命令完成，尚未证明实例加载包。启动失败先保留日志并定位包加载、配置/依赖、端口或就绪阶段。
5. **先做一个最小就绪探测。** HTTP 成功须同时对应 build-B 的版本/构建指纹与必要依赖状态。若首次探测失败，先查实例阶段与路由：新实例未起、未就绪、配置错、仍路由到 A、缓存或代理。记录每个假设与区分证据，不把后续批量连接失败归类为许多资源损坏。
6. **验证功能加载及一个真实消费者。** 查询功能契约确认同时包含 old_filter、new_category；以已批准功能语义做正例、非法参数/权限等适用负例，并由真实消费者操作一次新筛选，同时检查旧筛选兼容。不知道具体 URL/参数编码就从既有部署配置/接口契约定位，不能在计划中编造可运行生产命令。
7. **最小路径通过后才运行适用批量资源探测。** 再按本次包变化及既有门禁选择集合，区分连接/就绪、授权、单个媒体缺失/解码等错误。已通过且依据不变的测试不重复扩全量；新增失败/变更再选受影响检查。仅记录实际执行项。
8. **按现有恢复方案与发布观测闭环。** 记录版本/环境/时间/指纹、健康及功能/消费者原始证据、监控窗口与执行者。根据既有基线和产品护栏决定继续观察、放量或恢复，不能用模板数字代替该服务阈值。只有运行身份为 B、功能与适用消费者通过、所需恢复及发布检查已落实，才能据实际记录陈述 deployed。

## 定位树与停止条件

- 当前优先定位 A 排空为何未完成：活动请求是否结束、shutdown hook/后台工作是否阻塞、manager 是否报告 stopping。服务约定预算内继续观察，超预算由已有运行手册决定升级/恢复；不凭固定 sleep 后强杀。
- 端口空闲但 B 起不来：查启动日志、包实际加载路径、配置与必要依赖。禁止把“地址暂时连不上”当资源不存在。
- B 显示已起而 health 仍是 A：交叉核端口 PID、直接实例与入口代理/缓存的响应指纹；这只是待验证方向，当前没有证据断言代理缓存故障。
- health=B 但没有 new_category：比对所加载包、配置开关、路由/子进程及候选契约；定位后决定是否实现缺陷。不能以 200 跳过功能验证。
