# Host notes (maintainers only — NOT assembled into agent prompts)

v4 moved these facts out of the role prompts: they are for people editing this plugin, and they cost the working agents attention. The factory (`scripts/render-role-agents.py`) and health check (`scripts/health_check.py`) enforce them mechanically.

| Fact | Consequence in this plugin |
|---|---|
| ZCode/Grok inject one `agents/<role>.md` as the child system prompt; `@import` is not expanded | Sources live in `agents/profiles/<role>/` + `agents/_lib/`; the factory concatenates at compile time |
| A custom `tools:` list is exhaustive; MCP tools drop off unless listed as `mcp__<server>__<tool>` | Tool profiles are explicit lists; optional MCP tools come from `adapters/extra-tools.json` (compile-time allowlist) |
| `WebSearch` / `WebFetch` are real ZCode tool names (seen in the built-in `Explore` profile, host metadata probe 2026-09-17) | Web profile = author list + `WebSearch, WebFetch` for research/product/design/architecture hats |
| A non-empty `skills:` frontmatter list is a FilteredSkillPort allowlist | Never emit `skills:`; companion skills and the reviewer pool would fail with "Skill is not allowed for subagent" |
| Unknown frontmatter keys make Grok skip the agent (`memory`, `effort`, `thoughtLevel`, snake_case keys) | Factory strips them; health check forbids them |
| Plugin subagents get the Skill tool injected; ZCode's Skill page still requires Skill in custom lists | Every profile lists `Skill` |
| Skill directories named like build output (`coverage`, `dist`, …) are skipped by `shouldWalkSkillDirectoryEntry` | Health check forbids those names (v3.20.4) |
| Agent definitions are snapshotted at session start; the skill registry is re-scanned at spawn | After re-rendering agents, smoke-test in a **new** window |
| `RespondToCoordinator` is host-added | Not listed in profiles |
| macOS bash 3.2: `$VAR（` parses the full-width char into the name | Use `${VAR}` before full-width punctuation in scripts |

## Cross-host packaging and reference-only use (verified 2026-09-27: Claude Code 2.1.283, Grok 1.0.41, Codex CLI 0.156.1)

Every host uses the plugin by reference to one directory; nothing is copied (hosts.json `install`, hosts.md "Reference only").

`adapters/hosts.json` is the single source for identity and host settings; `scripts/workflow.py render` writes every manifest and `skills/sdlc/references/hosts.md` (the runtime table hats and the manager read). `render-role-agents.py` also writes the Codex agents. ZCode's `.zcode-plugin/plugin.json` is generated byte-identical to the hand-written original.

| Fact (how it was checked) | Consequence in this plugin |
|---|---|
| Claude Code does not scan a project's `.claude/plugins/`; plugins come from a marketplace (docs + isolated `CLAUDE_CONFIG_DIR` runs) | `.claude-plugin/marketplace.json` with `source: "./"`; a project registers `./<path-to-plugin>` under `extraKnownMarketplaces` and enables `sdlc-workflow@sdlc-workflow` |
| Claude Code rejects aggregate-marketplace entries that traverse a symlink (`link-traversing entry`); a marketplace root reached through a symlink is fine and loads in place | The plugin directory is its own marketplace |
| Claude Code and Grok scan `agents/` recursively; without a list, `agents/_lib` and `agents/profiles` fragments became 46 extra agents (Claude debug log: 65 agents) | `.claude-plugin/plugin.json` and `.grok-plugin/plugin.json` list the 19 rendered agents. Marketplace-entry component fields are ignored for in-place loading, so the list lives in plugin.json |
| Claude Code ignores `permissionMode` on plugin agents and logs a warning | Harmless; kept for ZCode/Grok |
| Grok manifest precedence: root `plugin.json` > `.grok-plugin/plugin.json` > `.claude-plugin/plugin.json` (`grok plugin validate` on fixtures) | **No root `plugin.json`**: an Agent Plugins portable manifest there made Grok drop the agent list (1 agent dir instead of 19). health-check forbids it |
| Grok project plugins need a trusted project and `[plugins].enabled`; plugin agents cannot declare `mcpServers`, hooks or `bypassPermissions` | Same frontmatter constraints as before (`FORBIDDEN_FM_KEYS`) |
| Grok documents kebab-case skill keys (`when-to-use`); ZCode and Codex route on `name` + `description` only | `description` must carry the trigger on its own (health-check DESC); `when_to_use` stays a Claude-only supplement |
| Codex plugins carry skills, MCP servers, apps and hooks — not commands or agents (OpenAI "Submit your Claude Code plugin") | Commands become "skill + `mode:`" requests (hosts.md table; the skills honour an explicit `mode:`). Role agents are generated TOML in `adapters/codex/agents/`, linked (not copied) by `scripts/link-codex.py` |
| Codex reads `.codex-plugin/plugin.json` before `.claude-plugin/plugin.json`, and `.agents/plugins/marketplace.json` before `.claude-plugin/marketplace.json` (isolated `CODEX_HOME` installs) | Codex gets its own manifest and marketplace. Codex entries require `policy` + `category`, which Claude Code reports as unknown (`--strict` fails), so the two marketplace files stay separate |
| `codex plugin add` installs a **copy** into `~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/`; it drops symlinks inside the plugin (a `skills` link gave 0 skills), and a cache version directory replaced by a symlink reads as not installed | Codex never uses the plugin mechanism here. `.codex-plugin/` and `.agents/plugins/marketplace.json` exist for distribution only |
| `$CODEX_HOME/skills/<dir>` as a directory symlink is followed; skills appear as `<plugin>:<skill>` (namespace from the plugin manifest above `skills/`), paths are shown through the link | `link-codex.py` links `~/.codex/skills/sdlc-workflow` → `skills/`. PLUGIN_ROOT is resolved from the SKILL.md **real path** (hosts.md) |
| Symlinked agent TOML files are loaded (a `codex exec` probe listed a linked `zz-ref-probe` agent); `skills.config[].path` does not add undiscovered skills; Codex has no project-scoped skill directory of its own (`.agents/skills` is shared with Grok and Claude Code) | Role agents are symlinks in `<project>/.codex/agents/` (relative when the plugin sits inside the project) or `~/.codex/agents/`; the skills link is user-level |
| `claude plugin install` writes a cache copy; a `directory` marketplace enabled through settings (project or user) with no install loads in place (27 skills / 7 commands / 19 agents, no cache directory) | Claude Code is wired through settings only |
| `grok plugin install` keeps a hashed copy under `~/.grok/installed-plugins`; `.grok/plugins/`, `~/.grok/plugins/` and `[plugins].paths` read the directory in place | Grok is wired through symlinks only |
| Codex custom agents are TOML (`name`, `description`, `developer_instructions`, optional `sandbox_mode`) in `<project>/.codex/agents/` (trusted projects) or `~/.codex/agents/`; built-ins are `default`, `worker`, `explorer`; spawn selects `agent_type`; no Skill tool | Agents are named `sdlc-workflow-<role>` (no colon), reviewer/qc get `sandbox_mode = "read-only"`, the body gains a Codex host note (read SKILL.md instead of the Skill tool). Generic fallback on Codex is `default`. The generated TOML parses with Python tomllib |
| Not verified here: a live Codex spawn of a linked role agent (only its listing), and a ZCode session after these files were added (no ZCode CLI) | Check `host_spawn` records on first real Codex use, and the ZCode startup log (`bootstrap.app.startup.plugins.completed`) for unchanged plugin counts |
