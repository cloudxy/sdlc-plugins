# Host notes (maintainers only — NOT assembled into agent prompts)

v4 moved these facts out of the role prompts: they are for people editing this plugin, and they cost the working agents attention. The factory (`scripts/render-role-agents.py`) and health check (`scripts/health_check.py`) enforce them mechanically.

| Fact | Consequence in this plugin |
|---|---|
| ZCode/Grok inject one `agents/<role>.md` as the child system prompt; `@import` is not expanded | Sources live in `agent-sources/profiles/<role>/` + `agent-sources/_lib/`; the factory concatenates at compile time |
| A custom `tools:` list is exhaustive; MCP tools drop off unless listed as `mcp__<server>__<tool>` | Tool profiles are explicit lists; optional MCP tools come from `adapters/extra-tools.json` (compile-time allowlist) |
| `WebSearch` / `WebFetch` are real ZCode tool names (seen in the built-in `Explore` profile, host metadata probe 2026-09-17) | Web profile = author list + `WebSearch, WebFetch` for research/product/design/architecture hats |
| A non-empty `skills:` frontmatter list is a FilteredSkillPort allowlist | Never emit `skills:`; companion skills and the reviewer pool would fail with "Skill is not allowed for subagent" |
| Unknown frontmatter keys make Grok skip the agent (`memory`, `effort`, `thoughtLevel`, snake_case keys) | Factory strips them; health check forbids them |
| Plugin subagents get the Skill tool injected; ZCode's Skill page still requires Skill in custom lists | Every profile lists `Skill` |
| Skill directories named like build output (`coverage`, `dist`, …) are skipped by `shouldWalkSkillDirectoryEntry` | Health check forbids those names (v3.20.4) |
| Agent definitions are snapshotted at session start; the skill registry is re-scanned at spawn | After re-rendering agents, smoke-test in a **new** window |
| `RespondToCoordinator` is host-added | Not listed in profiles |
| macOS bash 3.2: `$VAR（` parses the full-width char into the name | Use `${VAR}` before full-width punctuation in scripts |

## Cross-host packaging and reference-only use (verified 2026-09-27: Claude Code 2.1.283, Grok 1.0.41, Codex CLI 0.156.1)

Every host uses the plugin by reference to one directory; nothing is copied (hosts.json `install`, hosts.md "Reference only").

`adapters/hosts.json` is the single source for identity and host settings; `scripts/workflow.py render` writes every manifest and `skills/sdlc/references/hosts.md` (the runtime table hats and the manager read). `render-role-agents.py` also writes the Codex and Kimi agents. ZCode's `.zcode-plugin/plugin.json` is generated byte-identical to the hand-written original.

| Fact (how it was checked) | Consequence in this plugin |
|---|---|
| Claude Code does not scan a project's `.claude/plugins/`; plugins come from a marketplace (docs + isolated `CLAUDE_CONFIG_DIR` runs) | `.claude-plugin/marketplace.json` with `source: "./"`; a project registers `./<path-to-plugin>` under `extraKnownMarketplaces` and enables `sdlc-workflow@sdlc-workflow` |
| Claude Code rejects aggregate-marketplace entries that traverse a symlink (`link-traversing entry`); a marketplace root reached through a symlink is fine and loads in place | The plugin directory is its own marketplace |
| Claude Code and Grok scan `agents/` recursively; historically the source fragments under agents/ became 46 extra agents (Claude debug log: 65 agents); even an explicit list did not silence strict default-directory validation | Source fragments now live outside agents/, in agent-sources/. agents/ contains exactly 19 generated roles; explicit lists remain in the Claude/Grok manifests. Both Claude manifests pass --strict (2026-09-30) |
| Claude Code ignores `permissionMode` on plugin agents and logs a warning | Harmless; kept for ZCode/Grok |
| Grok manifest precedence: root `plugin.json` > `.grok-plugin/plugin.json` > `.claude-plugin/plugin.json` (`grok plugin validate` on fixtures) | **No root `plugin.json`**: an Agent Plugins portable manifest there made Grok drop the agent list (1 agent dir instead of 19). health-check forbids it |
| Grok project plugins need a trusted project and `[plugins].enabled`; plugin agents cannot declare `mcpServers`, hooks or `bypassPermissions` | Same frontmatter constraints as before (`FORBIDDEN_FM_KEYS`) |
| Grok documents kebab-case skill keys (`when-to-use`); ZCode and Codex route on `name` + `description` only | `description` must carry the trigger on its own (health-check DESC); do not rely on supplemental keys for discovery; Grok now documents `when_to_use` as an alias too |
| Codex plugins carry skills, MCP servers, apps and hooks — not commands or agents (OpenAI "Submit your Claude Code plugin") | Commands become "skill + `mode:`" requests (hosts.md table; the skills honour an explicit `mode:`). Role agents are generated TOML in `adapters/codex/agents/`, linked (not copied) by `scripts/link-codex.py` |
| Codex reads `.codex-plugin/plugin.json` before `.claude-plugin/plugin.json`, and `.agents/plugins/marketplace.json` before `.claude-plugin/marketplace.json` (isolated `CODEX_HOME` installs) | Codex gets its own manifest and marketplace. Codex entries require `policy` + `category`, which Claude Code reports as unknown (`--strict` fails), so the two marketplace files stay separate |
| `codex plugin add` installs a **copy** into `~/.codex/plugins/cache/<marketplace>/<plugin>/<version>/`; it drops symlinks inside the plugin (a `skills` link gave 0 skills), and a cache version directory replaced by a symlink reads as not installed | Codex never uses the plugin mechanism here. `.codex-plugin/` and `.agents/plugins/marketplace.json` exist for distribution only |
| A directory symlink under a Codex skills root (`<project>/.codex/skills/` or `$CODEX_HOME/skills/`) is followed; skills appear as `<plugin>:<skill>` (namespace from the plugin manifest above `skills/`), paths are shown through the link | `link-codex.py --project` links `<project>/.codex/skills/sdlc-workflow` → `skills/`. PLUGIN_ROOT is resolved from the SKILL.md **real path** (hosts.md) |
| Symlinked agent TOML files are loaded (a `codex exec` probe listed a linked `zz-ref-probe` agent); `skills.config[].path` does not add undiscovered skills. Codex also reads a project's `.codex/skills/` (not in the official docs; found from any subdirectory; the listed root is `<project>/.codex/skills`), so the project directory mirrors `.claude/` | `link-codex.py --project` puts both the skills link and the agent links in `<project>/.codex/` (relative when the plugin sits inside the project), isolated to that project; without `--project` they go to `$CODEX_HOME`, shared by every project |
| `claude plugin install` writes a cache copy; a `directory` marketplace enabled through settings (project or user) with no install loads in place (27 skills / 7 commands / 19 agents at the 2026-09-27 check, no cache directory; `/sdlc-refine` and `/sdlc-fix` were added later). | `grok plugin install` keeps a hashed copy under `~/.grok/installed-plugins`; `.grok/plugins/`, `~/.grok/plugins/` and `[plugins].paths` read the directory in place | Grok is wired through symlinks only |
| Codex custom agents are TOML (`name`, `description`, `developer_instructions`, optional `sandbox_mode`) in `<project>/.codex/agents/` (trusted projects) or `~/.codex/agents/`; built-ins are `default`, `worker`, `explorer`; spawn selects `agent_type`; no Skill tool | Agents are named `sdlc-workflow-<role>` (no colon), reviewer/qc get `sandbox_mode = "read-only"`, the body gains a Codex host note (read SKILL.md instead of the Skill tool). ## Five-host integration (2026-09-30)

- Version 4.2.0 adds Kimi manifests and generated role profiles, plus a project-only linker. Official [plugin documentation](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/plugins) says installation creates a user-level managed copy, so the local reference path uses `.kimi-code/skills/<skill>` and `.kimi-code/agents/sdlc-workflow-<role>.md` symlinks instead. The manifest supports distribution; local tests do not pretend it was installed.
- Kimi [agent discovery](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/agents) walks from the nearest Git root. Its tool names match exactly; all roles exclude Agent/AgentSwarm and set `subagents: []`. Reviewer/qc use only Read/Glob/Grep/Skill, without optional MCP additions. Project skills have bare names; packets retain qualified logical names.
- Kimi's real workspace catalog returned all 27 linked skills from the Git root and a subdirectory, and zero SDLC project skills outside. This establishes discovery, not model execution or G-fresh.
- Grok 1.0.44 `inspect --json` on auto_agents reports the enabled project plugin with 27 skills and 19 agents. Its top-level agents/skills arrays omit plugin components; `plugin details` did not resolve this project-only plugin. Use the plugin's `provides` inventory rather than interpreting the empty arrays as missing roles.
- Codex 0.157.1 `debug prompt-input` discovered all 27 skill paths in an isolated trusted project and subdirectory, with none outside. This endpoint does not expose the role catalog; the 19 TOML definitions and links are structurally checked. The existing auto_agents hub and 20 links are unchanged.
- `reference_links.py` preflights all source/target conflicts before installing, preserves foreign links/files, rejects redirected host subdirectories, recognizes equivalent links through a hub, and removes only links still pointing at its own source. Removal also handles owned dangling links. An I/O failure rolls back newly created links; empty directories may remain.
- A generic fallback is not an equivalent reviewer sandbox. Verify the effective read-only tools/sandbox and fresh context, or leave the review blocked. Codex parent runtime overrides can change declared sandbox settings. Native child dispatch and independent review require separate live evidence.

The execution plan, baseline, commands/exit codes and remaining host checks are maintained in the dated `grok-files/sdlc-workflow` execution directory, not in this repository. No business task history is rewritten by this update.

- Actual Codex CLI 0.157.1 forward test exposed `collaboration.spawn_agent` with no type selector, so it could not select a linked role (zero dispatches). The runtime table now distinguishes typed custom-agent support from prompt-bound fallback; `task_name` is not a type, and reading a TOML does not apply its sandbox. A reviewer fallback needs a verified read-only inherited session.
