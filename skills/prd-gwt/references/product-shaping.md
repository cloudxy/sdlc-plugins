# 产品塑形：先找到核心价值，再写需求

GWT 能保证需求**可测**，但保证不了需求**值得做**、**是核心**。这份参考解决写 spec 之前的三个问题：用户到底要完成什么任务？哪些功能是核心？这次先做哪个方案？

## 1. 用任务（JTBD）描述需求，而不是用功能

```
当 <情境>，我想要 <动机>，以便 <期望的结果>。
```

| 用户原话（解法） | 任务（JTBD） |
|---|---|
| 「加个导出 Excel 按钮」 | 当每周一要给老板汇报时，我想快速拿到上周数据的可读版本，以便 10 分钟内交差而不是花 2 小时 |
| 「市场里要有四类资产卡片」 | 当我（租户管理员）想给团队加一项能力时，我想确认它能解决我的问题并马上启用，以便不用找技术同事评估 |

同一个任务，有功能性（完成事）、情感性（不焦虑、有掌控感）、社会性（在老板面前显得专业）三层。亮点往往藏在后两层。

**任务比功能稳定**：功能会被替代，任务不会。把任务写进 `strategy.md` 第 2 节，每个功能都回答「它服务哪个任务的哪一步」。

## 2. 核心价值路径与 Aha 时刻

```
谁 → 触发情境 → 关键动作 → 【Aha：第一次得到价值的那一刻】 → 回来的理由（核心循环）
```

找 Aha 时刻的三个问题：
1. 留存下来的用户和流失的用户，**最早**在哪个行为上出现差异？（有数据时用数据，例如「7 天内生成过 3 份报表的用户留存高 2 倍」）
2. 用户在访谈里说「这时候我觉得值了」的是哪一步？
3. 如果只能保留一个屏幕，保留哪个？

**Aha 必须能被用户意识到**：结果要显眼、要快、不需要解释。验收走查时就检查这个。

## 3. 识别核心功能：移除测试 + 分层 + Kano

### 移除测试

逐个功能问：**去掉它，目标用户还能到达 Aha 吗？**

| 答案 | 层级 |
|---|---|
| 到达不了 | **核心**（在价值路径上） |
| 能到达，但产品不能卖 / 不能合规 / 不能运营 | **支撑**（账号、权限、计费、审计） |
| 能到达，但价值传不出去、转化不了 | **增长**（分享、邀请、付费引导） |
| 能到达，只是更顺更爽 | **体验** |
| 能到达，且没人在意 | 砍 |

### Kano 分类（决定「做到什么程度」）

| 类型 | 表现 | 投入策略 |
|---|---|---|
| 必备 | 缺了强烈不满，做好了不加分 | 做到够用即可，不要镀金 |
| 期望 | 越好越满意（线性） | 与竞品比较，做出可感知的领先 |
| 魅力 | 没有不失望，有了惊喜 | 集中投入 1 个，做成签名时刻 |
| 无差异 | 做不做都一样 | 不做 |

有访谈条件时用 Kano 问卷的「有 / 没有」成对问题；没有条件时用评论区与竞品差评推断，并标「推断」。

### 常见误判

| 误判 | 纠正 |
|---|---|
| 把操作者（平台管理员）当唯一用户 | 列出所有角色：谁获得价值、谁付费、谁操作。双边产品两边的价值路径都要写，哪怕另一边本轮只做假设 |
| 支撑功能被当成核心（「后台管理要全」） | 支撑功能做「够用」，把精力留给价值路径 |
| 竞品有 = 核心 | 竞品的核心未必是我们用户任务的核心 |

## 4. 机会-方案树（Opportunity Solution Tree）

```
目标结果（北极星或驱动指标）
├── 机会 1：用户痛点 / 未满足的任务（来自证据）
│   ├── 方案 A
│   ├── 方案 B
│   └── 方案 C
└── 机会 2
    └── …
```

规则：
- 先选**一个机会**（按对目标结果的影响 × 证据强度），仅对未解决的决定比较可信方案；已批准方案直接引用。
- 方案之间要**真的不同**：不同的交互模式、不同的价值交付方式、不同的规模——而不是同一方案的三个版本。
- 每个方案配一个**最便宜的验证**（假门、原型、访谈、数据查询），写进 spec §2.4。

## 5. 方案对比的维度

| 维度 | 问题 |
|---|---|
| 任务覆盖 | 解决了任务的哪几步？ |
| 价值路径贡献 | 让 Aha 更快 / 更强 / 更常发生 / 更多人经历？ |
| 亮点可能性 | 能不能做出可演示的签名时刻？（问 growth 与 designer） |
| 差异化 | 与用户实际在用的替代品比，差在哪？ |
| 代价 | 粗估人天（问 architect） |
| 风险 | 价值风险（用户不要）· 可用性风险（用户不会用）· 可行性风险 · 商业风险 |

**用户最初提的方案必须在表里**，并诚实比较；它常常是成本最低但只解决一部分任务的方案。

## 6. MVP 骨架：沿价值路径切，而不是按模块切

```
❌ 按模块做 MVP：先把「后台管理」做全，再做「货架」，最后做「详情」
✅ 按路径做 MVP：先让一个租户管理员能「找到 → 看懂 → 启用 → 用上」一个能力，每一步做到够用
```

- 「行走的骨架」：整条价值路径每一步都存在（哪怕粗糙），再逐步加厚。
- 砍范围时**围着路径砍**（角色、场景、数据量、自动化程度、格式），不要**砍断路径**。

## 7. 0→1 与低证据场景：假设模式

没有工单、没有行为数据时，不要：
- ❌ 把价值标成「未量化」然后排除在验收之外（等于放弃验证产品最重要的部分）；
- ❌ 编造证据。

要：
- ✅ 写成**可证伪的假设** + 最便宜的验证 + 判定指标 + 判定时间点：

| id | 假设 | 验证 | 指标（metrics.yaml id） | 判定 |
|---|---|---|---|---|
| A-1 | 租户管理员在看到详情页「帮你做」示例后，会在同一会话内启用能力 | 上线后 14 天，按会话统计 | detail_to_enable_rate | ≥ 15% 为成立 |

- 在 `strategy.md` 关键假设表登记，analyst 提交带证据结论，由 PM 采纳并更新状态。
- 假设成立前，相关的大投入（例如推荐算法）放 Later；让本次交付足以验证假设。

## 8. 写进 spec 与产品层的位置

| 产出 | 位置 |
|---|---|
| 任务（JTBD）、Aha、北极星、关键假设 | `strategy.md` |
| 价值路径、功能分层、Kano、关键旅程、Now/Next/Later | `feature-map.md` |
| 本功能在路径上的位置、方案对比、本功能假设 | `spec.md` §2 |
| 旅程步骤表（J-n） | `spec.md` §3 |
