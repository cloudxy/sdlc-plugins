# PM 验收走查：在运行中的产品上，用用户的身份走一遍

阶段 `accept`（verify 之后、最终审查之前）。**「测试全绿」不是验收。** 验收回答的是：用户按关键旅程走下来，能不能真的得到我们承诺的价值？

## 准备

| 输入 | 用途 |
|---|---|
| `00-discover/briefing.md` 的 Claim 与 Growth 段 | 我们承诺了什么价值、给谁 |
| `01-define/spec.md` 的核心价值与 Aha、关键旅程 J-n | 走查脚本 |
| `04-verify/coverage.md` 与 E2E 截图 | 已被自动化证明的部分 |
| `03-impl/*integration*.md` | 联调时的实际表现 |
| 运行中的构建（`sdlc.config.yaml` 的 `app.base_url`） | 亲自走 |

## 走查方法

1. **以目标人群的身份**，从真实起点开始（例如新注册账号、空数据、手机宽度），不要从开发者常用的已登录已有数据状态开始。
2. 按 J-n 逐步操作，每一步截图：`bash PLUGIN_ROOT/scripts/ui-evidence.sh <url> <feature>/04-verify/shots/pm <宽度>`，然后**打开截图看**。
3. 每一步记录：做了什么、看到什么、花了多久、有没有犹豫或卡住、是否符合 spec。
4. 到达 Aha 时刻时判断：用户**是否能意识到**价值？（结果是否显眼、是否需要解释、是否被弹窗/加载/空态挡住）
5. 走一条「不顺利」的路径：空数据、网络慢、没权限、输入错误——用户能否自己恢复？

## 判定表

| J-n | 步骤 | 期望（spec） | 实际（截图） | 用时 | 差距 | 严重度 |
|---|---|---|---|---|---|---|
| J-1 | 3 | 30 秒内看到报表首屏 | 45 秒，中途空白 20 秒无进度 | 45s | 无进度反馈，用户会以为卡死 | 阻塞 Aha |

严重度：**阻塞 Aha**（用户到不了核心价值）· **损伤价值**（能到，但价值被削弱或难以察觉）· **摩擦**（多余步骤、文案不清）· **瑕疵**。

## 结论规则

| 结论 | 条件 |
|---|---|
| `结论：通过` | 所有 J-n 能走通，Aha 时刻清晰可感知，无「阻塞 Aha」「损伤价值」级差距 |
| `结论：有条件通过` | 无阻塞；存在「损伤价值」级差距，且有明确修复计划、负责人与期限（需用户接受） |
| `结论：不通过` | 任一 J-n 走不通，或出现「阻塞 Aha」级差距 |

结论行原样写成 `结论：通过` / `结论：有条件通过` / `结论：不通过`（闸门据此判定）。

## 差距的去向

| 差距性质 | 交给谁 |
|---|---|
| 构建与 spec 不一致 | 实现帽（frontend / backend）返工 |
| 构建符合 spec，但 spec 本身让价值出不来 | 自己（pm）改 spec → 标 stale → 下游重做 |
| 体验与选定设计方向不一致 | designer 的设计走查会给出，协同确认 |
| 对外说法与构建不一致 | growth 的卖点核验 |

## 回写产品层

- `feature-map.md`：更新功能状态、旅程的实际步数/用时与成功标准达成情况。
- `strategy.md`：若走查推翻了关键假设（例如 Aha 需要的步数远多于预期），在假设表标注并提 open question。
