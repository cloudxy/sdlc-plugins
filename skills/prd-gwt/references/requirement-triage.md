# 需求分诊：理解缺口、假设与排序

## 分诊决策树

```
需求进来
├─ 已有清楚的范围、行为和授权吗？
│   是 → 复用来源，只处理影响本轮的遗漏；不重开已定方案
│   否 ↓
├─ 有具体证据或场景吗？（工单号/访谈/数据/可复现事件）
│   否 → 用场景/例子帮助表达；新想法标假设并设计低成本检验
│        无法支撑大投入时缩小或暂缓，不把缺证据等同于伪需求
│   是 ↓
├─ 产品现在能做到吗？
│   能 → 不是产品需求：用户找不到 → /designer（信息架构）
│                      用户不知道 → ops enablement（教/开/告，不是 sre）
│   不能 ↓
├─ 描述的是「问题」还是「解法」？
│   解法且目标未清 → 按需探索目标（下节），保留原提案
│   问题 ↓
├─ 多少用户有这个问题？
│   一个客户 → 能泛化吗？
│              不能 → 比较人工/配置与专用交付的价值、代价；不自动扩大成通用产品
│              能 → 按泛化后的形态重写需求
│   多个 ↓
└─ 进第 2 步问题定义
```

## 挖问题的三连问

当目标尚不明确时，下列问题可帮助理解；答案已知或方案已获明确授权时复用。用户答不上来、否定选项或改变目标时，按[共同对话方法](../../discover/references/discuss-protocol.md)切换帮助方式，不强制问完三题。

```
① 你现在怎么做这件事的？
   → 拿到现状与 workaround；当前成本是价值线索，不是价值上限

② 卡在哪一步？
   → 定位真实痛点。往往和用户以为的不是同一处

③ 这件事做成了，你接下来做什么？
   → 挖出背后的真实目标。经常发现有完全不同的更优解
```

### 实例：从「加个导出按钮」到真需求

```
用户：能不能加个导出 Excel 的按钮？

① 你现在怎么做的？
   → 手动一条条复制到 Excel，30 条要 20 分钟

② 卡在哪一步？
   → 不是复制慢，是复制完还要手动加一列「预计完成时间」
     再发给外部团队，对方回填后我再手动录回系统

③ 做成了接下来做什么？
   → 发给外部团队，等他们回填，再录回系统

真需求：与外部团队协作处理工单，目前靠 Excel 人肉往返
可能的解法：
  A. 导出按钮（用户提的）——省 20 分钟，但往返和录回还在
  B. 导出 + 导入回填 ——省掉手工录回
  C. 外部协作者只读链接 + 在线回填 ——彻底去掉 Excel
```

用户提的 A 是成本最低的解法，但**只解决了三分之一的问题**。三连问的价值就在这里：不问，就只会做 A，然后下个月用户回来说「能不能再加个导入」。

### 三连问的追问技巧

| 用户回答 | 追问 |
|---|---|
| 「这样比较方便」 | 现在不方便体现在哪？多花多少时间？ |
| 「其他系统都有」 | 你在那个系统里用它做什么？ |
| 「以后可能需要」 | 哪种未来场景、有什么依据？标记假设；按风险选择检验、预留或暂缓 |
| 「老板要求的」 | 老板想解决什么问题？（往老板那边再走一遍三连问） |
| 「就是想要」 | 有它和没它，你的工作有什么不同？ |

## 需要进一步理解的表达

| 形态 | 例子 | 真实处理 |
|---|---|---|
| 解法伪装 | 「加个导出按钮」 | 三连问挖问题 |
| 竞品抄袭 | 「XX 有这个功能」 | 我们的用户有同样的问题吗？我们的场景一样吗？ |
| 未来假设 | 「以后可能需要多语言」 | 当前或计划服务谁？保留假设及检验，不无依据承诺大范围建设 |
| 万能配置 | 「让这个变成可配置的」 | 有几个客户需要不同的值？1 个 → 硬编码 |
| 全都要 | 「所有字段都要支持筛选」 | 哪几个字段真的会被筛？看埋点数据 |
| 完美主义 | 「这个交互不够优雅」 | 有用户抱怨吗？影响完成任务吗？ |
| 技术驱动 | 「我们应该上 AI」 | 探索目标和适用场景；技术探索可作为有边界的实验，不直接认定生产价值 |

未来可能性不能自动成为当前实现范围；记录假设、投入边界和决定来源。新产品探索也不需要假装已经有行为数据。

## RICE 打分

```
RICE = (Reach × Impact × Confidence) / Effort
```

### 各因子口径

**Reach**——一个周期（通常一个季度）内受影响的用户数。

- 用**真实数据**：查埋点、查工单量、查用户表
- 不要用「所有用户」——所有用户都能看到不等于都会用
- 单位统一（都用「季度活跃用户数」，不要一个用日活一个用总注册）

**Impact**——对单个受影响用户的影响强度。固定档位，不要自创：

| 分值 | 含义 | 判据 |
|---|---|---|
| 3 | 巨大 | 用户当前完全做不到某件必须做的事 |
| 2 | 高 | 有 workaround 但成本很高 |
| 1 | 中 | 有 workaround，成本一般 |
| 0.5 | 低 | 体验改善，不影响完成任务 |
| 0.25 | 极小 | 锦上添花 |

**Confidence**——对 Reach 和 Impact 估计的信心。**这是诚实度检验**：

| 分值 | 依据 |
|---|---|
| 100% | 有直接数据（埋点/工单统计/A/B 结果） |
| 80% | 有间接证据（用户访谈 ≥5 人、竞品数据） |
| 50% | 有逻辑推理，无数据 |
| 20% | 拍的 |

上述比例只可作为团队约定的排序权重，不是统计置信度；未知应直接标未知，禁止据此声称验证。

**Effort**——人周。**必须问 `/architect` 拿粗估**，PM 自己估的工作量没有意义（不知道技术债在哪、不知道要改几个地方）。

### 打分表示例

| 需求 | Reach | Impact | Conf | Effort | RICE | 备注 |
|---|---|---|---|---|---|---|
| 工单导出 | 1200 | 2 | 80% | 2 | **960** | Reach 来自埋点：季度内用过工单列表的主管数 |
| 外部协作链接 | 1200 | 3 | 50% | 8 | **225** | Effort 含权限体系改造，来自 /architect |
| 列表字段自定义 | 300 | 0.5 | 50% | 3 | **25** | Reach 低：只有 3 个客户提过 |

结论：先做导出（RICE 最高且 Effort 小），外部协作链接价值高但超出本轮 appetite，拆到下轮；字段自定义不做。

### RICE 的三条使用纪律

1. **只用于排序，不用于决定做不做**。分低的可能是合规必做，分高的可能超 appetite
2. **分数接近时（差 < 20%）不假装精确**，按战略/依赖顺序决定
3. **Effort 差异大时优先小的**。两个需求 RICE 相同、Effort 分别是 1 周和 8 周 → 先做 1 周的（更快验证、风险更低）

## 需求变更的处理

需求进入下游后要改，先判断改动类型：

| 改动 | 处理 |
|---|---|
| 补充细节（原本没说清的边界） | 直接补进原 FR，通知下游 |
| 缩小范围（砍掉一部分） | 原 FR 标 `[scope reduced]` + 说明，通知 `/qa` 删对应用例 |
| 改变行为（原来这样现在那样） | **新开 FR + 原 FR 标 superseded**，不许原地改 |
| 完全废弃 | 原 FR 标 `[dropped: 理由]`，通知下游删票删用例 |

**原地改已冻结的 FR 是最容易出事的操作**：`/qa` 照旧版写了用例，`/backend` 照旧版实现了，谁都不知道变了。改动必须留痕且主动通知。

回流要看原因而不是次数。用户通过比较形成新偏好、外部事实变化、原先规则遗漏是不同原因；记录变化来源并只修订受影响内容。反复漏掉已知约束或双方持续误解同一规则时，复盘定义方法；不要把正常学习一律算作需求失控。
