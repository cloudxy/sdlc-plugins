# 度量蓝图

## 为什么必须在定义阶段做

埋点缺口在交付后才发现 = **本轮效果永远无法评估**。功能上线了，但不知道有没有人用、有没有解决问题，下一轮决策只能靠感觉。

这是 SDLC 里最常见也最昂贵的浪费：代价已经付了（开发完了），收益无法测量。

所以度量蓝图不是「上线后再说」，它是定义阶段的交付物，**缺的埋点写进 FR 与功能同期上线**。

## 三层指标与配对反向护栏（不设数量配额）

| 层 | 定义 | 选择原则（严禁凑数） | 作用 |
|---|---|---|---|
| **北极星** | 这个功能成功的唯一标志 | **唯一（1 个）** | 争议时的最终判据 |
| **驱动指标** | 能被本功能机制直接改变的前置行为 | 按核心价值路径机制选取，不设固定个数 | 诊断：北极星没动时定位断在哪一环 |
| **配对反向护栏** | 追逐北极星/驱动时最可能被牺牲或刷坏的对立面 | **每个目标/驱动指标至少配对对应反噬风险护栏**，附硬红线 | 防局部套利与次生灾害（如拉转化伤留存/涨退款、提 AI 速度推高幻觉或 Token 成本） |

### 北极星只能有一个

两个北极星等于没有北极星——它们冲突时你无法决策。

```
❌ 北极星：导出使用率提升 + 工单处理时长下降
   （使用率高但处理时长没变，算成功还是失败？）

✅ 北极星：工单平均处理时长下降 15%
   驱动指标：导出功能周使用率、单次导出耗时、外部往返次数
```

北极星要选**离用户价值最近的那个**，不是最容易涨的那个。「使用率」是驱动指标不是北极星——用户用了但没变快，功能就是失败的。

### 护栏指标最常被忽略

护栏是防止局部优化损害整体的唯一手段：

| 做的功能 | 护栏指标 |
|---|---|
| 导出功能 | 列表页加载时长（导出查询不能拖慢列表）、系统错误率 |
| 推荐算法 | 内容多样性、长尾内容曝光占比 |
| 简化注册流程 | 注册后 7 日留存（别为了转化引入低质用户） |
| 增加提醒推送 | 推送退订率、App 卸载率 |
| 缓存优化 | 数据陈旧导致的用户投诉量 |

**护栏指标要在开工前定，并给出红线值**：「列表页 P95 不得超过 1000ms，超了就回滚」。事后才想起来看，往往已经损害了几周。

## 指标唯一口径（SVOT）与四要素

全产品指标计算公式的唯一事实源（SVOT）是 `<product_root>/data/metrics.yaml`（由 `data-warehouse-engineer` 维护）。**禁止在 `spec.md` 中复制粘贴分子分母公式**，否则产品层升级口径后功能规格立刻沦为过期双份真相（DIE 公式漂移）：

- **复用已有指标：** `spec.md` 第 8 节直接引用 `metric:<id>@v<n>`，只填本功能的**基线、目标值、判定窗口与配对护栏红线**。
- **提议新增指标：** 当 `data/metrics.yaml` 尚无该指标时，在 `spec.md` / `01-define/tracking.md` 写出下方四要素并标注 `[提议→data-warehouse-engineer]`，交 `data-warehouse-engineer` 落入 `data/metrics.yaml` 后统一按 `metric:<id>@v1` 引用。

新增指标提议或产品层建档时，每个指标必须写清四件事，缺一个就会在复盘时吵架：

```
① 口径（归入 data/metrics.yaml）：怎么算的（分子分母、去重规则、计算窗口）
② 来源：数据从哪来（表.字段 / event:<name>）
③ 时间窗：按什么周期看（日/周/月），用记录时间还是业务时间
④ 目标值与配对红线（归入 spec.md）：多少算成功（含判定周期）、越哪条红线回滚
```

示例（新增指标提议草案）：

```
提议指标：metric:export_weekly_adoption@v1 [提议→data-warehouse-engineer]
① 口径：分子 = 一周内触发过 event:export_clicked 的主管去重数
        分母 = 一周内访问过工单列表（event:ticket_list_viewed）的主管去重数
② 来源：event:export_clicked（新增）；event:ticket_list_viewed（已有）
③ 时间窗：自然周（周一至周日），按事件发生时间
④ 本功能目标与配对护栏：上线四周内达到 30%；配对护栏 metric:ticket_list_p95_ms@v1 ≤ 1000ms、metric:export_failure_rate@v1 < 1%
```

**「时间窗用记录时间还是业务时间」是报表口径最常见的分歧点**。退款率用退款登记时刻还是实际退款时刻？跨月时两个口径的数字完全不同。这里定下来，`dba` 的时间字段设计和 `analyst` 的复盘口径才能对齐。

## 埋点缺口盘点

**这是度量蓝图的核心产出。** 逐个指标查数据来源，缺的立刻写进 FR。

| 指标 | 需要的数据 | 现有来源 | 状态 | 处理 |
|---|---|---|---|---|
| 工单处理时长 | `resolved_at - created_at` | `tickets` 表已有 | ✅ | — |
| 导出使用率 | 事件 `export_clicked` | 无 | ❌ **缺** | 写进 FR-05 |
| 单次导出耗时 | 事件 `export_completed` 带 duration | 无 | ❌ **缺** | 写进 FR-05 |
| 列表页加载时长 | 前端性能埋点 | 已有 RUM | ✅ | — |
| 外部往返次数 | 无法埋（发生在系统外） | — | ⚠️ **不可测** | 用访谈抽样代替，四周后回访 5 位主管 |

三种状态各自的处理：

- **✅ 有** —— 记下来源路径，交给 `analyst` 复盘时直接用
- **❌ 缺** —— **写成 FR**（例：`FR-05 埋点：导出行为与耗时上报`），与功能同期上线。不要写成「技术任务」，写成 FR 才会进验收
- **⚠️ 不可测** —— 显式声明不可测 + 给替代方案（访谈/抽样/问卷）。不许假装能测

**把埋点写成 FR 的意义**：FR 会被 `qa` 验收，技术任务不会。写成技术任务的埋点，上线后经常发现事件没上报或字段缺失。

埋点 FR 的 GWT 写法：

```
FR-05 导出行为埋点

GWT-05.1  Given 主管点击导出并成功下载
          When  导出完成
          Then  上报事件 export_completed，含字段：user_id、role、
                row_count、duration_ms、file_format
                在埋点后台可查到该事件

GWT-05.2  Given 导出失败
          When  失败发生
          Then  上报 export_failed，含 error_type
```

## 常见度量陷阱

| 陷阱 | 问题 | 修正 |
|---|---|---|
| 只看总量不看人均 | 总量涨可能只是用户涨了 | 用率或人均值 |
| 用平均值看分布 | 平均掩盖长尾（平均 200ms，P99 8 秒） | 用 P50/P95/P99 |
| 没有对照组就说「因为上线」 | 相关当因果 | 无对照只能说「变化」；要因果找 `analyst` 设计实验 |
| 指标能被轻易刷 | 「导出次数」可以反复点 | 用去重用户数，或加「有效导出」定义 |
| 选容易涨的当北极星 | 涨了但用户价值没变 | 选离用户价值最近的 |
| 目标值拍脑袋 | 无法判断成败 | 用基线 + 合理增幅；没基线先测两周基线 |
| 没定判定周期 | 上线三天说没效果 | 明确「四周后判定」，中途不下结论 |
| 忘了护栏 | 局部优化损害整体 | 为受影响风险设置适用护栏，不按数量凑指标 |
| 埋点字段不够 | 有事件但无法分组分析 | 事件必带：who（角色）、what（关键参数）、how long（耗时） |

**「没基线先测基线」值得强调**：目标值「处理时长下降 15%」的前提是知道现在是多少。不知道基线的目标值是空话。基线缺失时，第一轮的目标就是「建立基线」，这本身是合法的交付物。

## 交给下游

| 给谁 | 内容 |
|---|---|
| `architect` | 埋点 FR 需要的技术支持（事件上报通道是否存在） |
| `backend` · `frontend` · `data-collector` | 埋点 FR 与 `01-define/tracking.md` 的事件名与字段契约 |
| `data-warehouse-engineer` | `[提议→data-warehouse-engineer]` 新增指标草案，收编进 `data/metrics.yaml` 生成正式 `metric:<id>@v<n>` |
| `qa` | 埋点 FR 的 GWT（验收时要确认埋点后台真的能查到） |
| `analyst` | 度量蓝图引用的 `metric:<id>@v<n>`、目标与实验/读数窗口 |
| `dba` | 时间字段的业务语义（记录时间 vs 业务生效时间） |

## 自检

- [ ] 北极星只有 1 个，且离用户价值最近
- [ ] 驱动指标按价值路径机制选取（不按固定个数凑指标），能解释北极星的变化
- [ ] 每个目标/驱动指标均配对了反向护栏指标（防刷量/退款/流失/成本反噬）且给出硬红线
- [ ] 已定义指标引用 `metric:<id>@v<n>`（未在 `spec.md` 复制粘贴公式）；新增指标标明 `[提议→data-warehouse-engineer]` 且四要素齐全
- [ ] 时间窗明确了用记录时间还是业务时间
- [ ] 埋点缺口逐个盘点，状态标注（有/缺/不可测）
- [ ] 缺的埋点写成了 FR（不是技术任务）
- [ ] 埋点 FR 有 GWT，验收时能确认后台可查
- [ ] 不可测的指标给了替代方案
- [ ] 目标值有基线支撑；无基线时本轮目标是建立基线
- [ ] 明确了判定周期
