# 卖点与亮点：把功能变成「可演示的时刻」

**卖点不是功能清单换个名字。** 一个卖点必须同时满足：用户在产品里能在某一步**亲眼看到**、说得出**比替代品好在哪**、有**证明**、能**回答一个具体顾虑**。做不到的叫愿景，不叫卖点。

## 卖点句式

```
在 <关键旅程 J-n 的某一步>，<目标人群> <看到 / 得到> <具体结果（数字或对比）>，
因此不再需要 <替代品里的旧痛点>。
```

例：在「导入数据 → 看到报表」（J-1 第 2 步），运营负责人上传一份 Excel 后 **30 秒**看到可直接转发的周报，不再需要每周一花 **2 小时**手工做透视表。

## 从功能到时刻（FAB → Moment）

| 层 | 问题 | 例 |
|---|---|---|
| Feature 功能 | 我们做了什么 | 自动识别表头与指标 |
| Advantage 优势 | 比替代品好在哪 | 不用手工拖透视表 |
| Benefit 价值 | 用户得到什么 | 周报从 2 小时变 30 秒 |
| **Moment 时刻** | 在哪一步亲眼看到 | 上传完成后，报表逐项渐显，第一张图表带「已识别 12 个指标」 |

写到 Moment 这一层，设计师才能把它做成**签名时刻**，测试才能验收，销售才能演示。

## 证明类型（强 → 弱）

| 证明 | 说明 | 注意 |
|---|---|---|
| 现场演示 | 用户自己 30 秒内体验到 | 最强；要求时刻在关键路径上且稳定 |
| 实测数字 | 在真实量级数据上测得 | 写清测试条件，不许用最好一次的数字 |
| 对比 | 与替代品同任务同条件对比 | 引用来源与日期 |
| 客户案例 / 评价 | 真实用户原话 | 需授权；不许编 |
| 承诺 / 保障 | 退款、SLA | 须与运维、法务确认 |

## 亮点排序（最多 3 个）

对每个候选打分（1–5），按乘积排序：

| 候选 | 对目标人群的重要度 | 相对替代品的独特度 | 可证明度（在本次构建上） | 乘积 |
|---|---|---|---|---|

**可证明度低的候选不进前三**，它进 `growth.md` 的「待证明」列表，并作为需求交给 pm。

## 与其他角色的连接

| 连接 | 要求 |
|---|---|
| pm 的核心价值路径 / Aha 时刻 | 第一卖点通常就是 Aha 时刻；不一致时找 pm 对齐，二者之一有错 |
| designer 的签名时刻 | 卖点对应的时刻交给设计做成「被记住的那一刻」，写进 `design-system.md` |
| qa / 验收 | 卖点里的数字与时刻进入 `accept-growth.md` 的核验清单 |
| ops 发布说明 | 发布说明只能使用核验通过的说法 |

## 顾虑处理

| 常见顾虑 | 用哪个卖点回答 | 证明 |
|---|---|---|
| 「迁移成本高」 | 导入 30 秒出结果 | 现场演示 |
| 「数据安全吗」 | 权限与审计（地基信息） | 合规认证 / 审计日志截图 |
| 「和我现在用的 X 差不多」 | 独特属性对应的时刻 | 同任务对比 |

## 反模式

| 反模式 | 修正 |
|---|---|
| 「功能强大」「体验流畅」 | 说出时刻与数字 |
| 十个卖点并列 | 最多 3 个，其余降为支撑信息 |
| 卖点在关键路径之外（藏在设置第三层） | 要么把时刻搬到路径上（交 pm/designer），要么不当卖点 |
| 用未交付能力做卖点 | 标「待证明」，不进任何对外文案 |
