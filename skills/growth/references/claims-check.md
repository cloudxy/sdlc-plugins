# 卖点核验：对外说的每一句，都要在构建上找到证据

阶段 `accept`（verify 之后）。目的：**上线前拦住「说的和做的不一样」**。这是增长运营的验收，不是写文案。

## 1. 清点所有说法（claims inventory）

来源逐个过，漏一个就可能变成客诉：

| 来源 | 位置 |
|---|---|
| 发现带假设 | `00-discover/growth.md`、briefing `## Growth` |
| 产品层 | `<product_root>/growth.md` 的卖点与信息屋 |
| 规格里用户会看到的承诺 | `01-define/spec.md`（性能数字、上限、格式、权限） |
| 对外草稿 | 发布说明草稿、官网 / 商店文案、活动页、销售话术（如有） |
| 界面文案 | 空态、引导、付费墙里的价值表述 |

## 2. 逐条核验

| 说法 | 对应旅程步骤 | 核验方法 | 证据 | 结果 |
|---|---|---|---|---|
| 「30 秒出第一份报表」 | J-1 第 2 步 | 用 5000 行真实量级样例跑 3 次，取中位数 | `04-verify/shots/j1-report-1440.png`，计时 22s/27s/31s | ⚠️ 改写为「半分钟左右」 |
| 「支持导出 Excel」 | J-3 第 1 步 | 在构建上导出 | 只生成 `.csv` | ❌ 删除或改为「导出 CSV（Excel 可打开）」 |

核验方法优先级：在运行中的构建上亲自走（`bash PLUGIN_ROOT/scripts/ui-evidence.sh` 截图后读图确认）> 引用 E2E 通过记录 > 引用测试数据。**只读规格不算核验。**

数字类说法：在接近真实的数据量级上测，写清条件，取中位数而不是最好的一次。

## 3. 结果分级

| 结果 | 含义 | 处理 |
|---|---|---|
| ✅ 已证实 | 构建上看得到，条件写清 | 可以对外使用 |
| ⚠️ 改写 | 能力在，但说法夸大或条件不清 | 给出改写后的准确说法 |
| ❌ 删除 | 能力不存在或不稳定 | 从所有对外物料删除 |
| 🚫 产品缺口 | 这条是**核心卖点**，但构建没做到 | 交 pm + 实现帽返工；不能靠改文案解决 |

## 4. 演示脚本（≤5 步）

写一段任何人照着做都能复现亮点的脚本，并在构建上真跑一遍：

```
前置：新注册账号，准备 sample-5000.xlsx
1. 登录后点击「导入数据」
2. 选择 sample-5000.xlsx
3. 等待 → 看到报表逐项出现（亮点时刻）
4. 点击「分享」→ 复制链接
5. 无痕窗口打开链接 → 看到同一份报表
```

脚本跑不通 = 亮点不成立。

## 5. 结论规则

| 结论 | 条件 |
|---|---|
| `结论：通过` | 所有核心卖点 ✅，其余说法 ✅ 或已给出改写 |
| `结论：有条件通过` | 核心卖点 ✅，部分次要说法需改写/删除（条件 = 物料修改清单 + 负责人） |
| `结论：不通过` | 任一核心卖点为 🚫 或演示脚本跑不通 |

结论行必须原样写成 `结论：通过` / `结论：有条件通过` / `结论：不通过`（闸门据此判定）。
