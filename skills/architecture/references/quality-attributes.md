# 质量属性驱动的架构设计

好架构不是「用了什么技术」，而是**在可量化的质量目标之间做了有意识的取舍**。这份参考给出：怎么写质量属性场景、怎么估容量、怎么比较候选方案、互联网产品典型的演进阶段、怎么把架构规则变成自动检查。

## 1. 质量属性场景（QAS）怎么写

```
来源 → 刺激 → 环境 → 被测对象 → 响应 → 度量
```

| 属性 | 场景示例（互联网产品） | 度量 |
|---|---|---|
| 性能 | 用户在高峰期打开首页信息流 | 首屏接口 P95 < 300ms，LCP < 2.5s |
| 可伸缩 | 营销活动带来 10 倍 DAU（growth 的 launch 计划） | 峰值 QPS 下错误率 < 0.1%，扩容 < 10 分钟 |
| 可用性 | 单实例 / 单可用区故障 | 月可用性 99.9%；RTO < 5min；RPO < 1min |
| 一致性 | 用户支付成功后立即查看订单 | 读到已支付状态的比例 100%（读己之写） |
| 安全 | 越权访问他人数据、刷接口 | 0 越权；限流生效；审计覆盖 100% |
| 可演进 | 新增一种内容类型 / 支付渠道 / 数据源 | 稳定契约不破坏；受影响规则有明确所有者 |
| 可观测 | 核心旅程失败 | 5 分钟内告警，能定位到服务与版本 |
| 成本 | 每千 DAU 月基础设施成本 | < <金额>，随 DAU 次线性增长 |
| 隐私合规 | 用户注销 | 30 天内删除 / 匿名化个人数据 |

**只写与本功能相关的属性**；每条场景都要能被测（压测、故障演练、检查脚本）。

## 2. 容量估算（带数字的推导）

先选择工作负载模型：API 看到达率/并发/服务时间/热点；SDK 看宿主限制和兼容矩阵；批处理看数据量与完成窗口；流处理看事件速率、峰值与积压恢复；原生/离线端看内存、电量、存储与同步冲突；模型服务看 token、延迟、并发和成本。DAU 公式只用于能从用户活动推导请求的产品。每个输入注明实测、估算或目标，给区间和敏感因素，不固定 12 个月。


示例：内容社区「发布动态 + 浏览信息流」

| 输入 | 值 | 来源 |
|---|---|---|
| DAU | 50 万（12 个月目标） | strategy.md / growth.md |
| 人均浏览请求 / 天 | 60 | 分析数据或同类产品经验（标 [推断]） |
| 人均发布 / 天 | 0.3 | |
| 峰值系数 | 4（晚高峰） | 历史流量曲线 |
| 单条动态存储 | 2KB 正文 + 平均 1 张图 300KB | |

推导：

```
读 QPS 平均 = 500,000 × 60 / 86,400 ≈ 347；峰值 ≈ 347 × 4 ≈ 1,390
写 QPS 平均 = 500,000 × 0.3 / 86,400 ≈ 1.7；峰值 ≈ 7
文本年增量 = 150,000 条/天 × 2KB × 365 ≈ 110GB（含索引与副本 ×3 ≈ 330GB）
图片年增量 = 150,000 × 300KB × 365 ≈ 16TB → 对象存储 + CDN，不进数据库
```

这是工作负载估算，不是实测容量。读写比例约 200:1；是否需要缓存/副本以及单库承载能力，还需查询复杂度、热点分布、环境与实测证据。所有示例数值均为教学假设。

## 3. 候选方案对比

需要新取舍时比较可信候选；复用已接受决策时验证其适用条件。选择规则只维护在 [adr-and-tradeoffs.md](adr-and-tradeoffs.md)。以下是教学用的两方案对比，表内实测值不是本项目证据：

| 维度 | 方案 A：单体 + 缓存 + 只读副本 | 方案 B：读写分离服务 + 消息队列 |
|---|---|---|
| QAS-性能（峰值 1,390 读 QPS） | 满足（缓存命中 90% 时 DB 读 ~140 QPS，已测单实例 2,000） | 满足 |
| QAS-可演进（新增内容类型） | 模块内扩展 | 需同时改两个服务 |
| 实现代价 | 5 人天 | 20 人天 |
| 运维代价 | +Redis（已有） | +MQ +新服务部署与监控 |
| 故障模式 | 缓存击穿 → 限流与互斥重建 | 消息积压 / 重复 → 幂等消费 |
| 到下一阶段的代价 | 读压力继续增长时加副本；写 > 500 QPS 时再拆 | 已具备 |
| 风险 | 缓存一致性窗口（≤ 5s，产品已接受） | 过度设计，团队运维负担 |

**选定 A**，否决 B：当前与 12 个月目标下 A 满足全部场景，B 的额外代价换不来本阶段需要的属性。**复审触发**：写峰值 > 300 QPS 或信息流需要个性化排序（需要异步特征计算）。

证据优先级：已有监控数据 > spike 实测 > 同栈公开基准 > 经验估算（标 [推断]）。

## 4. 互联网产品典型演进阶段

下表是互联网产品可能的演进示例，不是每个项目的成长路线。未来变化作为候选增量记录，当前事实的更新遵循 [lifecycle.md](lifecycle.md)。

| 阶段 | 典型形态 | 触发下一阶段的信号 |
|---|---|---|
| 0 验证期 | 模块化单体 + 单库 + 托管服务 | 付费用户增长、核心接口 P95 接近预算 |
| 1 增长期 | + 缓存、只读副本、对象存储 + CDN、异步任务队列 | 单库写入或连接数瓶颈、报表查询拖慢在线库 |
| 2 规模期 | 分析查询迁至列式库 / 数仓；热点数据分片或拆库；搜索引擎 | 团队 > 3 个小组互相阻塞发布；某能力伸缩需求差一个量级 |
| 3 平台期 | 按限界上下文拆服务、事件驱动、多地域 | 合规或延迟要求多地域部署 |

**拆服务的五个正当理由**：独立伸缩、独立发布节奏、技术栈必须不同、团队边界已造成协作成本、故障隔离要求。「代码太多」「看起来更现代」不是理由。

## 5. 适应度函数（把架构规则变成 CI 里会红的检查）

| 规则 | 检查方式（例） |
|---|---|
| 模块边界：`report` 模块不得 import `billing` 内部包 | import-linter / dependency-cruiser / ArchUnit |
| 分层：Router 不引用 ORM | `impl-evidence` 的 check-layering 脚本 |
| 核心旅程性能预算 | CI 性能冒烟：关键接口 P95 超预算即失败 |
| 前端体积预算 | bundle size 检查 |
| 迁移可逆 | `up → down → up` 在 CI 跑 |
| 禁用依赖 / 许可证 | 依赖白名单检查 |
| 对外契约不破坏 | 契约测试 / OpenAPI diff |

每条注明实现者、执行/验证者、环境、目标、到期阶段与证据路径。实现者将适用的检查接入配置或 CI；架构师复核真实记录。未实现/未执行明确标记 planned/unverified，不把建议当成已通过。高成本压测/故障演练可放专用环境，不强塞每次 CI。

## 6. 常见坑

| 坑 | 纠正 |
|---|---|
| 「支持高并发」 | 写出 QPS、P95、错误率与环境 |
| 不核对既有决策就重新选型 | 验证复用条件；真实新取舍才比较 |
| 容量估算没有来源 | 每个输入标来源或 [推断]，列为复审条件 |
| 过度设计（为 100 倍流量准备） | 按业务规划期、负载区间与退出成本设计，保留复审触发条件 |
| 设计不足（完全不考虑增长） | 按产品类型读取投放、批任务、租户或设备增长等相关刺激 |
| 规则只写在文档 | 按风险挑选关键规则，安排实现/执行责任与证据，不设数量配额 |
