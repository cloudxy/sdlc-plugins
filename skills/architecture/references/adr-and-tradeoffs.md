# ADR 与技术选型取舍

## ADR 的判定标准

**这个决定三个月后想改，成本是「改几行」还是「改一片」？**

| 决策 | 可逆性 | ADR |
|---|---|---|
| 用哪个日志库 | 改几行（有抽象层的话） | 不必 |
| 日志格式与字段规范 | 改一片（所有调用点 + 采集配置） | 需要 |
| 某个函数的实现方式 | 改几行 | 不必 |
| 同步还是异步 | 改一片（调用方全改、语义变了） | **必须** |
| 数据存储选型 | 改一片 + 迁移数据 | **必须** |
| 对外 API 契约形态 | 改一片 + 所有客户端 | **必须** |
| 认证授权机制 | 改一片 + 安全审计 | **必须** |
| 多租户隔离模式 | 几乎不可改 | **必须** |
| 单体还是拆服务 | 几乎不可改 | **必须** |

## ADR 的核心价值：否决理由

**只写「我们决定用 X」的 ADR 等于没写。** ADR 的价值全在被否决的备选上——三个月后有人问「为什么不用 Y」，答案必须在文档里，而不在某人的记忆里（那个人可能已经离职）。

```
❌ 无用的 ADR
   决策：使用 Redis 做缓存
   理由：性能好，团队熟悉

✅ 有用的 ADR
   决策：使用 Redis 做缓存
   备选与否决：
     进程内缓存（Caffeine）—— 否决：多实例部署下缓存不一致，
       本场景要求 30 秒内全实例一致
     Memcached —— 否决：需要 Sorted Set 做排行榜（FR-08），Memcached 无此结构
     数据库查询 + 索引优化 —— 否决：已做过 spike，
       P95 仍为 340ms，NFR-01 要求 < 100ms（见 spike 记录）
   代价：新增运维依赖；需处理缓存穿透/雪崩（见 02-shape/contract.md 缓存策略段）
```

否决理由要**带证据或具体约束**，不能是「不够好」。

## 六类高频选型的取舍框架

### 1. 同步 vs 异步

| 维度 | 同步 | 异步 |
|---|---|---|
| 调用方体验 | 立即得到结果 | 需要轮询或推送 |
| 失败处理 | 直接返回错误 | 需要重试机制 + 死信处理 |
| 一致性 | 强 | 最终 |
| 复杂度 | 低 | 高（队列、幂等、监控、补偿） |
| 适用 | 耗时可控（< 1–2 秒）、调用方需要结果才能继续 | 耗时长/不确定、调用方不需要立即知道结果 |

**判据不是「耗时多久」，是「调用方需不需要结果才能继续」。**

选异步必须同时定四件事，缺一个上线就是坑：**重试策略**（次数与退避）、**幂等保证**（消费方必须幂等）、**死信处理**（重试耗尽后去哪、谁看）、**进度可见性**（用户怎么知道好了）。

### 2. 存储选型

先拆**事实**再选存储。一句「调度状态用 Redis 还是 MySQL」是**假二分**：入队 / 抢占 / 租约（**协调**）和任务定义 / 终态 / 审计（**记录**）不是同一个事实。iteration-4 architecture-2：跟着「默认关系库」的帽子把协调也塞进 MySQL；基线把协调给 Redis、记录给 MySQL。现网 `schedule_service.py` + `platform_core/queues.py` 是后者（MySQL 管 `next_run_at` / 任务行；Redis 管锁、TASK_QUEUE、scrapy-redis 队列）。

先问**这个事实的访问模式**，不要先选品牌再适配（和 `/dba` 的索引原则同源）。

| 事实类 | 访问模式 | 倾向 |
|---|---|---|
| 记录（权威、可查询、要过重启、要审计） | 事务、关系、报表 | 关系库 |
| 协调（热路径、TTL/抢占、可从记录重放） | 高频小操作、过期、阻塞弹出 | 已有队列 / Redis |
| 键值读写为主、要求低延迟（非权威） | KV | Redis / KV |
| 全文检索、复杂过滤聚合 | 倒排 | 搜索引擎 |
| 时序追加、按时间窗聚合 | 追加 | 时序库 |
| 文档结构差异大且不需 JOIN | 文档 | 文档库 |
| 图遍历（多跳关系） | 多跳 | 图库 |

**默认用关系库管记录。** 引入**新的**第二种存储门槛很高：多一套运维、监控、备份、故障模式。

真正的高门槛是「**同一事实两个写者**」（双写），不是「拓扑里已经付过钱的 Redis 再给匹配的访问模式用」。已有 Redis 给队列 / 锁用，不算「引入第二种存储」。

存储 ADR 必问四句（缺一句就还是笔记）：

1. 这句话里有几个事实？拆开了没有？
2. 拓扑里是否已经有这个存储？（读代码 / 部署清单。无代码则标 `[ASSUMED]`，把「Redis 是否已在拓扑」写成复审条件。）
3. 关系库加索引 / 物化视图能解决**这个事实**吗？
4. 若用两个存储：谁是该事实的唯一写者？崩溃时如何从记录重放协调？

无 NFR、无 spike 时禁止把桌面估算写成已测吞吐。Crawler 现网拆法（已落地，不是想象）：Scrapy 禁止直写 MySQL（B2）；worker 抢占循环不是「还没有第二种存储」的证据。

### 3. 单体 vs 拆服务

见 [boundary-derivation.md](boundary-derivation.md) 末节。核心：**默认不拆**，只在独立伸缩/独立发布/技术栈不同/团队边界/故障隔离这五个信号出现时拆。

### 4. 自研 vs 引入依赖

| 倾向自研 | 倾向引入 |
|---|---|
| 是核心业务逻辑 | 是通用基础设施 |
| 需求特殊，现成方案要大改 | 需求标准 |
| 代码量小（几百行内） | 自己写要几千行 |
| 依赖会带来大量传递依赖 | 依赖轻、维护活跃 |

引入依赖前必查四项：**最近提交时间**（半年没动的库要谨慎）、**未解决 issue 里有没有致命问题**、**许可证是否兼容**、**传递依赖数量**。

**版本要锁定**（精确版本或锁文件），不用开放范围——一次自动升级引入的破坏性变更足以毁掉一个下午。

### 5. 缓存策略

引入缓存前先问：**数据库真的是瓶颈吗？** 用 EXPLAIN 和实测数字证明（找 `/dba`），不要凭感觉加缓存。

缓存的代价是**一致性问题永久存在**：从此每个数据变更都要考虑「缓存要不要删」。

决定加缓存后，四件事必须定（详见 `/dba` 的 `redis-key-governance.md`）：键命名、TTL、失效路径、缓存不可用时的降级行为。

### 6. 数据一致性模型

| 模型 | 保证 | 代价 | 适用 |
|---|---|---|---|
| 单库事务 | 强一致 | 无法跨服务 | 同库操作，首选 |
| Saga（补偿事务） | 最终一致 | 每步要写补偿逻辑 | 跨服务且能补偿 |
| 事件 + 幂等消费 | 最终一致 | 需处理重复与乱序 | 通知类、可容忍延迟 |
| 本地消息表 | 最终一致，不丢 | 需扫表投递 | 要求消息不丢且不引入额外中间件 |
| 分布式事务（2PC/XA） | 强一致 | 性能差、故障阻塞 | 极少数场景，通常有更好选择 |

**能在一个库的一个事务里做完，就不要引入分布式一致性。** 这是最省事的选择，也是拆服务前应该反复确认的一点——为了「架构好看」把本可一个事务完成的操作拆成 Saga，是纯亏。

选最终一致必须在 ADR 里写明：**可接受的延迟窗口**、**期间用户看到什么**（会不会看到中间状态）、**不一致被发现时如何修复**（有无对账机制）。

## 记录 spike 结论

spike 的结论进 ADR 的「证据」段，格式：

```
spike：单机 CSV 生成性能
问题：单机能否在 10 秒内生成 10 万行 CSV
环境：M1 Pro / 16GB / Python 3.12 / 本地 MySQL 8
结果：10 万行 6.2 秒，内存峰值 340MB
      50 万行 34 秒，内存峰值 1.6GB（超出容器 1GB 限制 → OOM）
结论：10 万行以内可同步；超过转异步 + 流式写入
      → 决定 FR-06 的阈值定为 10000 行（留足余量）
```

**带数字的结论才能支撑决策。** 「性能可以」无法回答「阈值定多少」。

## ADR 的生命周期

| 状态 | 含义 |
|---|---|
| `proposed` | 提出，待评审 |
| `accepted` | 已采纳，生效中 |
| `superseded by ADR-nn` | 被新决策取代，**保留原文** |
| `deprecated` | 不再适用但无替代 |

**永不删除 ADR，永不原地改已 accepted 的决策。** 改判就新写一份并把旧的标 superseded——决策的演进史本身就是重要信息，它记录了团队认知的变化。
