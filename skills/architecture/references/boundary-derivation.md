# 从业务能力到模块边界

目标是让相关规则在同一责任边界内变化，让协作通过明确契约发生。Controller / Service / Repository 是一种内部组织方式，不等同于业务边界；一个 FR 可以由多个模块协作实现。模块数量、改动文件数和一句话是否包含「和」都不是边界质量判据。

## 推导步骤

1. 从 FR、业务流程、既有代码和领域词汇识别能力；不要逐 FR 建模块。
2. 按数据含义、生命周期、不变量和变更原因聚类。指出每个权威事实由谁维护、谁可以发起命令、谁只读或持有派生副本。
3. 为每条 FR 指定结果负责人和协作者；为每个事实/不变量指定唯一权威。唯一性针对责任，不要求 FR 只落一个模块。
4. 画出并分别标注编译/包依赖、运行时调用、数据流和事件关系；不能用一种箭头证明所有关系无环。
5. 检查事务边界、失败恢复、授权、重复/乱序、演进兼容和协作成本。结合实际约束决定是否移动或合并职责。

## 工单导出示例（候选边界，不是通用固定拆法）

| 能力/事实 | 权威职责 | 协作 |
|---|---|---|
| 工单可见范围 | 工单域决定业务数据过滤规则 | 身份域提供用户/组织事实；查询与导出都执行过滤 |
| 导出请求与状态 | 导出应用流程维护状态转换与结果 | 工单查询、通用文件转换、存储、通知适配器 |
| 文件格式转换 | 转换组件处理流式编码与格式 | 接收数据流和列定义；不自行决定谁能看敏感字段 |
| 脱敏策略 | 相关数据/业务规则的负责人决定 | 转换组件执行传入的策略；安全控制在所有出口保持一致 |
| 审计事实 | 审计模块记录事件 | 业务方提供可验证的 actor、对象与结果 |

「导出并通知」跨多个模块并不说明边界错误。反复同步修改同一业务规则、多个模块任意写同一状态、调用方必须了解被调方内部表，才是需要调查的耦合证据。共享数据库不等于共享写入所有权；多个进程也可能只是同一个权威模块的实例。

## 依赖与循环

依赖倒置示例：工单应用包定义 `NotificationPort`，只调用该接口；通知适配器包实现它并依赖应用接口；组合根装配实现。

```text
编译依赖：通知适配器 → 应用接口 ← 工单业务代码
          组合根 → 工单业务代码、通知适配器
运行时：  工单业务代码 → 注入的通知适配器
```

工单包不能同时 import 通知适配器包再声称编译依赖无环。共享流程可提取编排者；共享稳定抽象可提取独立契约包。双向事件不产生直接包依赖，却仍可能造成反馈环、因果循环和运行时耦合，需定义去重、终止条件、版本和补偿。

## 强制与演进

对关键边界选择适当检查：包导入约束、权限/不变量测试、契约兼容性或集成检查。将检查的实现和执行责任交给具体人员/角色；按 [lifecycle.md](lifecycle.md) 跟踪计划与实测。手工审查可以作为低风险过渡措施，但要说明覆盖盲区；不能把「写了脚本」当成边界永不腐烂的保证。

新建项目通常先评估模块化单体；既有系统优先验证其边界，不为套用默认架构重写。拆服务需有独立伸缩、发布、技术约束、团队协作或故障隔离的证据，并同时评估网络失败、分布式一致性、部署和运维成本。不是所有产品都需要走向微服务。
