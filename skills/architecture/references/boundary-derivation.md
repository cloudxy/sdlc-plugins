# 从 FR 到模块边界

## 为什么不能按技术分层切

`Controller / Service / Repository` 是**代码组织方式**，不是模块边界。按它切的后果：

```
加一个「导出」功能 → 改 ExportController、ExportService、ExportRepository
                    → 三个"模块"全动，等于没有边界

改一次工单字段 → TicketController、TicketService、TicketRepository
              → 加上所有引用它的地方
```

真正的边界要满足：**一个业务变更只落在一个模块内**。所以边界必须按**能力**（业务上要做成的事）切，技术分层在每个模块内部各自存在。

## 完整推导示例

需求：客服系统增加「工单导出与外部协作」。

### 输入 FR

```
FR-01 主管可批量导出未结工单为 CSV
FR-02 导出内容含负责人姓名与所属组
FR-03 导出行为记入审计日志
FR-04 主管可导出全组，客服仅自己负责的
FR-05 上报导出行为埋点
FR-06 超过 10000 行转异步，完成后站内通知
FR-07 导出文件中手机号中间四位掩码
```

### ① 能力聚类

逐条 FR 转成「系统需要具备的能力」，然后合并：

| FR | 能力拆解 |
|---|---|
| FR-01 | 工单查询（带筛选）· 数据转 CSV · 文件产出 |
| FR-02 | 用户信息读取（姓名、组织） |
| FR-03 | 审计记录 |
| FR-04 | 权限判定（角色 → 数据范围） |
| FR-05 | 事件上报 |
| FR-06 | 异步任务调度 · 站内通知 |
| FR-07 | 敏感字段脱敏 |

合并同类，得到候选模块：

```
【工单域】     工单查询（带筛选、带数据范围过滤）
【导出能力】   数据转 CSV、文件产出、大数据量异步化、脱敏
【用户域】     用户信息读取、权限判定
【通知能力】   站内通知
【平台】       审计记录、事件上报、异步任务调度
```

### ② 边界判定三问逐个过

**【导出能力】**

| 问 | 答 | 判定 |
|---|---|---|
| 能一句话说清职责吗 | 「把结构化数据按规则转成用户可下载的文件」 | ✅ 无「和」 |
| 变更理由单一吗 | 只有「支持新格式」「改脱敏规则」会让它改 | ✅ 都是同一类理由 |
| 跨边界数据量大吗 | 一次传入数据集 + 列定义，一次返回文件 | ✅ 不细碎 |

通过。且注意它**不依赖工单**——它接受任何结构化数据。这个发现很重要：导出能力是通用的，不该塞进工单域。

**【用户域】的权限判定** —— 这里有个陷阱：

| 问 | 答 | 判定 |
|---|---|---|
| 能一句话说清吗 | 「判断某角色能访问哪些数据」 | ⚠️ 「哪些数据」是工单的概念 |

权限判定跨了两个域：**角色定义**属于用户域，**数据范围规则**（主管看全组、客服看自己）是工单域的业务规则。

正确切法：用户域提供「这个用户是什么角色、属于哪个组」，工单域自己根据角色决定过滤条件。**不要让用户域知道工单的过滤逻辑。**

这就是第三问「跨边界数据量」的价值：如果权限判定放在用户域，工单域每次查询都要反复问「这个人能看这条吗」，接口细碎 = 边界切错位置。

### ③ 依赖方向

```
        ┌─────────────┐
        │  工单域      │  （编排者：查数据 + 定过滤 + 调导出）
        └──┬───┬───┬──┘
           │   │   │
     ┌─────┘   │   └──────┐
     ▼         ▼          ▼
┌────────┐ ┌──────┐ ┌──────────┐
│ 用户域  │ │导出能力│ │  平台     │
│(角色/组)│ │(CSV/脱敏)│ │(审计/埋点/异步)│
└────────┘ └──────┘ └──────────┘
                          ▲
                     ┌────┴────┐
                     │ 通知能力 │
                     └─────────┘
```

有向无环。工单域是编排者（知道业务流程），其余是被调用的能力（不知道自己被用在什么业务里）。

**「编排者知道流程，能力不知道自己被谁用」是一条好边界的标志。**

### ④ 耦合检查

| 检查 | 结果 |
|---|---|
| 导出能力需要知道工单结构吗 | 否——接受通用数据集 + 列定义 ✅ |
| 工单域改字段，导出能力要改吗 | 否——列定义是参数 ✅ |
| 工单域与用户域共享表吗 | 否——通过接口读 ✅ |
| 通知能力知道是导出触发的吗 | 否——接受通用通知请求 ✅ |

若发现「导出能力里有 `if (type == 'ticket')`」→ 边界破了，工单知识泄进了通用能力。

### ⑤ FR 归属核对

每条 FR 必须能落到某个模块，且**归属唯一**：

| FR | 归属 |
|---|---|
| FR-01 | 工单域（编排）+ 导出能力（转换） |
| FR-02 | 工单域调用户域 |
| FR-03 | 平台（审计），由工单域触发 |
| FR-04 | 工单域（过滤规则）+ 用户域（角色数据） |
| FR-05 | 平台（埋点），由工单域触发 |
| FR-06 | 平台（异步）+ 通知能力 |
| FR-07 | 导出能力（脱敏是导出规则的一部分） |

FR-07 的归属值得讨论：脱敏放导出能力还是工单域？**判据是变更理由**——「改脱敏规则」是数据出口的关注点，与工单业务无关，所以放导出能力。若脱敏规则因工单类型而异，则该规则属于工单域，导出能力只提供「按规则脱敏」的机制。

## 边界画错的六个症状

| 症状 | 说明 | 修 |
|---|---|---|
| 一个功能变更要动 3+ 模块 | 边界横切了业务 | 按能力重切 |
| 两模块共享表且都写 | 数据层没有边界，代码层的边界是假的 | 定所有者，另一方走接口 |
| 模块 A 里有 `if (来源 == B)` | B 的知识泄进了 A | A 应接受参数，不判断来源 |
| 接口需要反复来回问 | 边界切在了错误的位置 | 一次传够，或合并 |
| 循环依赖 | 无法独立测试/部署 | 提取共用 / 倒置 / 事件 |
| 某模块什么都依赖它 | 上帝模块 | 拆分，或它其实是编排者（合理） |

## 循环依赖的三种解法

### 提取共用

```
问题：订单域 ⇄ 库存域（下单要扣库存，库存不足要取消订单）

解法：提取「交易编排」模块
  交易编排 ──> 订单域
       └────> 库存域
  订单域与库存域互不依赖
```

适用于：循环源于两者共享一段业务流程。

### 依赖倒置

```
问题：工单域 ──> 通知域，通知域需要回调工单域更新发送状态

解法：工单域定义 NotifyResultHandler 接口，通知域只依赖接口
  工单域 ──> 通知域（调用）
  工单域 <── 通知域（通过工单域定义的接口回调）
  依赖方向仍是单向：通知域依赖工单域的接口定义
```

适用于：需要保持调用方向，但要反转编译期依赖。

### 事件解耦

```
问题：订单域 ⇄ 积分域（付款加积分，积分变动要记订单备注）

解法：订单域发 OrderPaid 事件，积分域订阅
      积分域发 PointsGranted 事件，订单域订阅
  两者都只依赖事件契约，互不依赖
```

适用于：语义本来就是「通知」，不需要同步返回值。**代价是最终一致性**——要在 ADR 里写明可接受的延迟窗口，以及事件丢失/重复的处理（消费方必须幂等）。

## 单体内的模块边界怎么强制

模块边界光靠文档约定会烂掉。三种强制手段，按成本递增：

| 手段 | 做法 | 成本 |
|---|---|---|
| 目录约定 + 评审 | 按模块建目录，评审时人工看 | 低，但会漏 |
| 静态检查脚本 | 检查 import 违规（模块 A 不许 import 模块 B 的内部包） | 中，一次写好长期有效 |
| 编译期隔离 | 每模块独立包/模块（Java 模块、Go internal、前端 workspace） | 高，但真的挡住 |

**至少要做到静态检查**——它把「文档里的边界」变成「CI 里会红的规则」，这是边界不腐烂的唯一保障。检查脚本挂进 `sdlc.config.yaml` 的 `lint` 闸门。

## 微服务拆分的判据

**默认不拆。** 单体内的清晰模块边界能解决大部分问题，且成本低得多。只在有以下明确信号时才拆：

| 信号 | 说明 |
|---|---|
| 独立伸缩需求 | 某能力的负载与其余部分差一个量级以上 |
| 独立发布节奏 | 某能力需要每天发，其余每月发，且相互阻塞 |
| 技术栈必须不同 | 某能力必须用另一种语言/运行时 |
| 团队边界 | 不同团队维护，协作成本已实际发生 |
| 故障隔离要求 | 某能力挂掉不能影响核心链路，且进程内隔离做不到 |

**这些信号里没有「代码太多」「看起来更现代」。** 拆服务的代价是分布式事务、网络故障处理、部署复杂度、可观测性成本、本地开发体验劣化——没有上述信号就是净亏损。

拆之前先问：**在单体里把边界画清楚，能解决这个问题吗？** 通常能。
