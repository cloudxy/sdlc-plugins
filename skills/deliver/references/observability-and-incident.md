# 可观测性与故障响应

## 监控四类

**上线无监控 = 发布即盲飞。** 四类最低要求：

### ① 可用性

| 指标 | 说明 |
|---|---|
| 健康检查 | 服务是否活着（要检查真实依赖，不只返回 200） |
| 错误率 | 5xx / 总请求 |
| 成功率 | 按关键接口分别看（总体成功率会掩盖单个接口的问题） |

**健康检查要有意义**：只返回 `{"status":"ok"}` 的端点无法发现「服务活着但数据库连不上」。要检查关键依赖。

### ② 延迟

```
P50  —— 典型用户体验
P95  —— 大多数用户的最差体验（NFR 通常定这个）
P99  —— 长尾，容量与超时配置的依据
```

**不要只看平均值**：平均 200ms 可能是「90% 的请求 50ms + 10% 的请求 1.5 秒」。平均值掩盖长尾。

**按接口分别看**：总体 P95 正常，某个关键接口可能已经很慢。

### ③ 饱和度

| 资源 | 为什么重要 |
|---|---|
| CPU / 内存 | 基础 |
| **连接池** | 耗尽时表现为「请求排队」而非报错，最难查 |
| 线程池 / worker | 同上 |
| 队列深度 | 增长说明消费能力不足 |
| 磁盘 | 满了会造成写入失败与日志丢失 |
| 外部服务额度 | 限流额度用尽 = 功能不可用 |

**连接池耗尽是最隐蔽的饱和**：应用日志里可能只看到「超时」，实际是在等连接。要单独监控池使用率。

### ④ 业务指标（最容易忽略，最有价值）

```
技术指标全绿 + 订单量掉一半 = 有逻辑错误
→ 这类问题技术监控发现不了
```

| 业务指标 | 发现什么 |
|---|---|
| 核心动作完成量（下单/导出/注册） | 逻辑错误导致流程走不通 |
| 关键流程转化率 | 某一步骤失败率上升 |
| 数据一致性抽查 | 数据错误 |

**业务指标通常比技术指标更早发现真实问题。** 加它的成本不高，收益很大。

## 告警设计

### 三级分级（不分级等于没告警）

| 级别 | 判据 | 响应时限 | 通知 |
|---|---|---|---|
| **P0** | 核心功能不可用、数据损坏、安全事件 | 分钟级 | 电话/强提醒，直到确认 |
| **P1** | 重要功能受损、错误率显著上升、容量即将耗尽 | 30 分钟 | 即时消息 + 值班 |
| **P2** | 非关键异常、指标偏离但用户无感 | 工作时间 | 汇总/看板 |

**「全是 P0 等于没有 P0」**：告警泛滥训练团队忽略告警。P0 要严格限定在「必须立刻有人起床处理」的情况。

### 每条告警必须带处理指引

```
告警：导出失败率 > 5%（持续 5 分钟）
级别：P1

可能原因：
  ① 对象存储不可用
  ② 数据库慢查询（大范围导出请求）
  ③ AI 分类服务超时（应自动降级）

排查步骤：
  1. 看 dashboard「导出健康」，确认失败集中在哪一步
  2. 集中在存储上传 → 查存储服务状态页；检查凭证是否过期
  3. 集中在查询 → 看慢查询日志；查是否有超大范围请求
  4. 集中在 AI 分类 → 确认已降级到规则（未降级 = bug，记缺陷）

临时缓解：
  调低单次导出上限（配置项 EXPORT_ROW_LIMIT，热更新无需发版）

升级条件：
  15 分钟未缓解，或失败率 > 20% → 升 P0，通知 <责任人>

相关：runbook <链接> · dashboard <链接>
```

**没有处理指引的告警，收到的人只能干看着。** 指引要具体到「看哪个面板、查哪个日志、改哪个配置」。

### 告警的三个质量要求

| 要求 | 说明 |
|---|---|
| **可动作** | 收到后知道该做什么。做不了什么的告警应该降级为看板指标 |
| **有阈值与持续时间** | 「错误率 > 5%」不够，要「持续 5 分钟」（避免瞬时抖动误报） |
| **有抑制与聚合** | 同一问题不重复轰炸（会掩盖其它告警）；根因告警触发时抑制派生告警 |

**误报是告警系统的最大杀手**：一周三次误报之后，团队就不再看这条告警了。宁可阈值宽松一点，也不要频繁误报。

### 告警要定期审查

```
过去一个月：
  这条告警触发了几次？
  几次是真问题？（误报率）
  真问题里，是不是每次都做了同样的处理？（→ 可以自动化）
  从来没触发过？（→ 阈值是否失效，或该删）
```

**从未触发过的告警要审查**：可能是阈值设错了（永远达不到），也可能是这个场景本来就不会发生（该删）。

## 故障响应四段

### 顺序不能乱：止损 → 时线 → 根因 → 复盘

**「先止损再查因」是铁律。** 故障期间首要目标是恢复服务。

```
❌ 故障中：「等一下，我先看看日志搞清楚为什么」→ 故障时长翻倍
✅ 故障中：先回滚/降级恢复服务 → 恢复后慢慢查
```

### ① 止损（手段按速度排序）

| 手段 | 适用 | 速度 |
|---|---|---|
| **回滚** | 刚发布后出问题 | 最快恢复到已知 good 状态 |
| 降级 | 某个功能出问题，核心链路还能保 | 快（若有开关） |
| 限流 | 容量问题、下游过载 | 快 |
| 扩容 | 容量问题 | 较慢（分钟级） |
| 修复上线 | 无法回滚（数据已变） | 最慢，最后选择 |

**功能开关（feature flag）是最有效的止损工具**：不发版就能关掉出问题的功能。高风险功能上线时配一个开关，成本很低。

### ② 时线（恢复后立即记，不要等复盘）

```
14:32  发布 v2.3.1（灰度 10%）
14:41  导出失败率告警 P1（8.2%）
14:43  值班确认，开始排查
14:47  定位：失败集中在存储上传步骤
14:49  决定回滚
14:53  回滚完成，失败率回落至 0.3%
15:20  根因确认：新版使用的存储 SDK 版本与现有凭证格式不兼容
```

**时线要在记忆新鲜时记。** 隔一天再回忆，时间点和判断过程都会失真。

时线的价值：算出**发现耗时**（9 分钟）和**恢复耗时**（12 分钟）——这两个数字是改进监控与响应流程的依据。

### ③ 根因（区分直接原因与根本原因）

```
直接原因：存储 SDK 版本与凭证格式不兼容
根本原因：① 依赖升级未在预发环境验证存储上传路径
         ② 预发环境用的是 mock 存储，与生产不一致（环境保真度问题）
```

**只找直接原因会导致同类问题反复发生。** 要追问「为什么这个问题能走到生产」。

### ④ 复盘

| 纪律 | 说明 |
|---|---|
| **对事不对人** | 追问「流程为什么允许这个错误发生」，不追问「谁写错了」 |
| **改进项有责任人和时间** | 否则复盘等于没做 |
| **区分「加检查」与「改机制」** | 「下次注意」不是改进项 |

**追责式复盘的后果是团队不再暴露问题** —— 下次出故障会先想怎么掩盖。这比故障本身危害更大。

## 逃逸归因

**区分两类问题，处理路径完全不同：**

| 类型 | 例 | 处理 |
|---|---|---|
| **需求/实现缺陷** | 逻辑错、边界漏、标准理解错 | 走全链回流（回定义或实现帽） |
| **环境/流程逃逸** | CI 配置错、部署脚本 bug、依赖漂移、证书过期、环境不一致 | **走逃逸归因**，改流程不改需求 |

把环境问题当需求问题处理，会浪费时间重做需求，而真正的漏洞（闸门缺失）没修。

### 逃逸归因四问

```
① 这个问题本该在哪一道闸门被拦住？
   → 依赖升级 + 存储上传路径 → 本该在集成测试或预发验证拦住

② 那道闸门为什么没拦住？
   → 集成测试用 mock 存储，不走真实上传路径
   → 预发环境也是 mock（环境保真度不足）

③ 怎么改闸门让它下次能拦住？
   → 在预发环境接真实存储（沙箱账号）
   → 集成测试增加一个真实上传的用例（标记为需真实环境）
   → 依赖升级时强制跑该用例

④ 这个改动会不会让闸门太慢或太吵？
   → 真实上传测试约 3 秒，可接受
   → 只在依赖变更时跑，不进每次 CI
```

**「加个人工检查项」通常是坏答案** —— 人会忘。能自动化的要自动化（进脚本闸门）。

### 记进 _lessons.md

```
## 2026-09-05 · 存储 SDK 升级导致导出失败

类型：环境逃逸（非需求缺陷）
发现耗时：9 分钟 | 恢复耗时：12 分钟
本该拦住的闸门：集成测试 / 预发验证
未拦住的原因：两处都用 mock 存储

改进项：
  [ ] 预发环境接真实存储沙箱 —— <责任人> —— <日期>
  [x] 集成测试加真实上传用例（依赖变更时触发）—— <责任人> —— 已完成
  [ ] 依赖升级流程加「影响面清单」步骤 —— <责任人> —— <日期>

不可自动化的部分：
  依赖升级时需人工判断影响哪些外部集成 → 已加入 PR 模板检查项
```

**逃逸归因的累积价值**：三个月后回看 `_lessons.md`，能发现哪类闸门反复失效——那就是系统性问题所在。

## 闸门度量

**拦截数为 0 的闸门应该删。**

```
过去一个季度：
  单元测试闸门：拦截 47 次   ← 有价值
  架构检查闸门：拦截 12 次   ← 有价值
  某个格式检查：拦截 0 次    ← 要么规则已内化，要么规则无效 → 考虑删除
```

闸门不是越多越好：每道闸门都有维护成本和时间成本。不拦东西的闸门只是在浪费每次 CI 的时间，且会让人习惯性跳过检查。
