# 发布策略与回滚

## 运行版本与就绪顺序

共享工作树或多项工作并行时，先固定本次源码/构建/配置身份、文件归属及已有 WIP；不能把另一任务的暂存内容顺带提交，或因 Git 可合入就声称候选版本已经验证。沿项目现有发布方式重建并核对实际消费位置，版本号、包名与源码路径本身都不是运行实例已加载的证据。

服务切换先确认获授权的进程完成停止、目标端口与新实例就绪，再执行大批探测。第一个就绪探测失败时先定位服务阶段，不把后续批量连接失败记成许多资源缺陷。等待与升级停止方式沿该服务的运行约定，不用一个通用固定等待秒数或强杀无关进程替代。

200 健康响应不能证明本次功能已载入；按适用契约补新参数/响应形状、版本指纹或特征正反例，并核一个实际消费者。已通过的测试范围留证；按新变更影响及项目门禁选择后续检查，耗时异常先诊断，不能靠删必要测试或绕过失败门禁结束发布。

## 定向验证与共享工作区发布

按明确的变更影响与当前用户约束选择检查集，记录检查对应的提交、环境、命令及实际覆盖；只改版本元数据不自动增加业务测试范围。保留项目原钩子及其定向配置。若钩子范围与当前约束冲突，先解决冲突或报告所缺决定，不能跳过钩子，也不能暗中跑全量。

共享工作区有无关 WIP 时，可在干净副本对固定的本次提交执行原门禁并推送；核内容、提交身份和目标分支一致，避免混入素材、凭据、私有计划或他人暂存改动。不使用整仓 add、reset 或 stash 清场来换取干净状态。修正最后一处代码/夹具后更新候选并重跑受影响检查，不能引用旧候选的绿灯。

失败保留为失败；基线可复现的旧测试错误写清来源与影响，按已有授权修复或交有权者决定，不能自行豁免。推送后核远端实际提交。静态文件已生效不等于运行中的后端已更新；是否重启按实际消费方式及在途任务判断，不为文案/样式更新打断活动生成。

### 多代理共享仓库的单点集成与清理收尾

- **单点串行推送，杜绝并发争抢测试库**：多个宿主或代理（如 Grok、Codex、AGY）共享同一仓库与测试数据库时，推送前先检查本机无其他并发 `pre-push` / 测试进程；由单一集成者串行完成门禁与推送，避免双路 CI 互相锁死测试库。
- **禁止 `stash push ... && push; stash pop` 绕行**：他人留下的脏文件或失败改动不得先暂存再在推送后自动 `stash pop`，否则会在并发或推送结束后将损坏代码静默弹回主工作树。
- **删旧检出目录必跑 `git worktree prune`**：清理临时验证目录或隔离工作区后，立即执行 `git worktree prune` 并核对 `git worktree list` 无 `prunable` 僵尸登记。
- **幂等暂存收据清理须宽限期 + 摘要双证**：清理上传／任务暂存目录（如 `.staging/*.json`）不得整批清空；仅删除超过约定宽限期（如 24 小时）、旁无未提交 `.bytes` 且目标对象已校验摘要存在的收据。

## 回滚为什么必须实测

**写下来的回滚步骤在真要用的时候经常是错的。** 常见的失效方式：

| 失效 | 原因 |
|---|---|
| 命令语法错 | 写的时候没跑过 |
| 权限不足 | 写方案的人有权限，值班的人没有 |
| 依赖已变 | 旧版本镜像已被清理 |
| 数据不兼容 | 旧代码读不了新版写入的数据 |
| 步骤顺序错 | 先回滚代码还是先回滚数据，顺序错了会出错 |
| 耗时远超预期 | 以为 5 分钟，实际 40 分钟 |

**故障期间是最不适合调试回滚方案的时刻。** 所以要在发布前的平静时刻跑一遍。

## 按实际变更选择代码、数据、配置的恢复验证

### ① 代码回滚

```
$ <部署新版本>
$ <验证新版本运行正常>
$ <执行回滚命令>
$ <验证服务恢复正常：健康检查 + 一个真实请求>
记录：回滚耗时 <n> 分钟
```

**关键是记录实测耗时。** 5 分钟和 40 分钟对应完全不同的风险决策：40 分钟的回滚意味着灰度要更谨慎、观察要更灵敏。

### ② 数据回滚

```
$ alembic upgrade +1      exit: 0
$ alembic downgrade -1    exit: 0     ← 这一步是重点
$ alembic upgrade +1      exit: 0
```

**并且要回答：down 之后数据还在吗？**

| 变更类型 | down 后数据 |
|---|---|
| 加表/加列/加索引 | 删除新增表/列可能丢失新写入数据；索引回退也需评估约束变化 |
| 回填数据 | 通常保留（回填是幂等的） |
| **删列/删表**（contract 步骤） | **数据丢失** —— 必须显式声明不可逆 + 变更前备份 |
| 改类型（缩小） | 可能截断 —— 不可逆 |

### ③ 配置回滚

配置也会引发故障（改错了限流阈值、改错了外部地址）。要能快速恢复：

- 配置有版本记录（谁改的、改了什么、什么时候）
- 能一键回到上一版
- 配置变更也要走灰度（先在一个实例生效，观察后全量）

## 数据兼容性：回滚的隐藏杀手

**新版写入的数据，旧版代码能读吗？** 这个问题决定了回滚是否真的可行。

### 典型失效

```
新版：加了 NOT NULL 字段 channel，并开始写入
回滚到旧版：旧版不知道 channel 字段，插入时不带它
→ 违反 NOT NULL 约束 → 所有写入失败
→ 回滚反而造成了更大的故障
```

```
新版：把 status 的取值从 'done' 改成 'completed'
回滚到旧版：旧版遇到 'completed' 不认识
→ 状态判断全错，可能触发错误的业务逻辑
```

### 解法：expand-contract 降低兼容风险，不能自动保证可回滚

`dba` 的 expand-contract 三步法的核心价值就在这里：

```
Step 1 expand（加可空列 + 双写）
  → 回滚安全：旧版忽略新列
Step 2 migrate（回填 + 切读）
  → 回滚安全：两列数据都完整，旧版读旧列
Step 3 contract（删旧列）
  → 回滚有损：需要从新列恢复数据
```

前两步也必须验证双写一致性、旧版本可读写性及新增数据的保存；不能由步骤名称推定回滚安全。contract 之后可能只能前滚或恢复。数据变更方法以 schema skill 为唯一源。

### 枚举值扩展的兼容性

新增枚举值时，旧版代码遇到未知值会怎样？

```
❌ 旧版：switch(status) { case 'a': ... case 'b': ... }  // 无 default，未知值静默跳过
✅ 旧版：有 default 分支，未知值走安全路径 + 记日志
```

**这要求在设计时就让消费方容忍未知值** —— 这是 `architect` 契约设计的一部分（前端要有 default 分支、消费方要容忍未知字段）。

## 回滚窗口

**有些变更过了某个时间点就不能简单回滚了。** 要明确写出这个窗口：

| 变更 | 回滚窗口 |
|---|---|
| 纯代码逻辑 | 无限制 |
| 新增数据写入 | 数据产生后回滚，新数据可能变成孤儿 |
| 发出的事件/消息 | **下游消费后不可撤回** |
| 发出的通知/邮件 | 不可撤回 |
| 对外 API 变更 | 客户已适配后回滚会破坏他们 |
| 收缩型 DDL | 执行后数据已丢失 |

**「已发出的消息不可撤回」是最容易被忽略的**：回滚了代码，但下游已经根据错误的事件做了处理。这类变更要考虑补偿机制而非单纯回滚。

## 发布策略与风险匹配

| 风险 | 特征 | 策略 | 观察时长 |
|---|---|---|---|
| 低 | 文案/样式/日志/配置 | 直接发布 | 15 分钟 |
| 中 | 新增功能、加字段、加索引 | 10% → 50% → 100% | 每档 30 分钟 |
| 高 | 改既有逻辑、改认证、改数据结构 | 1% → 5% → 25% → 100% | 每档 1–2 小时 |
| 不可逆 | 数据迁移、破坏性 DDL | 备份 + 演练 + 窗口期 + 全程盯 | 按变更定 |

### 灰度维度选择

| 维度 | 优点 | 缺点 |
|---|---|---|
| 流量比例 | 简单 | 同一用户可能命中不同版本，体验不一致 |
| **用户 ID 哈希** | 同一用户始终同一版本 | 推荐默认 |
| 租户 | 便于定向观察与回滚，爆炸半径清晰 | 多租户系统适用 |
| 内部用户优先 | 自己人先踩坑 | 内部用户行为可能不代表真实用户 |
| 地域 | 可按时区错峰 | 需要地域路由能力 |

**多租户系统优先按租户灰度**：一个租户出问题只影响一个客户，且定位与回滚都清晰。

### 放量判据（提前定，不临场判断）

```
放量条件（全部满足）：
  ✅ 错误率 ≤ 基线 + 0.5%
  ✅ P95 ≤ 基线 × 1.2
  ✅ 业务指标 ≥ 基线 - 2%
  ✅ 无 P0/P1 告警
  ✅ 日志无新增未知异常类型

回滚条件（任一满足，不讨论）：
  ❌ 错误率 > 基线 + 2%
  ❌ P95 > 基线 × 2
  ❌ 数据不一致
  ❌ P0 告警
```

**「不讨论」这三个字很重要。** 故障时人在压力下会倾向「再观察一下」，把判据提前写死能避免这种拖延。

### 基线怎么取

```
❌ 用发布前一分钟的数据当基线（波动大）
✅ 用同期数据：上周同一时段、或过去 7 天同一小时的均值
```

**流量有周期性**：周一上午和周六凌晨完全不同。基线要同期对比。

### 观察时长要覆盖业务周期

有些代码路径只在特定时刻执行：

| 路径 | 需要观察到 |
|---|---|
| 定时任务 | 至少一次执行 |
| 月末结算 | 跨月才能验证 |
| 每日报表 | 至少一天 |
| 缓存过期后的回源 | 超过 TTL 时长 |
| 重试与死信 | 超过重试窗口 |

**只观察 30 分钟就全量的高风险变更，会漏掉这些低频路径。** 有低频路径时，灰度期要延长或专门触发验证。

## 发布前的门禁核对

**门禁未全绿不发布。** 这不是 SRE 的判断权限：

```
✅ 正确：脚本失败 → 不发布 → 要么修，要么走人工豁免流程（有记录、有责任人）
❌ 错误：脚本失败 → 「这个失败看起来不影响」→ 发布
```

要核对的是**实际输出**而非声称：

```
❌ qa 说「测试都过了」
✅ 看 test-report.md 里的命令 + 退出码原样输出；确认 skipped 数量已解释
```

引用门禁指纹（commit sha + 命令 + 退出码）进 release-checklist —— 这样事后能确认「发布的确实是那个通过了测试的版本」。

## 专项高危面：优雅降级、金融仅补偿恢复与不可逆客户端发版

跨行业专项交付规范详见 [industry-delivery-sops.md](../../impl-evidence/references/industry-delivery-sops.md)：

1. **优雅降级演练（Graceful Brownout）**：
   - 高消耗或强外部依赖能力（LLM 生成、推荐重排、实时富化、大表同步导出）必须配备运行时热开关或自适应负载卸载。上线前在预发真实触发一次降级开关，验证：非核心支路快速返回降级态，核心登录/读/交易链路延迟与成功率不受拖累，关闭降级后自动恢复。
2. **金融与账本仅补偿恢复（Fintech Compensation-Only Recovery）**：
   - 涉及资金清结算、钱包余额、双式记账分录或合规审计流水的变更，**严禁执行破坏性 `downgrade` 迁移或回删/篡改已提交账本记录**。故障恢复一律采用「代码安全止损（熔断/开关）+ 前滚修复（Roll-forward）+ 反向红冲/补偿分录（Compensating Journal Entry）」，并与 `dba` 对账确保借贷零差额。
3. **不可逆客户端二进制发版（iOS / Android / Desktop / CLI / SDK / 固件）**：
   - 已下发到用户终端或卡在应用商店审核队列的二进制包无法像服务端容器那样秒级回滚。发版就绪（`readiness.md`）必须核实：① 服务端远端功能熔断开关（Kill-Switch）；② 最低支持版本门禁与强制升级引导（如 `426 Upgrade Required` + 升级弹窗）；③ 服务端接口保持至少 **N-2** 活跃客户端版本向后兼容；④ 崩溃率（Crash-Free Sessions）红线与签名公证（Code Signing / Notarization）指纹。

## 实测记录格式

```
回滚实测 · <日期>

代码回滚：
  $ <部署命令>                          exit: 0
  $ curl -f https://.../health          exit: 0   （新版正常）
  $ <回滚命令>                          exit: 0
  $ curl -f https://.../health          exit: 0   （回滚后正常）
  $ <一个真实业务请求>                    exit: 0
  实测耗时：4 分 20 秒

数据回滚：
  $ alembic upgrade +1                  exit: 0
  $ alembic downgrade -1                exit: 0
  $ alembic upgrade +1                  exit: 0
  数据恢复能力：✅ 结构变更，无数据损失

数据兼容性：
  ✅ 新版写入的行，旧版代码可正常读取（已用旧版镜像验证）
  ✅ 新增字段为可空，旧版插入不带该字段不会失败

回滚窗口：
  ⚠️ 本次会向下游发出 export.completed 事件，已消费的事件不可撤回
  → 回滚后需人工确认下游状态（联系 <责任人>）

执行人权限：
  ✅ 值班角色 <role> 具备回滚权限（已验证）
```
