# 发布策略与回滚

## 回滚为什么必须实测

**写下来的回滚步骤在真要用的时候经常是错的。** 常见的失效方式：

| 失效 | 原因 |
|---|---|
| 命令语法错 | 写的时候没跑过 |
| 权限不足 | 写方案的人有权限，值班的人没有 |
| 依赖已变 | 旧版本镜像已被清理 |
| 数据不兼容 | 旧代码读不了新版写入的数据 |
| 步骤顺序错 | 先回滚代码还是先回滚数据，顺序错了会出错 |
| 耗时远超预期 | 以为 5 分钟，实际 40 分钟 |

**故障期间是最不适合调试回滚方案的时刻。** 所以要在发布前的平静时刻跑一遍。

## 三类回滚都要实测

### ① 代码回滚

```
$ <部署新版本>
$ <验证新版本运行正常>
$ <执行回滚命令>
$ <验证服务恢复正常：健康检查 + 一个真实请求>
记录：回滚耗时 <n> 分钟
```

**关键是记录实测耗时。** 5 分钟和 40 分钟对应完全不同的风险决策：40 分钟的回滚意味着灰度要更谨慎、观察要更灵敏。

### ② 数据回滚

```
$ alembic upgrade +1      exit: 0
$ alembic downgrade -1    exit: 0     ← 这一步是重点
$ alembic upgrade +1      exit: 0
```

**并且要回答：down 之后数据还在吗？**

| 变更类型 | down 后数据 |
|---|---|
| 加表/加列/加索引 | 结构回退，无数据损失 |
| 回填数据 | 通常保留（回填是幂等的） |
| **删列/删表**（contract 步骤） | **数据丢失** —— 必须显式声明不可逆 + 变更前备份 |
| 改类型（缩小） | 可能截断 —— 不可逆 |

### ③ 配置回滚

配置也会引发故障（改错了限流阈值、改错了外部地址）。要能快速恢复：

- 配置有版本记录（谁改的、改了什么、什么时候）
- 能一键回到上一版
- 配置变更也要走灰度（先在一个实例生效，观察后全量）

## 数据兼容性：回滚的隐藏杀手

**新版写入的数据，旧版代码能读吗？** 这个问题决定了回滚是否真的可行。

### 典型失效

```
新版：加了 NOT NULL 字段 channel，并开始写入
回滚到旧版：旧版不知道 channel 字段，插入时不带它
→ 违反 NOT NULL 约束 → 所有写入失败
→ 回滚反而造成了更大的故障
```

```
新版：把 status 的取值从 'done' 改成 'completed'
回滚到旧版：旧版遇到 'completed' 不认识
→ 状态判断全错，可能触发错误的业务逻辑
```

### 解法：expand-contract 保证每步可回滚

`/dba` 的 expand-contract 三步法的核心价值就在这里：

```
Step 1 expand（加可空列 + 双写）
  → 回滚安全：旧版忽略新列
Step 2 migrate（回填 + 切读）
  → 回滚安全：两列数据都完整，旧版读旧列
Step 3 contract（删旧列）
  → 回滚有损：需要从新列恢复数据
```

**前两步的回滚是完全安全的。** 只有第三步需要谨慎，而第三步应该在充分观察后才做。

### 枚举值扩展的兼容性

新增枚举值时，旧版代码遇到未知值会怎样？

```
❌ 旧版：switch(status) { case 'a': ... case 'b': ... }  // 无 default，未知值静默跳过
✅ 旧版：有 default 分支，未知值走安全路径 + 记日志
```

**这要求在设计时就让消费方容忍未知值** —— 这是 `/architect` 契约设计的一部分（前端要有 default 分支、消费方要容忍未知字段）。

## 回滚窗口

**有些变更过了某个时间点就不能简单回滚了。** 要明确写出这个窗口：

| 变更 | 回滚窗口 |
|---|---|
| 纯代码逻辑 | 无限制 |
| 新增数据写入 | 数据产生后回滚，新数据可能变成孤儿 |
| 发出的事件/消息 | **下游消费后不可撤回** |
| 发出的通知/邮件 | 不可撤回 |
| 对外 API 变更 | 客户已适配后回滚会破坏他们 |
| 收缩型 DDL | 执行后数据已丢失 |

**「已发出的消息不可撤回」是最容易被忽略的**：回滚了代码，但下游已经根据错误的事件做了处理。这类变更要考虑补偿机制而非单纯回滚。

## 发布策略与风险匹配

| 风险 | 特征 | 策略 | 观察时长 |
|---|---|---|---|
| 低 | 文案/样式/日志/配置 | 直接发布 | 15 分钟 |
| 中 | 新增功能、加字段、加索引 | 10% → 50% → 100% | 每档 30 分钟 |
| 高 | 改既有逻辑、改认证、改数据结构 | 1% → 5% → 25% → 100% | 每档 1–2 小时 |
| 不可逆 | 数据迁移、破坏性 DDL | 备份 + 演练 + 窗口期 + 全程盯 | 按变更定 |

### 灰度维度选择

| 维度 | 优点 | 缺点 |
|---|---|---|
| 流量比例 | 简单 | 同一用户可能命中不同版本，体验不一致 |
| **用户 ID 哈希** | 同一用户始终同一版本 | 推荐默认 |
| 租户 | 便于定向观察与回滚，爆炸半径清晰 | 多租户系统适用 |
| 内部用户优先 | 自己人先踩坑 | 内部用户行为可能不代表真实用户 |
| 地域 | 可按时区错峰 | 需要地域路由能力 |

**多租户系统优先按租户灰度**：一个租户出问题只影响一个客户，且定位与回滚都清晰。

### 放量判据（提前定，不临场判断）

```
放量条件（全部满足）：
  ✅ 错误率 ≤ 基线 + 0.5%
  ✅ P95 ≤ 基线 × 1.2
  ✅ 业务指标 ≥ 基线 - 2%
  ✅ 无 P0/P1 告警
  ✅ 日志无新增未知异常类型

回滚条件（任一满足，不讨论）：
  ❌ 错误率 > 基线 + 2%
  ❌ P95 > 基线 × 2
  ❌ 数据不一致
  ❌ P0 告警
```

**「不讨论」这三个字很重要。** 故障时人在压力下会倾向「再观察一下」，把判据提前写死能避免这种拖延。

### 基线怎么取

```
❌ 用发布前一分钟的数据当基线（波动大）
✅ 用同期数据：上周同一时段、或过去 7 天同一小时的均值
```

**流量有周期性**：周一上午和周六凌晨完全不同。基线要同期对比。

### 观察时长要覆盖业务周期

有些代码路径只在特定时刻执行：

| 路径 | 需要观察到 |
|---|---|
| 定时任务 | 至少一次执行 |
| 月末结算 | 跨月才能验证 |
| 每日报表 | 至少一天 |
| 缓存过期后的回源 | 超过 TTL 时长 |
| 重试与死信 | 超过重试窗口 |

**只观察 30 分钟就全量的高风险变更，会漏掉这些低频路径。** 有低频路径时，灰度期要延长或专门触发验证。

## 发布前的门禁核对

**门禁未全绿不发布。** 这不是 SRE 的判断权限：

```
✅ 正确：脚本失败 → 不发布 → 要么修，要么走人工豁免流程（有记录、有责任人）
❌ 错误：脚本失败 → 「这个失败看起来不影响」→ 发布
```

要核对的是**实际输出**而非声称：

```
❌ /qa 说「测试都过了」
✅ 看 test-report.md 里的命令 + 退出码原样输出；确认 skipped 数量已解释
```

引用门禁指纹（commit sha + 命令 + 退出码）进 release-checklist —— 这样事后能确认「发布的确实是那个通过了测试的版本」。

## 实测记录格式

```
回滚实测 · <日期>

代码回滚：
  $ <部署命令>                          exit: 0
  $ curl -f https://.../health          exit: 0   （新版正常）
  $ <回滚命令>                          exit: 0
  $ curl -f https://.../health          exit: 0   （回滚后正常）
  $ <一个真实业务请求>                    exit: 0
  实测耗时：4 分 20 秒

数据回滚：
  $ alembic upgrade +1                  exit: 0
  $ alembic downgrade -1                exit: 0
  $ alembic upgrade +1                  exit: 0
  数据恢复能力：✅ 结构变更，无数据损失

数据兼容性：
  ✅ 新版写入的行，旧版代码可正常读取（已用旧版镜像验证）
  ✅ 新增字段为可空，旧版插入不带该字段不会失败

回滚窗口：
  ⚠️ 本次会向下游发出 export.completed 事件，已消费的事件不可撤回
  → 回滚后需人工确认下游状态（联系 <责任人>）

执行人权限：
  ✅ 值班角色 <role> 具备回滚权限（已验证）
```
