# 用例推导

## 为什么不能照着实现写用例

```
实现：if row_count > 10000: raise Error
用例（照实现写）：测 10001 报错，测 10000 通过  ✅ 通过

实际 GWT：单次最多导出 10000 条
真实缺陷：如果实现写的是 >= 10000，照实现写的用例仍然"通过"
         因为用例是从实现推导的，实现的错误被复制进了用例
```

**用例的唯一合法来源是 GWT 与契约。** 写用例时不要打开实现代码——这是纪律，不是建议。

## 等价类划分

把输入取值空间切成「行为相同」的类，每类取一个代表值。

### 完整示例

```
参数：filter.status（工单状态筛选）
契约：可选，string[]，枚举 open/pending/resolved/closed，不传 = 全部

有效等价类：
  E1  不传                    → 返回全部状态
  E2  单个有效值 ["open"]      → 只返回 open
  E3  多个有效值 ["open","pending"] → 返回这两种
  E4  全部值（4 个都传）        → 等同不传
  E5  空数组 []                → 行为？契约没写 → 回 /architect 问

无效等价类：
  I1  非枚举值 ["invalid"]     → 400 INVALID_PARAM
  I2  混入非枚举 ["open","x"]  → 400
  I3  类型错误 "open"（非数组） → 400
  I4  大小写 ["OPEN"]          → 行为？契约没写 → 回 /architect
```

**E5、I4 这类「契约没写」的发现是等价类划分的重要产出**——它暴露了契约的空白。回 `/architect` 补，不要自己假设一个行为去测。

### 每个等价类一条用例

不要对 `["open"]`、`["pending"]`、`["resolved"]` 各写一条——它们同属 E2，行为相同。**测一个等于测全部**，这是控制用例数量的主要手段。

例外：**枚举值本身的完整性**值得单独覆盖一次（确认每个枚举值都被后端识别），可以用参数化测试一次跑完，不算独立用例。

## 边界值

**缺陷密集分布在边界。** 每个边界取三点：界内、界上、界外。

| 约束 | 界内 | 界上 | 界外 |
|---|---|---|---|
| 最多 10000 条 | 9999 | **10000** | 10001 |
| 区间 ≤ 90 天 | 89 天 | **90 天** | 91 天 |
| 长度 1–64 字符 | 2, 63 | **1, 64** | 0, 65 |
| 最多 50 个 ID | 49 | **50** | 51 |
| 分页 limit ≤ 100 | 99 | **100** | 101 |

**「界上」最容易出错**：`>` 与 `>=` 混用、`<=` 与 `<` 混用，只有恰好取边界值才能发现。这类缺陷在生产上表现为「刚好 10000 条时报错」，极难排查。

### 其它常见边界

```
数字：      0 · 负数 · 极大值（整数溢出）· 精度（0.005 的舍入）
字符串：    空串 · 只有空格 · 首尾空格 · 超长 · 特殊字符 · emoji · SQL/HTML 注入串
集合：      空 · 1 个 · 上限 · 上限+1
时间：      跨天边界（23:59:59 → 00:00:00）· 月末 · 闰年 2/29 · 时区边界 · 夏令时
分页：      第 1 页 · 最后一页 · 超出最后一页 · 数据量恰好等于页大小
并发：      同时 2 个请求 · 同时 N 个请求
```

**「数据量恰好等于页大小」**是分页实现的经典边界：20 条数据每页 20 条时，`has_more` 该是 false 还是 true？很多实现在这里错。

**空串 vs null vs 缺字段**是三种不同输入，行为可能不同，各测一次。

## 状态流转覆盖

从 PRD 的流转图推导。**合法与非法都是必需的**。

### 示例

```
流转图：
pending ──支付成功──> paid ──发货──> shipped ──签收──> completed
   └──超时/取消──> canceled
终态：completed, canceled
```

**合法流转**（每条边一条用例）：

| 用例 | Given | When | Then |
|---|---|---|---|
| TC-101 | 订单 pending | 支付回调成功 | 状态 paid，`paid_at` = 回调时刻，库存已扣 |
| TC-102 | 订单 paid | 发货操作 | 状态 shipped，`shipped_at` 已记 |
| TC-103 | 订单 pending | 超时 30 分钟 | 状态 canceled，库存已释放 |

**非法流转**（每条不存在的边一条用例）：

| 用例 | Given | When | Then（**三项都要断言**） |
|---|---|---|---|
| TC-121 | 订单 canceled | 支付回调到达 | ① 状态仍 canceled ② 记录「迟到回调」 ③ **库存未扣** |
| TC-122 | 订单 shipped | 再次发货 | ① 状态仍 shipped ② 无重复记录 ③ 无重复扣减 |
| TC-123 | 订单 completed | 任何流转 | ① 状态不变 ② 返回错误 ③ 无副作用 |

**只断言「返回错误」是不够的。** 真实事故形态：接口返回了 409，但库存已经扣了——因为实现里先扣库存再校验状态。不断言副作用就测不出来。

### 状态流转的组合

状态 × 操作的矩阵，把所有格子列出来：

| 状态＼操作 | 支付 | 发货 | 取消 | 退款 |
|---|---|---|---|---|
| pending | ✅ TC-101 | ❌ TC-124 | ✅ TC-103 | ❌ TC-125 |
| paid | ❌ TC-121 | ✅ TC-102 | ❌ TC-126 | ✅ TC-104 |
| shipped | ❌ | ❌ TC-122 | ❌ | ✅ |
| canceled | ❌ TC-121 | ❌ | ❌ | ❌ |
| completed | ❌ TC-123 | ❌ | ❌ | ✅/❌ |

**空格子是漏测。** 这张表让漏测一眼可见，比列表形式好用。

## 权限矩阵覆盖

从 PRD 权限矩阵逐格推导：**每个角色 × 每个操作**。

| 角色＼操作 | 导出自己的 | 导出全组 | 导出其它组 | 查看他人任务 |
|---|---|---|---|---|
| 主管 | ✅ TC-201 | ✅ TC-202 | ❌ TC-203 | ✅ TC-204 |
| 客服 | ✅ TC-205 | ❌ TC-206 | ❌ TC-207 | ❌ TC-208 |
| 未登录 | ❌ TC-209 | ❌ | ❌ | ❌ |

### 越权测试的三类（第三类最容易漏）

```
① 换角色    —— 用客服账号做主管的操作
② 换数据范围 —— 改请求里的 ID/租户，访问他人数据
③ 直接调接口 —— 绕过前端，直接构造 HTTP 请求
```

**第三类是真正的安全测试**：前端隐藏了按钮不等于后端有校验。必须用 curl / 测试客户端直接发请求。

多租户系统还要加一类：**跨租户访问**（改 `tenant_id` 或用 A 租户的 token 访问 B 租户的资源 ID）。这是最严重的漏洞类型，必测。

## 组合裁剪：pairwise

3 个参数各 4 个取值 = 64 种全组合，维护不动。**两两组合**把它压到十几组，且经验上能发现大部分组合缺陷。

### 原理

保证**任意两个参数**的每种取值组合至少出现一次。多数缺陷由两个参数的交互引起，三个以上参数同时交互才触发的缺陷很少。

### 示例

```
参数：
  status:  [open, pending, resolved]        3 个
  format:  [csv]                            1 个
  columns: [最少 1 列, 典型 4 列, 最多 20 列]  3 个
  scope:   [自己, 全组]                      2 个

全组合 = 3 × 1 × 3 × 2 = 18 组
pairwise ≈ 6 组：

TC  status    format  columns  scope
1   open      csv     1 列     自己
2   open      csv     4 列     全组
3   pending   csv     20 列    自己
4   pending   csv     1 列     全组
5   resolved  csv     4 列     自己
6   resolved  csv     20 列    全组
```

检验：任取两列，它们的取值组合都出现过。

### 什么时候不用 pairwise

| 情况 | 用 |
|---|---|
| 参数少（≤3 个且取值少） | 全组合（成本本来就低） |
| 极高风险场景（支付、权限） | 全组合 |
| 参数间确实无交互 | 单因素（每次变一个） |
| 有明确的高危组合 | pairwise + 手工补上高危组合 |

**必须在测试计划里注明裁剪策略**——审查者要能看出你是有意裁剪而非遗漏。写「已用 pairwise 从 18 组裁剪至 6 组」，而不是默默只写 6 条。

## 从 GWT 到用例的完整展开示例

```
GWT-01.4  Given 选中 10001 条工单
          When  点击导出
          Then  提示「单次最多导出 10000 条」，不产生文件
```

这一条 GWT 展开为：

| 用例 | 输入 | 断言 |
|---|---|---|
| TC-004 | 10001 条 | 422 + code=ROW_LIMIT_EXCEEDED + detail.limit=10000 + **无导出任务记录** + **无文件** |
| TC-005 | 10000 条（界上） | 200/202 + 任务创建成功 |
| TC-006 | 9999 条（界内） | 200/202 |
| TC-007 | 0 条（选中但全部已删） | 空态行为（GWT-01.2） |

**一条 GWT 通常展开 2–4 条用例**（界上、界外、以及 Then 里各项副作用的断言）。矩阵里要能看出这个展开关系。

注意 TC-004 的断言包含了「不产生文件」——这是 GWT 的 Then 里明确写的，必须断言。只断言错误码等于漏测了一半。
