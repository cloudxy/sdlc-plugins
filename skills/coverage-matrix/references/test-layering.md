# 分层、隔离、环境保真、回归

## 分层判定

放错层的代价：能在单测覆盖的放进 E2E，套件慢十倍且易碎；该在集成测的放单测，mock 掉了真实行为等于没测。

```
这个用例验证什么？
├─ 纯逻辑/算法/格式化/校验规则/边界值
│   → 单元测试（毫秒级，无外部依赖）
├─ 真实 DB 读写/事务/并发/幂等/迁移
│   → 集成测试（需要真实数据库）
├─ 跨系统串联/关键用户旅程
│   → E2E（只测主干，个位数到十几条）
└─ 性能/容量
    → 专项测试（需要接近生产的数据量）
```

### 各层的判定要点

| 层 | 该测 | 不该测 |
|---|---|---|
| **单元** | 边界值、等价类、算法分支、格式化、纯校验规则 | 需要真实 DB 的行为、跨组件协作 |
| **集成** | 事务回滚、并发冲突、幂等、唯一约束、真实 SQL 行为、外部依赖降级（mock 掉依赖但走真实内部链路） | 纯逻辑分支（下移到单测）、UI 交互 |
| **E2E** | 「用户能不能走通主路径」 | 边界值、错误分支、权限矩阵的每一格 |

**E2E 的正确用法**：一条 E2E 覆盖「登录 → 筛选 → 导出 → 下载成功」的主干。不要写「E2E 测超限报错」——那在集成层测更快更稳。

### 金字塔比例

```
      ╱╲        E2E        个位数到十几条
     ╱──╲       集成       几十到上百条
    ╱────╲      单元       几百到上千条
```

倒过来的形状（E2E 最多）是常见反模式：套件跑半小时、随机失败、维护成本高到没人愿意改。

## 测试隔离

**每个用例必须能单独跑、能并行跑、能任意顺序跑。**

### 四条纪律

```
① 自己准备数据，自己清理
   ❌ 依赖数据库里预先存在的记录
   ✅ 用例内创建所需数据，结束后回滚或删除

② 不依赖其它用例的产物
   ❌ TC-002 用 TC-001 创建的订单
   ✅ 各自创建

③ 不依赖执行顺序
   ❌ 用例 A 改了全局配置，用例 B 依赖这个改动
   ✅ 每个用例自己设置所需状态

④ 不共享可变状态
   ❌ 模块级变量、共享的 mock 对象
   ✅ 每个用例独立的 fixture
```

违反这些的症状：**单独跑通过，全套跑失败**，或者**并行跑随机失败**。这类问题排查成本极高。

### 事务回滚做隔离

```python
@pytest.fixture
async def db_session():
    async with engine.begin() as conn:      # 开事务
        async with AsyncSession(bind=conn) as session:
            yield session
        await conn.rollback()                # 用例结束回滚，数据不残留
```

比「用例结束后删数据」更可靠——删的逻辑本身可能有 bug 或漏删。

### 时间与随机

```python
❌ assert order.created_at.date() == date.today()      # 跨天时随机失败
✅ with freeze_time("2026-09-05 14:30:00"):
       ...
   assert order.created_at == datetime(2026, 9, 5, 14, 30, tzinfo=UTC)

❌ user = create_user(name=random_string())            # 失败时无法复现
✅ faker.seed_instance(42)                             # 固定种子
```

**跨天边界的随机失败**是最烦人的一类：CI 在半夜跑就红，白天跑就绿。凡涉及「今天」「本周」「本月」的用例都要冻结时间。

## 环境保真度

**测试库与生产库不同 = 一整类缺陷测不出来。**

### SQLite 放行、真库报错的常见情况

| 差异 | SQLite 行为 | MySQL/PG 行为 |
|---|---|---|
| 字符串长度约束 | 忽略 `VARCHAR(20)` 长度 | 超长报错或截断 |
| 类型严格性 | 动态类型，什么都能存 | 严格校验 |
| 并发写 | 库级锁，测不出行锁竞争 | 行锁，能测出死锁与等待 |
| `SELECT ... FOR UPDATE` | 无效果 | 真实加锁 |
| 唯一索引与 NULL | 行为不同 | 多个 NULL 可共存（MySQL） |
| 日期函数 | 语法不同 | `DATE_FORMAT` / `TO_CHAR` |
| JSON 操作 | 支持有限 | 各有自己的语法 |
| 事务隔离级别 | 不可配 | 可配，行为差异明显 |
| 大小写敏感 | 表名不敏感 | 取决于配置与平台 |

### 处理方式

**优先用与生产同类型的数据库跑集成测试**（Docker 起一个 MySQL/PG）。这是最省事的做法——环境保真的成本远低于漏掉一整类缺陷。

做不到时，把涉及以上差异的用例标注：

```
TC-030  唯一约束在并发下的行为    [需真库验证]
TC-031  DATE_FORMAT 时区转换      [需真库验证]
TC-032  FOR UPDATE 锁等待         [需真库验证]
```

这份清单交 `/sre` 在预发环境跑，结果贴回 `test-report.md`。**标注了但没人跑等于没标注**——要在矩阵里跟踪状态。

### 其它保真度问题

| 项 | 风险 |
|---|---|
| 数据量 | 1000 行测不出 N+1 和全表扫；性能用例需要接近生产的量级 |
| 外部依赖 mock | mock 的行为可能与真实不同（真实服务的超时、限流、错误格式） |
| 单实例 vs 多实例 | 单实例测不出分布式锁、缓存一致性问题 |
| 时区配置 | 测试环境 UTC、生产环境本地时区 → 时间相关缺陷 |

**mock 掉的依赖要在报告里列出**，让 `/qc` 知道哪些行为未经真实验证。

## 回归策略

### 影响面推导

改动来了，按五个维度找影响：

```
① 直接影响 —— 改动的模块/函数自身的用例
② 调用方   —— 搜引用：谁调了改动的接口/函数
③ 共享数据 —— 谁读写了改动涉及的表/字段（改字段类型影响所有读它的地方）
④ 共享配置 —— 谁依赖了改动的配置项/常量/枚举
⑤ 已知坑   —— 回归集里与此模块相关的历史缺陷用例
```

第 ③ 项最容易漏：改了 `orders.status` 的枚举值，所有读这个字段的报表、导出、筛选都受影响。

### 回归集的维护

**核心纪律：每个修复的缺陷都要有一条用例进回归集。** 这是「同一个坑不踩两次」的唯一保障。

```
缺陷 BUG-012 修复
  → 复现用例 TC-R012 进回归集（不是修完删掉）
  → 用例注释里写：对应 BUG-012，现象是 X，根因是 Y
```

注释里写清对应的缺陷和根因很重要——三个月后有人想删这条「看起来没用」的用例时，注释会阻止他。

### 回归集要跑得快

回归集会被频繁执行，慢了就没人跑。

- 优先放在**单测/集成层**，不要都堆 E2E
- 目标：全套回归在几分钟内跑完
- 慢用例（性能测试、大数据量）单独成套，按需触发

### 退役规则

长期不失败的用例可以考虑退役，但要满足：

- 对应功能已重写或下线
- 有更好的用例覆盖了同一场景
- **退役要记录**（在哪里、为什么），不要静默删除

**不要因为「一直通过」就删** —— 一直通过说明它在保护一个没有退化的行为，这正是回归用例的目的。

## 测试代码质量

测试代码也是代码，但纪律不同：**清晰性优先于 DRY**。

```
✅ 用例里适度重复是可以接受的 —— 一眼看清测什么比消除重复更重要
❌ 过度抽象的测试工具链 —— 失败时要读三层辅助函数才知道测了什么
```

三条具体要求：

- **测试名说清场景**：`test_export_returns_422_when_rows_exceed_limit` 而非 `test_export_2`
- **Arrange-Act-Assert 三段清晰**，用空行分隔
- **一个用例一个断言主题**（可以多条 assert，但都指向同一个行为）

失败信息要能定位：

```
❌ assert result == expected                  # 失败时只说「不相等」
✅ assert result.code == "ROW_LIMIT_EXCEEDED", f"got {result.code}, body={result.json()}"
```
