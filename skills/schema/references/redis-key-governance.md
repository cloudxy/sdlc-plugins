# Redis 键治理

Redis 没有 schema，所以治理必须靠文档纪律。一个键上线三个月后没人知道它是谁写的、什么时候过期、改了数据要不要删它——这是 Redis 事故的常态成因。

**先区分可重建缓存、权威业务/恢复状态、协调租约与投递回执，再决定命名、过期/清理、故障行为。** Redis 中的任务、账本、写入计划不自动适用缓存规则。多步状态转换参见 [可恢复写入](recoverable-writes.md)。

## 命名规范

```
<域>:<实体>:<标识>[:<变体>]
```

| 例 | 说明 |
|---|---|
| `order:detail:1001` | 订单详情缓存 |
| `user:session:a1b2c3` | 会话 |
| `tenant:42:quota:daily` | 多租户配额，租户 ID 前置 |
| `report:sales:2026-01:v2` | 带版本变体，改口径时 v2 与 v1 并存 |

规则：

- 分隔符统一用 `:`，不混用 `_` `-` `/`
- **多租户系统租户 ID 必须在键里**，且靠前——否则无法按租户清理，也易跨租户串数据
- 键里不放会变的业务值（用户名、状态名）——它们变了老键就成了垃圾
- 有口径变更风险的加版本后缀，切换时新旧并存，老键自然过期
- 键名长度控制在 ~64 字节内（键本身占内存，百万级键的键名开销可观）

## 键生命周期矩阵

每个键在设计时填满这张表，进 `db-spec.md` 的 Redis 段：

| 字段 | 填什么 |
|---|---|
| 键模式 | `order:detail:{order_id}` |
| 类型 | String / Hash / ZSet / Set / List |
| 用途与权威 | 缓存 / 唯一业务或恢复状态 / 租约 / 回执；丢失后从何处重建或接管 |
| 值结构 | JSON 字段清单，或 Hash 的 field 列表 |
| 数据来源 | 哪张表 / 哪个接口 |
| 写入方 | 哪个服务的哪个路径 |
| 读取方 | 哪些调用方（列全，contract 时要用） |
| 过期与淘汰 | TTL 或不设 TTL 的依据；实际 maxmemory-policy、持久化与被逐出/丢失后的行为 |
| 失效/确认清理 | 谁在什么确认条件后删；中断、到期与孤儿状态如何回收 |
| 未命中行为 | 回源查库 / 返回空 / 报错 |
| 容量估算 | 键数量级 × 单值大小 = 内存占用 |

## TTL 决策

| 数据特征 | TTL 取值 | 理由 |
|---|---|---|
| 会话 / 登录态 | 与业务超时对齐（如 30 分钟滑动） | 安全边界 |
| 允许明确陈旧窗口的业务缓存 | 短（30 秒 – 5 分钟）+ 主动失效 | TTL 是兜底，主动删是主路径 |
| 允许延迟的统计/报表 | 中（5 – 60 分钟） | 与刷新周期对齐 |
| 字典 / 配置类 | 长（数小时）+ 变更时主动删 | 极少变 |
| 协调租约 | 按允许持有期设定 | 还需 token、续租/回收及过期后旧执行者的约束；TTL 本身不保证独占 |
| 幂等去重标记 / 回执 | 覆盖允许的离线、重试和人工重放窗口 | 接管与业务提交边界不同；超窗行为须明确 |
| 限流计数器 | 与窗口一致 | 窗口过期即失效 |
| 唯一 pending / 未确认计划 / 发布意图 | 按恢复协议确认清理，必要时不设 TTL | 自动过期可能销毁唯一恢复材料；定义回收、容量与防逐出措施 |

**红线：任何缓存键不得无 TTL。** 唯一例外是显式声明「永不过期」并同时给出：理由、容量上限估算、以及淘汰策略（依赖 `maxmemory-policy` 时要说明配的是哪个）。

可重建缓存批量过期时可给 TTL 加随机抖动（如 `300 + rand(60)` 秒）；安全期限、配额窗口与恢复/去重保留期不能机械抖动。无 TTL 的状态仍需确认清理、容量上限及孤儿回收，且不等于不会被逐出或服务器故障后不丢。

## 失效路径

以下模式只讨论缓存。权威任务/恢复状态使用其提交、确认与回收协议，不因“源数据变化”直接删除。缓存需回答：源数据变了，谁负责失效？

三种模式，选一个并写进矩阵：

| 模式 | 做法 | 适用 |
|---|---|---|
| Cache-Aside（主流） | 写库后**删**缓存（不是改缓存） | 大多数业务缓存 |
| 写穿透 | 写库同时写缓存 | 读极频繁且能接受写放大 |
| 纯 TTL | 不主动失效，靠过期 | 能容忍 TTL 时长内的陈旧数据（统计类） |

Cache-Aside 的关键细节：**删而不是改**。并发下「改缓存」会因两个请求的写序颠倒而留下永久错值；删除也可能失败或与读回填竞态，需要重试、版本检查/对账并说明一致性窗口。

删除时机是先删还是后删：

- **先写库后删缓存**（Cache-Aside 标准）：期间可能有请求读到旧值，窗口短，可接受
- 要求更严 → **延迟双删**：写库前删一次，写库后延迟几百毫秒再删一次，覆盖「读请求在写库期间回填了旧值」的窗口
- 可选：订阅变更日志驱动失效，但仍存在处理延迟/重复/失联恢复；延迟双删和 CDC 都不能自动保证强一致

## 三个经典故障与处理

### 缓存穿透（查不存在的数据，每次都打库）

恶意或异常请求查一个永远不存在的 ID，缓存永不命中，全部压到数据库。

处理：**缓存空值**——未命中回源查库也没有时，写一个短 TTL（30–60 秒）的空标记；或前置布隆过滤器拦掉不存在的 ID。

### 缓存击穿（热点键过期瞬间大量请求回源）

单个热点键过期，同一瞬间上千请求同时回源。

处理：回源加互斥（`SET key val NX EX ttl` 抢锁，抢不到的短暂等待后重读缓存）；或热点键逻辑过期（值里带过期时间戳，过期后由第一个读到的请求异步刷新，其余先返回旧值）。

### 缓存雪崩（大量键同时过期 / Redis 整体不可用）

处理：TTL 加随机抖动打散过期时间；数据库侧加限流与熔断，保证 Redis 挂掉时数据库不被打死——**缓存不可用时系统应降级而非崩溃**，这一点要在设计时明确写出降级行为。

## 危险命令

| 命令 | 问题 | 替代 |
|---|---|---|
| `KEYS pattern` | 阻塞整个实例遍历全部键 | `SCAN` 游标分批 |
| `FLUSHALL` / `FLUSHDB` | 清空数据 | 生产禁用，用 `SCAN` + 定向 `DEL` |
| `DEL bigkey`（大 Hash/Set） | 释放大对象阻塞 | `UNLINK`（异步释放） |
| `HGETALL` 大 Hash | 单次拉取巨量数据 | `HSCAN`，或拆键 |
| `SMEMBERS` 大 Set | 同上 | `SSCAN` |

**大键（bigkey）是 Redis 头号性能问题**：单个 String > 10KB，或集合类元素数 > 5000，就要考虑拆分。设计阶段就估算，别等线上告警。

## 交付前自检

- [ ] 每个键有完整的生命周期矩阵行
- [ ] 命名遵循 `域:实体:标识`，多租户带租户 ID
- [ ] 已按用途选择 TTL 或确认清理；唯一恢复状态不会仅因到期失去接管依据
- [ ] 失效/确认清理、孤儿回收与被逐出后的恢复行为明确
- [ ] 仅对适用缓存采用 TTL 抖动，未改变安全、配额与去重窗口
- [ ] 未命中行为已定义（回源 / 空值 / 报错）
- [ ] 容量估算做过（键数 × 值大小）
- [ ] 无大键设计（> 10KB String 或 > 5000 元素集合）
- [ ] Redis 不可用时的降级行为已写明
- [ ] 代码里无 `KEYS` / `FLUSHALL`
