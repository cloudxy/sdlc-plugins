# 评估集建设与受控迭代

## 为什么评估集必须先建

AI 效果没有编译错误。改坏了不报错，只是**悄悄变差**。

```
无评估集的迭代：
  改 prompt → 手工试几条 → 「感觉好了」→ 上线 → 线上反馈变差 → 不知道是哪次改动

有评估集的迭代：
  改 prompt → 跑 100 条 → 82% → 81% → 这次改动是负向，回滚
```

手工试几条的问题：你会**下意识挑选自己觉得会过的样本**，且样本量太小（3 条全对不代表 80% 准确率）。

## 评估集规模与分层

### 规模

| 任务复杂度 | 规模 |
|---|---|
| 简单分类（2–5 类） | 100–150 条 |
| 复杂分类 / 抽取 | 200–300 条 |
| 生成类（摘要/改写） | 100–200 条（人工评成本高） |
| 样本量依据 | 根据目标误差、风险、分层和成本确定；小样本只能支持有限结论 |

**50 条时单条错误影响 2 个百分点**——分数波动会掩盖真实变化。能拿到更多数据就拿。

### 五层分层（不能全是典型样本）

```
典型场景    40%   最常见的真实输入
边界场景    25%   超长、超短、缺字段、格式异常、特殊字符、多语言混杂
困难场景    20%   人也要想一下的、有歧义的、需要上下文推断的
对抗场景    10%   可能诱导错误输出的、prompt 注入尝试
历史失败     5%   线上真实错例（有的话，价值最高）
```

**只有典型样本的评估集会给虚高分数。** 典型样本上 95%，加入边界后可能掉到 78%——后者才是线上会遇到的。

各层要**分别看分数**，不只看总分：

```
总分 84%
  典型 96%   ← 好
  边界 71%   ← 问题在这里
  困难 68%
  对抗 90%
```

总分掩盖了边界场景的问题。分层报告能直接指出改进方向。

## 标注口径

**标注规范比标注本身重要。** 口径不清，两个人标同一条会给不同答案，评估集本身就不可靠。

### 每个标签写四项

```
标签：需要人工介入

定义：工单内容表明用户情绪激烈或涉及金额纠纷，自动回复可能激化矛盾

正例：
  - 「我已经投诉三次了，再不解决我就去消协」（情绪激烈 + 多次投诉）
  - 「你们扣了我 2000 块，凭什么？」（金额纠纷）
反例：
  - 「怎么修改收货地址？」（普通咨询，语气平和）
  - 「订单还没发货，麻烦催一下」（有诉求但语气正常）

边界规则（最重要）：
  - 有金额但只是询问（「运费多少」）→ 不算纠纷 → 不需人工
  - 语气强硬但无实质诉求（「你们效率太低了」）→ 不需人工
  - 提到「投诉」但是在问投诉渠道 → 不需人工
  - 同时满足多条件时 → 需人工（保守策略，因为漏判代价高）
```

**边界规则是标注规范的核心**。定义和例子容易写，边界情况才是分歧发生的地方。

### 一致性检验（不能跳过）

```
① 取 20 条，两个人独立标
② 算一致率 = 一致条数 / 20
③ < 80% → 口径不清，回去改规范，重标
④ ≥ 80% → 逐条讨论不一致的，把结论写进边界规则
⑤ 剩余样本可以单人标
```

**跳过一致性检验的后果**：后面所有效果数字都建立在一个自己都不自洽的标准上。你会花几周优化一个测不准的指标。

单人标注时也要做**自我一致性检查**：隔一天重标 20 条，看和第一次是否一致。不一致说明自己的口径也在漂移。

## 划分与冻结

```
dev（开发集）  70%   迭代时反复看，允许过拟合
test（测试集） 30%   只在关键节点跑，不许用来调 prompt
```

**为什么测试集必须冻结**：反复看着测试集调 prompt，你会（有意或无意地）针对它优化，它就变成了第二个开发集，失去了「预测线上表现」的能力。

关键节点才跑 test：方案定型时、上线前、大改动后。跑完不要根据 test 结果继续调——那样就污染了它。

**test 分数明显低于 dev** 说明在 dev 上过拟合了（prompt 里塞了太多针对 dev 特例的规则）。

### 版本化

```
eval-set-v1  初版，100 条
eval-set-v2  补充线上错例 30 条，修正 5 条标注错误
eval-set-v3  新增对抗层 15 条
```

**效果数字必须绑版本号**：「84%（eval-set-v2）」。不同版本的分数不可比——v3 加了对抗样本，分数下降不代表模型变差。

## 指标选择

### 分类任务

| 指标 | 什么时候用 | 陷阱 |
|---|---|---|
| 准确率（Accuracy） | 类别均衡 | **不平衡数据下无意义**（99% 是负例时，全猜负例就有 99%） |
| 精确率（Precision） | 误报代价高 | 单看会漏掉召回问题 |
| 召回率（Recall） | 漏报代价高 | 单看会导致过度报警 |
| F1 | 需要平衡 | 掩盖了 P/R 的具体分布 |
| PR-AUC | 不平衡数据 | 比 ROC-AUC 更适合不平衡场景 |

**先想清楚误报和漏报哪个代价高**，再选指标：

```
「需要人工介入」的判断：
  漏报（该人工的没转人工）→ 用户激怒，可能投诉升级 → 代价高
  误报（不该人工的转了人工）→ 浪费一点人力 → 代价低
  → 优化召回率，接受较低精确率
```

这个权衡要**问 `/pm`**，不是技术判断。

### 生成任务

| 方式 | 适用 | 说明 |
|---|---|---|
| **人工评可接受性** | 主要手段 | 二分（可接受/不可接受）比五级评分一致性更高 |
| 关键要素检查 | 摘要、抽取 | 规则检查必须包含的要素是否都在 |
| 结构校验 | JSON 输出 | schema 校验，自动 |
| BLEU / ROUGE | **谨慎** | 与人的判断相关性弱，不要当主指标 |
| LLM-as-judge | 辅助 | 需要先验证 judge 与人工标注的一致性，否则是用一个不确定评另一个不确定 |

**不要用自动指标伪装主观质量评估。** ROUGE 上升 5 个点不代表摘要变好了，可能只是更多地复制了原文词汇。

LLM-as-judge 可以用，但**必须先测它和人工的一致性**（同样 30 条，judge 与人标对比）。一致性不够就不能用它做决策依据。

## 受控迭代

### 每轮只变一个变量

```
❌ 轮 3：改了 prompt 措辞 + 换 gpt-4o-mini + 温度 0.7→0.3
        分数 76% → 83%，不知道哪个起作用，也不知道有没有互相抵消

✅ 轮 3：只改 prompt 措辞          76% → 79%
   轮 4：只换模型                  79% → 82%
   轮 5：只调温度 0.7→0.3          82% → 83%
```

单变量的收益：知道每个改动的贡献，能回滚具体的某个改动，能判断哪个方向值得继续投入。

### 迭代记录（全部保留）

| 轮 | 改了什么（一个变量） | dev 分数 | 分层分数 | 主要失败模式 |
|---|---|---|---|---|
| 1 | 基线：关键词规则 | 68% | 典型 85 / 边界 52 / 困难 40 | 无法处理隐含情绪 |
| 2 | 换 LLM + 零样本 prompt | 74% | 典型 88 / 边界 65 / 困难 58 | 过度判定为需人工 |
| 3 | prompt 加 3 个反例 | 79% | 典型 92 / 边界 70 / 困难 62 | 长文本时忽略后半段 |
| 4 | 长文本先摘要再判断 | 82% | 典型 93 / 边界 78 / 困难 68 | 多语言混杂时误判 |
| 5 | prompt 声明语言无关 | 81% | 典型 92 / 边界 77 / 困难 67 | — |
| 6 | 回滚轮 5，改用示例覆盖多语言 | 84% | 典型 94 / 边界 80 / 困难 70 | 剩余错误多为真实歧义 |

**轮 5 是负向的，也要记录。** 只报轮 6 的 84% 会让人以为一路顺利上升，掩盖了「声明式指令不如示例有效」这个重要发现。

### 看失败样本比看分数重要

**每轮至少人工看 10 条错例**，归类失败模式：

```
轮 3 的 21 条错例归类：
  长文本忽略后半段    8 条  ← 最大类，优先处理
  隐含情绪未识别      5 条
  多语言混杂          4 条
  真实歧义（人也难判） 3 条  ← 这类可能是天花板
  标注错误            1 条  ← 修正评估集
```

分数告诉你「有多少错」，错例告诉你「往哪改」。**最大的失败类别就是下一轮的改进方向**。

「真实歧义」类别的占比是**天花板信号**：如果 15% 的样本连人都判不准，就不要指望模型到 95%。这个数字要告诉 `/pm`，避免承诺做不到的准确率。

**标注错误也会被发现**——模型答对了但评估集标错了。这类要修正评估集并记录（说明评估集本身的质量在提升）。

## prompt 版本管理

prompt 是代码，同库版本管理：

```
prompts/
  triage_v1.txt          基线
  triage_v2.txt          加反例
  triage_v3.txt          当前生产版本
  README.md              每版对应的评估分数与变更说明
```

**要能回答**：当前生产用的是哪版？它的评估分数是多少（哪个评估集版本）？上一版是什么、为什么换？

不做版本管理的后果：线上效果变差时，无法确定当前 prompt 与上次测过的是否一致。

## 线上效果回归

上线不是终点。三件事持续做：

```
① 每次改动重跑评估集 —— AI 没有编译错误，改坏了不会报错
② 线上采样人工检查 —— 上线初期高频（每天几十条），稳定后降频
③ 线上错例进评估集 —— 这是评估集持续改进的主要来源
```

**线上分布会漂移**：用户的输入方式会变、业务场景会扩展。三个月前 85% 的方案，现在可能只有 70%——不是模型变了，是输入变了。定期用新的线上数据补充评估集。

## 可比性

数据/标签/评分器改变时重跑基线与候选；开发集用于调试，留出集独立。表中规模与比例是规划示例，不能视为统计充分性保证；结果报告分层覆盖、重复试验和不确定性，不靠样本门槛宣布质量。
