# RAG 管线设计与诊断

## RAG 的核心问题

**生成质量的上限由检索质量决定。** 检索不到正确内容时，再好的模型也只能编——而且它会编得很流畅，让人看不出来。

所以 RAG 的调优顺序是：**先修检索，再调生成**。反过来做是最常见的时间浪费。

## 管线各环节

```
文档 → ① 切分 → ② 嵌入 → ③ 存储 → ④ 检索 → ⑤ 重排 → ⑥ 组装 → ⑦ 生成 → ⑧ 引用校验
```

每个环节都有独立的失效模式。**必须分环节评估**，否则只能看到「最终答案不对」但不知道哪一步坏了。

### ① 切分（最容易被低估）

| 策略 | 说明 | 适用 |
|---|---|---|
| 固定长度 | 每 N token 一块 | 快速起步，但会切断语义 |
| 重叠窗口 | 固定长度 + 10–20% 重叠 | 缓解切断问题，常用默认 |
| **按结构切** | 按标题层级、段落、条款编号 | **文档有结构时首选** |
| 语义切分 | 按语义相似度断点 | 无结构长文本 |
| 父子块 | 检索小块，返回其所属大块 | 需要上下文的问答 |

**按结构切通常明显优于固定长度**：法规按条款切、文档按小节切、FAQ 按问答对切。结构本身携带了作者对语义边界的判断。

切分要**保留元数据**：来源文档、标题路径、页码、更新时间。这些是引用校验与过滤的基础。

**块大小的权衡**：太小则上下文不足（检索到了但信息不完整），太大则噪声多且浪费 token。常见起点 300–800 token，需要按实际效果调。

### ② 嵌入

- **中文场景要用支持中文的嵌入模型**，不要用纯英文模型
- 同一套内容的**索引与查询必须用同一个嵌入模型**（换模型要全量重建索引）
- 嵌入模型换代时，效果可能明显提升——值得定期评估新模型

### ③ 存储与元数据过滤

向量库要支持**元数据过滤**（按时间、来源、权限过滤）。这不是可选项：

```
多租户场景：必须按 tenant_id 过滤 —— 否则跨租户泄露知识库内容
时效性场景：按更新时间过滤 —— 否则检索到已废弃的旧版文档
权限场景：  按可见范围过滤 —— 否则用户看到无权访问的内容
```

**权限过滤必须在检索层做**，不能靠生成时的 prompt 约束。模型不会可靠地遵守「不要引用第 3 篇」这种指令。

### ④ 检索

| 方式 | 优势 | 劣势 |
|---|---|---|
| 向量检索 | 语义相似，能匹配同义表达 | 精确匹配差（型号、编号、专有名词） |
| 关键词检索（BM25） | 精确匹配强 | 无法处理同义表达 |
| **混合检索** | 两者互补 | 需要融合策略（RRF 等） |

**混合检索通常明显优于单一方式。** 尤其在有专有名词、编号、型号的场景——用户问「XR-200 的保修期」，向量检索可能返回其它型号的保修条款。

`top_k` 的选择：先取较多（20–50）再重排，比直接取 3–5 更好。

### ⑤ 重排

用交叉编码器（cross-encoder）对候选重排，比向量相似度准确得多（它同时看查询和文档，而不是各自编码后算距离）。

**收益通常很明显**，成本是增加一次模型调用的延迟。延迟预算允许时应该做。

### ⑥ 组装

```
系统指令
+ 检索到的内容（带来源标记，用于引用）
+ 用户问题（明确分隔，声明为数据）
```

三条纪律：

- **每个块带来源标记**（`[doc-3]`），要求模型引用时标注 —— 这是引用校验的基础
- **明确要求「基于给定内容回答，不确定就说不知道」** —— 减少但不能消除编造
- **用户输入放在明确分隔的区域**并声明为数据（防 prompt 注入）

上下文长度不够时，优先保留重排后最相关的块，而不是简单截断。

### ⑦ 生成

温度设低（0–0.3）——RAG 场景要的是忠于检索内容，不是创造性。

### ⑧ 引用校验（最常被跳过，但很有用）

**要求模型给出引用，然后校验引用是否真实存在且相关。**

```
① 模型输出：「保修期为 24 个月 [doc-3]」
② 校验：doc-3 是否在检索结果里？
③ 校验：doc-3 是否真的包含「24 个月」这个信息？
④ 不通过 → 标记为低置信，或降级为「未找到明确答案」
```

这一步能拦掉相当一部分编造。实现成本不高（字符串/语义匹配），收益明确。

## 分环节评估

**只评最终答案无法定位问题。** 至少分两段评：

### 检索评估（先做这个）

```
评估集：50–100 个「问题 → 正确答案所在的块 ID」对

指标：
  Recall@k   —— 正确块在 top-k 里的比例（最重要）
  MRR        —— 正确块的平均排名倒数
  Precision@k—— top-k 里相关块的比例
```

**Recall@5 < 80% 时不要碰生成环节** —— 检索都找不到，生成再怎么调都是无源之水。

### 生成评估

```
在「检索正确」的子集上评估生成质量：
  忠实度（faithfulness）—— 回答是否只基于检索内容，有无编造
  相关性              —— 是否回答了问题
  完整性              —— 是否遗漏了检索内容里的关键信息
```

**分开评的价值**：总分 70% 可能是「检索 90% × 生成 78%」也可能是「检索 75% × 生成 93%」——改进方向完全不同。

## 常见失效与诊断

| 症状 | 可能原因 | 怎么查 |
|---|---|---|
| 答案完全不相关 | 检索没找到 | 看检索结果，查 Recall@k |
| 答案部分正确但遗漏 | 切分把信息切断了 | 看被检索到的块，是否信息不完整 |
| 精确查询失败（型号/编号） | 纯向量检索 | 加关键词检索（混合） |
| 检索到但答案还是错 | 生成环节问题 | 在检索正确的子集上单独评生成 |
| 编造不存在的内容 | prompt 未约束 + 无引用校验 | 加「不确定就说不知道」+ 引用校验 |
| 引用了不存在的来源 | 无引用校验 | 加校验 |
| 检索到过时内容 | 无时间过滤 | 元数据加更新时间 + 过滤 |
| 跨租户/越权内容泄露 | **检索层无权限过滤** | **元数据过滤，不靠 prompt** |
| 长文档只用到开头 | 上下文截断策略差 | 按重排分数保留，不简单截断 |
| 同一问题答案不稳定 | 温度过高 | 降到 0–0.3 |
| 延迟过高 | 重排 + 长上下文 | 减 top_k、缓存、异步预热 |

**「检索到但答案还是错」与「检索没找到」是两个完全不同的问题**，混在一起排查会浪费大量时间。先分环节定位。

## 与 /dba 和 /backend 的协作

| 给谁 | 内容 |
|---|---|
| `/dba` | 向量库选型的数据语义诉求；元数据字段（含 `tenant_id`）；索引重建的运维成本 |
| `/backend` | 检索接口契约、超时设置、降级链（检索失败时怎么办）、缓存策略 |
| `/architect` | 是否引入向量库（这是不可逆决策，要 ADR）、成本与延迟预算 |
| `/sre` | 索引重建流程、向量库监控、成本告警 |

**引入向量库是不可逆决策**（新增一套存储的运维、备份、监控），要走 `/architect` 的 ADR。先问：关系库的全文检索能力够用吗？数据量小、查询模式简单时经常够。

## 上线前自检

- [ ] 切分策略按文档结构（有结构时），块大小经过评估
- [ ] 块保留元数据（来源、标题路径、更新时间、租户）
- [ ] 嵌入模型支持目标语言；索引与查询同模型
- [ ] **权限/租户过滤在检索层**（不靠 prompt）
- [ ] 时效性场景有更新时间过滤
- [ ] 用了混合检索（有专有名词/编号时必须）
- [ ] 检索评估集已建，Recall@5 ≥ 80%
- [ ] 生成评估在「检索正确」子集上单独做
- [ ] prompt 要求基于给定内容、不确定说不知道
- [ ] 用户输入在分隔区域并声明为数据
- [ ] 每块带来源标记，输出要求引用
- [ ] 引用校验已实现
- [ ] 温度 ≤ 0.3
- [ ] 检索失败的降级行为已定义
- [ ] 延迟与成本已实测（含重排环节）
- [ ] 索引重建流程已交 `/sre`
