# 无监督场景：分群与异常检测

无标签场景的核心困难：**没有客观的对错，评估必须结合业务**。所以纪律不同于有监督建模——业务可解释性优先于统计指标。

## 分群（聚类）

### 先问「分群要用来做什么」

**没有用途的分群是最常见的浪费**：跑出 5 个簇，画了漂亮的雷达图，然后没人用。

```
① 分完群要做什么 —— 差异化运营？定价？产品功能取舍？
② 每群要能被描述 —— 运营要能一句话说清「这群人是谁」
③ 群数要可执行 —— 运营团队能同时维护几套策略？（通常 3–6 个）
```

**群数上限由执行能力决定，不由轮廓系数决定。** 统计上最优的 12 个簇，运营做不出 12 套策略，等于没分。

### 特征选择决定分群语义

**分群结果完全由输入特征决定。** 用什么特征 = 你想按什么维度分：

| 输入特征 | 得到的分群语义 |
|---|---|
| 消费金额 + 频次 + 最近购买 | RFM 价值分群 |
| 功能使用频率 | 使用行为分群 |
| 生命周期阶段特征 | 成熟度分群 |
| 全部特征一起丢进去 | **语义混乱，无法解释** |

**不要把所有特征都丢进去。** 按分群目的选 3–8 个特征，且这些特征在业务上属于同一个语义维度。

### 预处理必做

```
① 标准化 —— 否则「金额」（万级）会压倒「频次」（个位数）
② 处理长尾 —— 金额类特征通常极度右偏，考虑 log 变换
③ 处理异常值 —— 极端值会独占一个簇
④ 相关特征去重 —— 高相关特征等于给该维度加权
```

**忘记标准化是最常见的错误**，它会让分群完全由量纲最大的特征决定。

### 方法选择

| 方法 | 适用 | 注意 |
|---|---|---|
| K-Means | 球形簇、规模相近 | 需预设 k；对异常值敏感 |
| 层次聚类 | 需要看层级结构、样本量小 | 计算成本高 |
| DBSCAN | 任意形状、能识别噪声点 | 密度差异大时表现差 |
| **业务规则分箱** | 维度少且业务有共识（RFM 打分） | **优先试这个** |

**业务规则分箱经常优于算法聚类**：RFM 各维度切 3 档、组合成 27 类再合并成 5 组——可解释、可复现、业务能理解、不需要重训。

算法聚类的价值在于**发现意料之外的结构**。如果业务已经知道该怎么分，就不需要算法。

### 评估：统计指标只是辅助

| 层面 | 手段 |
|---|---|
| 统计 | 轮廓系数、簇内距离/簇间距离（**只用于排除明显糟糕的方案**） |
| **业务可解释性** | 每群能否一句话描述？特征分布差异是否符合直觉？ |
| **稳定性** | 换时间窗重跑，群体结构是否相似？（不稳定的分群无法用于长期策略） |
| **可执行性** | 群数在运营能力内？各群规模够大（太小的群不值得单独策略）？ |
| **业务差异** | 各群在**未参与分群的业务指标**上是否有显著差异？ |

**最后一条是最好的验证**：用消费特征分群，然后看各群的留存率是否不同。如果不同，说明分群捕捉到了真实差异；如果一样，这个分群对业务没意义。

### 分群交付物

每个群必须给出：

```
群名（业务语言，不是「簇 3」）
规模（人数与占比）
一句话画像
关键特征的均值/分布（与整体对比）
在业务指标上的差异（留存、ARPU 等）
建议策略
```

**「簇 0/1/2」这种命名交付出去就没人用。** 命名成「高频小额型」「沉睡高价值型」才能进入运营讨论。

## 异常检测

### 先定义「异常」

**异常检测比分群更依赖定义。** 三种完全不同的场景：

| 类型 | 例 | 方法倾向 |
|---|---|---|
| **点异常** | 单笔交易金额异常 | 统计阈值、孤立森林 |
| **上下文异常** | 金额正常但对该用户异常 | 按实体建立个体基线 |
| **集体异常** | 单笔都正常但序列异常（分批小额套现） | 序列/图方法 |

**上下文异常最常被误处理**：用全局阈值检测「大额交易」，会把大客户的正常交易全报出来。要按实体建个体基线。

### 有标签就不是异常检测

如果有历史标注的异常样本（确认的欺诈记录），**优先用有监督方法**——它几乎总是优于无监督。

无监督异常检测适用于：从未见过的异常类型、标注极少、需要发现未知模式。

**实践中常见的组合**：无监督做初筛（降低人工审核量）→ 人工确认 → 积累标签 → 转有监督。这个路径要在方案里写明。

### 方法

| 方法 | 适用 | 注意 |
|---|---|---|
| **统计阈值**（分位数、3σ） | 单变量、分布近正态 | 最简单，先试；长尾分布用分位数不用 σ |
| 孤立森林 | 多变量、高维 | 无需假设分布 |
| LOF | 局部密度异常 | 对参数敏感 |
| 自编码器重构误差 | 高维、复杂模式 | 需要较多数据；解释性差 |
| **规则组合** | 业务已知的异常模式 | **优先，且可解释** |

**业务规则优先**：已知的欺诈模式（同一设备多账号、注册即大额）用规则写出来，比模型更可靠且能解释给风控团队。

### 评估：无标签时怎么评

```
① 人工审核 top-N —— 取分数最高的 50 条人工判断，算精确率
② 已知案例召回 —— 用历史确认的异常case测能否检出
③ 误报率成本 —— 人工审核能力有限，误报率直接决定可用性
④ 稳定性 —— 换时间窗，异常率是否稳定（暴涨说明阈值不适应新分布）
```

**人工审核 top-N 是最实用的评估**：它直接回答「审核这 50 条，有多少是真异常」——这就是业务能感受到的价值。

### 阈值不是模型的一部分

**阈值由业务能力决定，且需要能随时调整**：

```
每天能人工审核 100 条
→ 阈值设在「每天报出约 80 条」的位置（留缓冲）
→ 阈值必须可配置，不硬编码
```

审核能力变化时（人员增减、大促期间）阈值要跟着调。把阈值做成配置项，这一点写进给 `/backend` 的交付说明。

## 与有监督建模的共同纪律

无监督也不能违反这些：

| 纪律 | 说明 |
|---|---|
| **as-of 口径** | 特征仍然不能包含未来信息 |
| 按时间切分验证 | 用早期数据分群，看晚期数据是否落入相似结构 |
| 基线对比 | 业务规则分箱 / 全局阈值 是基线 |
| 离线在线一致性 | 特征计算逻辑必须一致 |
| 坏例分析 | 看误报案例，归类原因 |
| 失效边界 | 哪些人群/场景不适用 |

**「无监督所以不用验证」是错的。** 只是验证方式不同：从「预测准不准」变成「结构稳不稳、业务上有没有差异」。

## 交付自检

**分群**

- [ ] 分群用途明确（分完要做什么动作）
- [ ] 群数在运营执行能力内（通常 3–6）
- [ ] 特征按分群目的选择，语义维度一致（不是全部丢进去）
- [ ] 已标准化；长尾特征已变换；异常值已处理
- [ ] 试过业务规则分箱作为基线
- [ ] 每群有业务语言的命名与一句话画像
- [ ] 换时间窗重跑，结构稳定
- [ ] 各群在**未参与分群的业务指标**上有显著差异
- [ ] 各群规模足够大，值得单独策略

**异常检测**

- [ ] 异常类型已识别（点/上下文/集体）
- [ ] 上下文异常按实体建了个体基线
- [ ] 确认过是否有历史标签（有则优先有监督）
- [ ] 试过业务规则作为基线
- [ ] 人工审核 top-N 算了精确率
- [ ] 已知案例的召回已测
- [ ] 阈值按审核能力设定，且**可配置不硬编码**
- [ ] 换时间窗验证异常率稳定
- [ ] 无监督→有监督的演进路径已写明

**共同**

- [ ] as-of 口径无泄漏
- [ ] 离线在线特征一致性已校验
- [ ] 坏例已归类
- [ ] 失效边界已写进 model-card
