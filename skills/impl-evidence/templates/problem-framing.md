## 1. 业务问题与决策用途

**没有决策用途的模型不要建。**

| 项 | 内容 |
|---|---|
| 业务问题 | <高价值用户流失率上升> |
| **预测出来做什么动作** | <向高流失风险用户发送挽留优惠券 + 人工回访> |
| 谁执行 | <系统自动发券；人工回访由客户成功团队> |
| **处理能力上限** | <人工回访每天 50 个；发券无上限但预算 ￥2 万/月> |
| 不做动作的后果 | <按现流失率，季度损失约 <n> 万> |

### 能力约束决定指标（关键）

```
每天只能人工回访 50 人
→ 不需要「全量准确率」，需要「top-50 的精确率」
→ 主指标：Precision@50 / lift@top-2%
→ 不用 AUC 作主指标
```

## 2. 标签定义

**精确到可以写成 SQL。**

```sql
-- 流失标签定义
-- 「在 as-of 后 30 天内无任何登录，且此前 90 天内至少登录 3 次」
SELECT u.user_id,
       CASE WHEN COUNT(l2.id) = 0 THEN 1 ELSE 0 END AS is_churned
  FROM users u
  JOIN logins l1 ON l1.user_id = u.user_id
                AND l1.at >= :asof - INTERVAL 90 DAY
                AND l1.at <  :asof
  LEFT JOIN logins l2 ON l2.user_id = u.user_id
                     AND l2.at >= :asof + INTERVAL 7 DAY      -- 间隔期后
                     AND l2.at <  :asof + INTERVAL 37 DAY     -- 标签窗 30 天
 GROUP BY u.user_id
HAVING COUNT(DISTINCT l1.id) >= 3                             -- 此前活跃
```

| 项 | 定义 | 理由 |
|---|---|---|
| 事件定义 | <「活跃」= 登录（不含被动推送打开）> | <登录代表主动使用> |
| 标签窗 | <30 天> | <业务共识：30 天不登录基本不会回来> |
| **间隔期** | <7 天> | **<挽留动作需 7 天执行，模型必须提前 7 天预测>** |
| 特征窗 | <as-of 前 90 天> | <覆盖一个完整行为周期> |

### 三个时间窗

```
|------- 特征窗 90d -------|-- 间隔 7d --|--- 标签窗 30d ---|
       观察行为              预留执行期      观察结果
                          ↑
                      as-of（预测时刻）
```

**没有间隔期的模型经常无用**——它在用户已决定离开的当天才预测出来。

### 人群范围（含排除规则与理由）

| 规则 | 理由 |
|---|---|
| 排除注册 < 30 天 | <特征窗数据不足，且新用户流失是另一个问题（激活）> |
| 排除已注销 | <已流失，非预测对象> |
| 排除内部/测试账号 | <行为模式异常> |
| 排除企业账号 | <多人共用，个体行为模型不适用>（见 model-card 失效边界） |

**排除规则直接影响模型能用在谁身上**，必须写清。

## 3. 样本构造

| 项 | 内容 |
|---|---|
| as-of 点选取 | <每月 1 日，共 8 个点（2026-01 至 2026-08）> |
| 样本量 | <总 <n> 条，其中正例 <n> 条（<x>%）> |
| 同一用户多样本 | <是，不同 as-of 各一条 → **切分需保证实体不跨集**> |
| 正例率 | <3.2%>（**不平衡 → 不用准确率作指标**） |

## 4. 切分方案

| 集 | 时间范围 | 样本量 | 正例率 |
|---|---|---|---|
| 训练 | <2026-01 至 06 的 as-of 点> | <n> | <x>% |
| 验证 | <2026-07> | <n> | <x>% |
| **测试** | <2026-08（最新）> | <n> | <x>% |

- [ ] 按时间切分（**未随机切时序数据**）
- [ ] 实体不跨集（同一用户不同时在训练与测试）
- [ ] 测试集是最新时段
- [ ] 计划做滚动窗口验证（报告各折方差）

## 5. 指标与目标

| 项 | 指标 | 目标 | 理由 |
|---|---|---|---|
| **主** | <Precision@50> | <≥ 40%> | <回访能力 50/天，报出来的要有 4 成真流失> |
| 辅 | <lift@top-2%> | <≥ 5> | <业务易理解> |
| 辅 | <PR-AUC> | <≥ 0.25> | <总体排序能力> |
| 参考 | <Recall@50> | — | <只能覆盖一小部分，不作目标> |
| 校准 | <需要 / 不需要> | — | <按概率分档发券 → 需要校准> |

**不用准确率**：正例率 3.2%，全猜负例即 96.8%。

## 6. 基线阶梯

| 级 | 方案 | 预期 | 实际 |
|---|---|---|---|
| ① | 常量（全预测不流失） | Precision@50 = 3.2% | <填> |
| ② | 单规则「30 天未登录」 | — | <填> |
| ③ | 逻辑回归 + 5 特征 | — | <填> |
| ④ | 树模型 + 全特征 | — | <填> |

**复杂模型必须证明超过简单基线，且好得值那份复杂度**（特征管线 + 模型服务 + 监控的成本）。

很多场景下规则基线已够用——这不是失败，是省下了整套 ML 基建。

## 7. 预测时刻的数据可获取性（上线前关键核对）

| 数据 | 离线有 | **线上预测时能拿到** | 说明 |
|---|---|---|---|
| <登录行为> | ✅ | ✅ 实时 | |
| <订单数据> | ✅ | ✅ T+0 | |
| <客服工单> | ✅ | ⚠️ T+1 延迟 | <特征需按 T+1 口径重算> |
| <第三方画像> | ✅ | ❌ **拿不到** | <该特征必须删除> |

**「离线数据里有」不等于「预测时刻有」。** 这一栏没核对就建模，上线时会发现一半特征拿不到。
