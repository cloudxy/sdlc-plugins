# Prototype branches

## CONCEPT

Use a short story, annotated flow or sample input/output when the uncertainty is what the user means or how a proposed experience fits. Include the scenario, the decision/question and what feedback is needed. Mark invented examples as illustrations. The user can reject the whole framing; revise the question instead of polishing the rejected concept. No code is required. Prepared materials alone are not observed results.

## LOGIC

Use the smallest executable model that can answer the question: HTML for a state walkthrough, a CLI/notebook or scratch harness for computation. For an HTML state model, isolate the reducer/machine from the DOM and show relevant state after actions. A user's “that shouldn't be possible” is a reported rule discrepancy to resolve, not an automatic technical verdict.

Avoid unrelated production infrastructure. A correctness, concurrency or performance question needs repeatable checks and appropriate actual inputs; a simulated screen cannot establish throughput. Keep all runtime data and code in the declared scratch paths.

## UI

Compare meaningful visual alternatives only while a visual choice is unresolved; a route/switcher or side-by-side material can help. Reuse accepted constraints rather than reopening them. Prototype-only tokens must be labelled; production still consumes designer tokens.

## FAKE

A waitlist, “notify me” or pricing concept can test a specified intent hypothesis. A local draft or simulated click is preparation, not measured demand. Live exposure and data collection require explicit authorization and an appropriate disclosure/handling plan; no charges. Record actual observed actions, denominator/context and limitations. A click alone does not establish willingness to pay. This is discovery, not a production launch.
