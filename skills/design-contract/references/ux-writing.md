# 文案即设计内容

> 界面里出现文字只有一个理由：让产品更容易被理解和使用。文案是设计内容，不是装饰——它和间距、颜色一样需要刻意设计。这直接决定 edge-states.md 的质量：每个状态的文案都是设计决策，不是实现时随手编的。

## 命名：用户视角，不是系统视角

用用户能懂的语言命名，不按系统怎么建来命名：

```
✅ 用户「管理通知」          ❌ 界面叫「Webhook 配置」
✅ 「导出记录」              ❌ 「下载历史数据集快照」
```

具体、对新用户清晰，永远胜过聪明。描述这个东西**是什么/做什么**，不要推销它。

## 主动语态：CTA 说出会发生什么

按钮文案 = 按下之后发生的动作，不是含糊的动词：

```
✅ 「保存更改」    ❌ 「提交」
✅ 「发布文章」    ❌ 「确定」
✅ 「测试连接」    ❌ 「执行」
```

## 动作命名贯穿整个流程

一个动作在流程全程保持同一个名字——按「发布」按钮，出来的 toast 就该是「已发布」：

```
按钮「测试连接」 → 成功 toast「连接成功」   ✅ 名字连贯
按钮「测试连接」 → 成功 toast「操作完成」   ❌ 断裂——用户要猜"操作"是哪个
```

界面词汇是用户在产品里认路的路标；连贯一致是用户学会认路的唯一方式。

## 错误文案公式

**发生了什么 + 现在怎么做**，用界面的口吻，不是某个人的口吻：

```
✅ 连接失败：API Key 无效或已过期。检查 Key 后重新测试。
❌ 抱歉，出了点问题！            ← 道歉 + 含糊，用户不知道下一步
❌ Error: Exception in handler  ← 系统口吻泄漏，用户无法行动
```

错误**不道歉**，也**从不含糊**。含糊的错误文案会制造重复工单——用户看不懂就只能来找人工。

## 空态 = 邀请行动

空屏不是句号，是邀请函：

```
✅ 还没有接入任何供应商。「添加供应商」开始接入 →
❌ 暂无数据                      ← 死胡同
```

## 六态的文案责任

[edge-states](../templates/edge-states.md) 里每个状态都需要文案，文案责任分配：

| 状态 | 文案要回答 | 常见错误 |
|---|---|---|
| 空态 | 现在能做什么 | 「暂无数据」死胡同 |
| 加载 | 在发生什么（可感知进度） | 无任何提示白屏 |
| 错误 | 发生了什么 + 怎么办 | 道歉/含糊/堆异常栈 |
| 边界 | 恰好到限值时说什么 | 静默截断 |
| 权限 | 谁能做 + 怎么获得权限 | 只说「无权限」 |
| 离线 | 哪些仍可用 + 恢复后怎样 | 假装一切正常 |

## 语气基线

平实动词、sentence case、无填充词；语气与品牌和受众匹配。**每个文字元素只做一件事**——一个提示框别同时解释概念、道歉、推销新功能。

## 与其他规范的关系

- 纯图标按钮的 `aria-label` 文案也归设计，规则见 [tokens-and-a11y.md](tokens-and-a11y.md)（「删除工单」不是「删除」）
- 错误文案里的错误码透出规范见仓库 `/coding-style`（面向用户的消息永远不带堆栈）
