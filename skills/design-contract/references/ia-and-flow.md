# 信息架构与用户流程

## 信息架构：从任务到导航

### 为什么不能按系统模块分组

系统模块反映的是**技术边界**，用户心智反映的是**任务归属**。两者经常不一致：

```
系统模块：工单模块 / 用户模块 / 导出模块
用户心智：我的工作台 / 我导出过的东西 / 团队设置

「导出历史」放哪？
  按系统 → 工单模块下（因为导出的是工单）
  按心智 → 「我导出过的东西」（用户想的是「我之前做的操作」）
```

判据：**用户找这个功能时，脑子里想的第一个词是什么？** 想的是「我的下载」就不该放在工单模块深处。

不确定时找 `/ops` 拿真实反馈，或做卡片分类（把功能名给几个真实用户，让他们自己分组）。

### 任务清单的提取

从 FR 提取，**动词开头**：

```
FR-01 主管可批量导出未结工单
  → 任务：导出工单
FR-06 超过 10000 行转异步，完成后通知
  → 任务：查看导出进度、接收完成通知
FR-03 导出行为记审计日志
  → 不是用户任务（系统行为，无界面）
```

**不是每条 FR 都对应用户任务**。审计、埋点这类是系统行为，标注「无界面」，避免后面核对时以为漏了。

### 导航深度

| 使用频率 | 可达层级 |
|---|---|
| 每天多次 | **1 层**（主导航直达，或快捷键） |
| 每天一次 | ≤ 2 层 |
| 每周一次 | ≤ 3 层 |
| 极少用（设置、导出历史） | 3 层可接受 |

**超过三层基本没人找得到。** 如果一个常用功能只能放三层深，说明信息架构本身需要重组。

### 路由命名

```
/tickets                    列表
/tickets/:id                详情
/tickets/:id/edit           编辑
/exports                    导出历史列表
/exports/:id                单个导出详情
```

三条纪律：

- **名词复数 + ID**，不用动词（`/tickets/:id` 而非 `/viewTicket?id=`）
- **可预测**：知道列表是 `/tickets`，就该能猜到详情是 `/tickets/:id`
- **状态进查询参数**：`/tickets?status=open&page=2`，不要为筛选建新路由

路由是 `/frontend` 的实现契约，也是用户可分享的链接——命名定了就不要轻易改（改了旧链接全失效）。

## 用户流程

### flow 不是页面清单

```
❌ 页面清单
   1. 工单列表页
   2. 导出配置弹窗
   3. 下载

✅ flow：屏序列 + 每屏的进入/交互/离开
```

页面清单只说了「有哪些屏」，flow 要说清「怎么从一屏到下一屏」「每屏能做什么」「做了之后会怎样」。

### 每屏必须写的六项

```
屏 N：<名称>
├─ 进入方式    从哪来（导航点击 / 上一屏的哪个操作 / 深链接）
├─ 关键元素    这屏有什么（不用穷举所有元素，列关键的）
├─ 主操作      用户在这屏最主要做的一件事
├─ 交互描述    每个交互元素的行为与条件（文字，不只靠图）
├─ 离开方式    有哪些出口，各自去哪
└─ 返回行为    从下一屏返回时，这屏是什么状态
```

**「返回行为」最容易漏，也最容易被抱怨**：用户填了半个表单，进下一步又返回，发现填的东西没了。

### 交互描述要具体到条件

```
❌ 「点击导出按钮进入配置」

✅ 「导出按钮：
     - 未勾选任何行时 disabled，tooltip 显示「请先选择要导出的工单」
     - 勾选后 enabled，文案变为「导出 (30)」，数字随勾选变化
     - 勾选数超过 10000 时仍 enabled，但显示警告图标 +
       tooltip「超过 10000 条将转为后台导出」
     - 点击后进入屏 2（弹窗），列表保持当前勾选与滚动位置」
```

**disabled 的条件、文案的动态变化、点击后原状态是否保留** —— 这三项 `/frontend` 必须知道，图里看不出来。

### 四个交互态

每个可交互元素都要定义：

| 态 | 定义什么 |
|---|---|
| `hover` | 视觉变化（用哪个 token） |
| `focus` | **键盘焦点的可见样式**（不能只有 hover 没有 focus） |
| `active` | 按下瞬间的反馈 |
| `disabled` | 视觉 + **为什么禁用的说明方式** |

`focus` 经常被漏：设计稿是鼠标视角画的，键盘用户看不到焦点在哪。

`disabled` 的说明方式三选一：tooltip（悬停可见，触摸设备不友好）、旁注文案（始终可见，占空间）、点击时提示（发现成本高）。**按场景选，但必须选一个。**

### 分支与异步

```
屏 3：导出结果
├─ 分支 A：行数 ≤ 10000
│   → 立即下载 + Toast「导出成功」+ 弹窗关闭
├─ 分支 B：行数 > 10000
│   → 弹窗关闭 + 页面顶部出现进度条
│   → 进度条可点击进入 /exports/:id 查看详情
│   → 完成时：站内通知 + 进度条变为「下载」按钮
│   → 用户离开页面再回来：进度状态从服务端恢复（不依赖前端内存）
└─ 分支 C：失败
    → 见 edge-states.md 错误态，按错误码分
```

**异步流程要定义四件事**：进度怎么看、离开页面再回来怎样、完成怎么通知、失败怎么办。少一个前端就得自己编。

### 首次使用 vs 熟练使用

高频功能要考虑两种用户：

```
首次使用：需要引导（空态的说明、第一次的提示、示例数据）
熟练使用：需要效率（记住上次的选择、快捷键、批量操作、跳过确认）
```

**熟练用户的效率优化**在高频功能上收益很大：记住上次选择的导出列、支持键盘全选、不要每次都弹确认框。

但**破坏性操作永远要确认**——删除、覆盖、不可逆操作不因为用户熟练就跳过。

## 设计范围核对

交付前逐条 FR 核对，这一步是防漏的唯一手段：

| FR | 涉及的屏 | flow 覆盖 | 六态齐全 | 结论 |
|---|---|---|---|---|
| FR-01 | 屏 1、2、3 | ✅ | ✅ | 覆盖 |
| FR-04 权限 | 屏 1（按钮）、屏 2（范围选择） | ✅ | ⚠️ 缺权限态 | **待补** |
| FR-03 审计 | — | ➖ 无界面 | ➖ | 系统行为 |
| FR-06 异步 | 屏 3 分支 B | ✅ | ⚠️ 缺离线态 | **降级声明** |

三种结论：

- **覆盖** —— flow 与六态都齐
- **待补** —— 有缺口，本轮补
- **降级声明** —— 本轮不做，写明理由并同步 `/pm`（例：「内网工具无离线场景，不做离线态」）

**「无界面」要显式标注**，否则核对时无法区分「漏了」和「不需要」。
