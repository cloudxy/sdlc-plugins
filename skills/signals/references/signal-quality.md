# 信号质量：偏差、归纳、量化

## 渠道偏差

**每个渠道都有系统性偏差。** 不知道偏差就会得出错误结论。

| 渠道 | 谁会出现在这里 | 谁不会 | 典型误判 |
|---|---|---|---|
| 工单/客服 | 遇到麻烦且愿意花时间反馈的 | 满意的、放弃的、自己解决的 | 「产品到处是问题」 |
| 应用商店评论 | 极度满意或极度不满的 | 中间态（大多数） | 「用户爱憎分明」 |
| 社群/社交 | 活跃、外向、有影响力的 | 沉默用户、企业用户 | 把 KOL 的偏好当大众需求 |
| 主动访谈 | 愿意配合的（通常是重度用户） | 轻度用户、已流失用户 | 高估功能复杂度需求 |
| 问卷 | 有耐心填的 | 忙的、不在乎的 | 问法引导出的假需求 |
| NPS | 两端 | 中间 | 分数波动被过度解读 |
| **使用数据** | 所有人（客观） | — | 知道做了什么，不知道为什么 |

### 沉默的大多数

**主动反馈的用户通常不到 1%。** 所以：

```
9 个人抱怨「导出麻烦」
+ 使用数据显示 89 人在 10 分钟内连续导出 3 次以上
= 至少 89 人有这个需求（沉默的 80 人用重复操作表达了）
```

**行为数据是发现沉默需求的唯一手段。** 这是运营最有价值的产出之一——它把「9 个人的抱怨」变成「89 个人的问题」，改变了优先级。

### 已流失用户的声音最难拿到也最重要

他们不再提工单（因为不用了），但他们的离开原因是最关键的信息。手段：流失前的最后几条反馈、退订问卷、主动回访（转化率低但值得）。

## 归纳方法

### 合并的判据是「问题本质」不是「关键词」

```
同一主题（不同表达，同一问题）：
  「导出太麻烦了」
  「能不能一次导出多个」
  「每次只能下一个，要点五十次」
  → 批量导出缺失

不同主题（同一关键词，不同问题）：
  「导出的文件打不开」        → 文件格式兼容
  「导出太慢，等了五分钟」    → 性能
  「导出的列不够用」          → 功能完整性
```

按关键词分组会把三个不同的问题混成「导出问题」，`/pm` 拿到后无法分诊。

### 区分症状与原因（不要在归纳阶段下判断）

```
用户说：「导出太慢了」

可能的原因：
  ① 真的慢（服务端耗时长）
  ② 无进度提示，等待感被放大
  ③ 用户预期错位（以为是即时的，实际是批量任务）

归纳时的正确记法：
  主题：导出等待体验差
  用户原文：<3 条>
  可能原因：真实性能 / 无进度反馈 / 预期管理
  待验证：需要 /analyst 看实际耗时分布
```

**下判断是 `/pm` 和 `/analyst` 的事。** 你把可能性都列出来，比选一个猜测更有价值。

### 保留原文样本

每个主题附 **2–3 条真实原文**。这是主题真实性的证据，也保留了情绪强度：

```
「每次只能下一个，要点五十次」（工单 #4521）
    ↑ 这句比「用户希望批量导出」有信息量得多：
      它给出了具体数字（五十次）和真实痛感
```

改写会丢失这些。`/pm` 读原文能感受到问题的严重程度。

### 严重度不同的不合并

```
❌ 主题：导出问题（12 条）
   混了「导出功能完全不可用」（故障）和「导出的列想自定义」（体验）

✅ 分开：
   导出失败率高（故障，3 条）→ **立即转 /sre**
   导出列不可自定义（体验，9 条）→ 信号池
```

**故障不走信号池。** 信号池是需求输入，故障是运维事件——混在一起会延误处理。

## 影响面量化

### 三个数字

| 数字 | 定义 | 陷阱 |
|---|---|---|
| 提及次数 | 多少条反馈提到 | **不等于人数**（一人可能提 5 次） |
| **影响用户数** | 多少个不同用户受影响（去重） | 这才是排序依据 |
| 频次 | 受影响用户多久遇到一次 | 每天一次 vs 每月一次，紧迫度差很多 |

### 行为数据交叉验证

**这一步能把信号强度提升一个量级。** 方法：找出「用行为表达需求」的模式。

| 需求主题 | 行为信号 |
|---|---|
| 批量操作缺失 | 短时间内重复同一操作 N 次 |
| 搜索能力不足 | 搜索后无点击，或连续修改关键词 |
| 功能难发现 | 功能使用率极低但满意度不差 |
| 流程太长 | 中途放弃率高（漏斗某步骤流失） |
| 字段/列不够 | 导出后立即又导出（换配置重试） |
| 性能问题 | 操作后短时间内刷新/重试 |

找 `/analyst` 拿这些数据，或看现有看板。

### 拿不到数据时

**标注「影响面未量化」，不要编数字。**

```
✅ 主题：批量导出缺失
   提及：12 条 / 9 个用户
   影响面：**未量化**（缺少导出功能的埋点，已建议 /pm 在下轮补埋点）
   主观判断：从工单描述看，提及者都是高频使用者

❌ 主题：批量导出缺失
   影响面：约 30% 用户  ← 编的
```

编的数字会进入 `/pm` 的 RICE 打分，污染整个优先级排序。**「未量化」是诚实且有用的信息**，它同时暴露了埋点缺口。

### 信号弱时如实报告

```
✅ 主题：支持暗色模式
   提及：2 条 / 2 个用户
   信号强度：**弱**（样本过小，无法判断代表性）
   建议：若要评估，需主动收集（在设置页加一个「你希望我们做什么」入口）
```

**把 2 条反馈写成「用户强烈要求暗色模式」是最有害的操作**：它可能导致几周的开发投入去解决一个不存在的需求。

## 竞品信息的可靠性分级

| 来源 | 可靠性 | 注意 |
|---|---|---|
| 亲自试用 | **高** | 最可靠，但要注意试用版可能功能受限 |
| 官方文档 | 高 | 可能滞后于实际版本 |
| 用户在公开渠道的评价 | 中 | 有偏差，但能看到真实痛点 |
| 第三方评测 | 中 | 可能过时或有商业关系 |
| 销售材料/官网宣传 | **低** | 系统性夸大 |
| 传闻/内部消息 | **不可用** | 不要写进分析 |

标注来源是让 `/pm` 判断结论可信度的前提。

## 上线后追踪

### 对照当初的预测（不是只看现在的数字）

```
P0 时的假设（引用 /pm 度量蓝图）：
  北极星：工单处理时长下降 15%
  驱动：导出使用率达 30%
  护栏：列表页 P95 不超 1000ms

P9 实际：
  ✅ 使用率 42%（超预期 12 个点）
  ⚠️ 处理时长下降 8%（未达 15%）
  ✅ 列表页 P95 = 820ms（护栏未破）
```

**「对照预测」比「报告现状」有价值得多**：它检验了团队的判断力，且指出假设错在哪。

### 未达成项的分析（不下定论）

```
⚠️ 处理时长仅下降 8%（目标 15%）
   可能原因：
     ① 导出只解决了「取数据」，外部往返仍是瓶颈（P0 时低估了这一环）
     ② 使用率虽 42%，但可能集中在少量工单上
     ③ 统计口径问题（处理时长的定义是否包含等待外部回复）
   建议：请 /analyst 验证原因 ②③
```

**你给可能性，`/analyst` 做验证。** 不要自己下因果结论——没有对照组时只能说「变化」不能说「因为」。

### 三类都报

| 类 | 说明 |
|---|---|
| ✅ 达成 | 简要报 |
| ⚠️ **未达成** | **重点报** + 可能原因 |
| ❌ 新问题 | 新出现的反馈主题，进信号池 |

**只报好数据的 P9 复盘是自我欺骗**，且让下一轮重犯同样的错。未达成的部分才是学习点。

### 原主题的提及量变化

```
主题「批量导出缺失」：
  上线前 30 天：12 条
  上线后 30 天：1 条（且这条是问「能否导出更多列」）
  → 原问题基本解决 ✅

主题「导出速度慢」：
  上线前：5 条
  上线后：7 条  ← 变多了
  → 可能是使用量上升带来的绝对数增加，需按使用量归一化
```

**按使用量归一化**：使用量翻倍时提及量增加 40% 其实是相对下降。不归一化会误判。
